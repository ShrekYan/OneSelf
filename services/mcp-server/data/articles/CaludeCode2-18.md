# Spec-kit Clarify 是怎么把模糊需求问清楚的？

上一篇讲了 `/speckit-specify`：它负责把一句需求变成结构化的 `spec.md`。

但现实开发里，第一版规格文档通常不可能一次就完整。很多关键规则，只有继续追问才会暴露出来。所以这一篇继续讲 Spec-Kit 的第二个阶段：`/speckit-clarify`。

## 一、Clarify 在流程里的位置

Spec-Kit 的主流程是：

```
Specify → Clarify → Plan → Tasks → Implement
```

`Clarify` 位于 `Specify` 之后、`Plan` 之前。

也就是说：

```
先生成 spec.md
 ↓
再澄清 spec.md 里的模糊点
 ↓
再进入技术方案设计
```

它的核心职责是：

在写技术方案之前，把需求里不确定、不完整、容易产生歧义的地方问清楚。

如果说 `specify` 是“先写一版需求说明书”，那 `clarify` 就是“拿着需求说明书继续追问细节”。

## 二、为什么需要 Clarify？

很多需求看起来很简单，但真正进入实现时，会发现大量隐藏问题。

比如我这次的案例是“忘记密码功能”。

初始需求大概是：

```
我想实现忘记密码功能。
前端页面已经实现，位置：apps/web/src/pages/ForgotPassword/index.tsx。
授权微服务：services/auth-service。
业务微服务：services/backend。
中文描述。
```

这段描述能让 AI 生成一版 `spec.md`，但它还不够完整。

因为至少还有几个关键问题没说清楚：

- 验证码能力还没接入时，重置密码流程怎么办？

- 前端是直接调 `auth-service`，还是统一调 `backend`？

- 任务阶段要不要生成单元测试？

- 密码重置成功后旧会话怎么处理？

- 未注册手机号要不要明确提示？

这些问题如果不澄清，后面的 `plan.md` 就只能靠 AI 猜。

而 AI 一旦猜错，后面的任务和代码也会跟着错。

所以 Clarify 的价值就是：

把“AI 猜”变成“用户确认”。

## 三、Clarify 大概怎么执行？

`/speckit-clarify` 的执行机制可以概括成三步：

```
扫描 spec.md
 ↓
提出关键问题
 ↓
把答案写回 spec.md
```

更详细一点：

```
Phase 1: Scan
读取当前 spec.md，扫描需求里的不确定点

Phase 2: Question
挑出最关键的问题，向用户提问

Phase 3: Integrate
把用户答案写入 Clarifications，并同步更新相关章节
```

注意，它不是随便问问题，而是会优先找那些“影响大、又不明确”的地方。

## 四、Clarify 会扫描哪些模糊点？

Clarify 会从多个维度检查 `spec.md`。

常见包括：

| 维度       | 关注点                             |
| ---------- | ---------------------------------- |
| 功能范围   | 功能边界是否明确，哪些做，哪些不做 |
| 数据模型   | 涉及哪些实体、状态、生命周期       |
| 用户流程   | 正常流程、失败流程、空状态是否清楚 |
| 非功能要求 | 性能、安全、隐私、审计等是否明确   |
| 外部依赖   | 第三方服务不可用时怎么办           |
| 边界情况   | 异常输入、重复操作、冲突场景       |
| 术语一致性 | 同一个概念是否有多个叫法           |
| 成功标准   | 是否可衡量、可测试                 |

以忘记密码为例，最关键的模糊点就不是“页面好不好看”，而是这些更影响实现的问题：

- 验证码暂时没接入时，是否允许重置密码？

- 前端应该调用哪个服务？

- 是否需要单元测试任务？

这些答案会直接影响后续的技术方案和任务拆分。

## 五、Clarify 的提问不是越多越好

`/speckit-clarify` 通常不会无限提问。

它会优先挑最关键的问题，一次最多问几个高影响问题。

这是一个很重要的设计。

因为如果 AI 把所有细节都拿来问，用户会很累，流程也会变慢。

所以 Clarify 的目标不是“问完所有问题”，而是：

先解决会影响架构、数据、任务和验收的关键不确定性。

一些不重要的问题，可以留到后面实现时自然解决。

比如：

```
按钮文案用“确认”还是“提交”
```

这类问题一般不值得在 Clarify 阶段阻塞流程。

但下面这种问题就很关键：

```
验证码未接入时，是否允许不校验验证码直接重置密码？
```

因为它会影响 API 行为、验收标准、安全边界和后续任务。

## 六、案例：忘记密码功能里的 3 个澄清问题

在我的 `forgot-password` 规格里，最终留下了 3 条澄清记录：

```
## Clarifications ### Session 2026-06-05 - Q: 目前验证码能力未接入时，重置密码流程应如何处理验证码？
 → A: 暂不校验验证码；只要手机号和密码字段合法即可重置。

- Q: 忘记密码流程中前端应直接调用哪个后端服务？
 → A: 前端只调用 backend；backend 作为中间层调用 auth-service 完成认证能力。

- Q: 忘记密码任务清单是否需要生成单元测试任务？
 → A: 不需要任务单元测试；以 lint/build/typecheck 和 quickstart 手工验收为主。
```

这三条看起来不长，但影响很大。

下面拆开看。

## 七、澄清 1：验证码未接入时怎么办？

问题是：

```
目前验证码能力未接入时，重置密码流程应如何处理验证码？
```

答案是：

```
暂不校验验证码；只要手机号和密码字段合法即可重置。
```

这个澄清会直接影响规格里的多个地方。

比如用户故事里出现了：

```
在验证码未接入阶段完成可用恢复流程
```

对应的验收场景也变成：

```
Given 验证码能力未接入，
When 用户提交已注册手机号、合法新密码和一致的确认密码，
Then 系统不校验验证码并完成密码重置。
```

Functional Requirements 里也明确写入：

```
FR-004: 当前阶段验证码能力未接入时，系统 MUST 允许不校验验证码完成密码重置。
FR-010: 用户 MUST 能够提交手机号、新密码和确认密码完成密码重置；验证码字段在当前阶段不作为重置成功的必要条件。
```

这就是 Clarify 的作用：

一个回答，不只是记录在问答里，还会同步影响用户故事、验收标准、功能需求和边界情况。

## 八、澄清 2：前端应该调用哪个服务？

问题是：

```
忘记密码流程中前端应直接调用哪个后端服务？
```

答案是：

```
前端只调用 backend；backend 作为中间层调用 auth-service 完成认证能力。
```

这个问题对我的项目很重要。

因为项目是 Monorepo 多服务结构：

```
apps/web # 前端 H5
services/auth-service # 认证服务
services/backend # 主业务服务 / BFF 中间层
services/log-service # 日志服务
```

忘记密码属于认证能力，但前端不直接调用 `auth-service`，而是统一调用 `backend`，再由 `backend` 调用 `auth-service`。

这条澄清最终进入了功能需求：

```
FR-020: 忘记密码前端入口 MUST 只调用 backend 暴露的接口，由 backend 作为中间层调用 auth-service 完成认证领域处理。
```

如果没有这个澄清，Plan 阶段可能会出现两种不同方案：

```
方案 A：web → auth-service
方案 B：web → backend → auth-service
```

AI 可能会任选一个。

而 Clarify 的作用就是在进入 Plan 前，把这种关键架构边界先确认掉。

## 九、澄清 3：是否需要单元测试任务？

问题是：

```
忘记密码任务清单是否需要生成单元测试任务？
```

答案是：

```
不需要任务单元测试；以 lint/build/typecheck 和 quickstart 手工验收为主。
```

这个澄清会影响后续 `tasks.md` 的内容。

如果没有说明，AI 可能会自动生成很多测试任务，比如：

```
编写 auth-service 单元测试
编写 backend controller 测试
编写前端表单测试
```

但这次需求明确不生成单元测试任务，而是以：

```
lint / build / typecheck / quickstart 手工验收
```

作为主要验证方式。

这会让后续任务清单更符合当前开发目标。

## 十、Clarify 会把答案写到哪里？

最直接的位置是 `spec.md` 的 `Clarifications` 章节。

结构大概是：

```
## Clarifications ### Session 2026-06-05 - Q: ... → A: ...
- Q: ... → A: ...
```

但它不只是追加问答记录。

一个澄清答案还可能同步更新：

| 澄清类型 | 可能更新的位置                    |
| -------- | --------------------------------- |
| 功能规则 | Functional Requirements           |
| 边界情况 | Edge Cases                        |
| 用户流程 | User Story / Acceptance Scenarios |
| 验收方式 | Success Criteria / Tasks 输入     |
| 数据概念 | Key Entities / Assumptions        |
| 服务边界 | Requirements / Assumptions        |

所以 `Clarifications` 更像是“决策记录”，而不是唯一生效位置。

真正重要的是：这些回答会变成 `spec.md` 的正式内容。

## 十一、Clarify 后为什么要重新 Plan？

因为 `plan.md` 是从 `spec.md` 推导出来的。

如果 Clarify 修改了 `spec.md`，那么后续计划也应该跟着更新。

例如这条澄清：

```
前端只调用 backend；backend 作为中间层调用 auth-service。
```

会影响 Plan 阶段的系统调用链：

```
web → backend → auth-service
```

而不是：

```
web → auth-service
```

再比如这条澄清：

```
当前阶段暂不校验验证码。
```

会影响：

- API 参数校验

- 后端服务逻辑

- quickstart 验收流程

- 后续真实验证码接入说明

所以每次 Clarify 后，都要意识到：

```
spec.md 变了，下游文档也可能需要重新生成或更新。
```

## 十二、什么时候需要运行 Clarify？

我现在的经验是，只要出现下面这些情况，就适合运行 Clarify：

- 需求里有“先暂时”“后续再接入”这类阶段性策略

- 功能涉及多个服务，调用边界不明确

- 验收方式没有说清楚

- 错误提示、安全策略、权限规则有歧义

- 用户故事写出来后，你感觉还缺点东西

- Plan 阶段开始前，想再确认一遍需求没有坑

忘记密码这种功能就非常适合 Clarify。

因为它涉及：

- 账号安全

- 验证码能力

- 密码规则

- 服务调用边界

- 错误提示是否暴露账号存在性

- 会话失效策略

这些点如果不提前说清楚，后面很容易返工。

## 十三、什么时候不需要 Clarify？

不是所有事情都要 Clarify。

下面这些情况一般没必要：

- 改一个文案

- 改一个按钮样式

- 修一个明确的小 bug

- 调整代码格式

- 技术实现细节已经在 Plan 阶段解决

Clarify 主要解决的是“需求不明确”，不是替代所有讨论。

## 十四、Clarify 阶段的几个注意点

### 1. 不要把技术实现问题都塞给 Clarify

比如：

```
这个接口用 POST 还是 PATCH？
```

如果它不是需求层面的关键差异，更适合放到 Plan 阶段。

Clarify 更应该问：

```
用户重置密码成功后，是否需要让旧会话失效？
```

这是业务规则，会影响实现，但本身不是技术细节。

### 2. 澄清记录要写得像决策

好的澄清记录应该是明确的：

```
暂不校验验证码；只要手机号和密码字段合法即可重置。
```

不好的记录是模糊的：

```
验证码以后再说。
```

前者能指导后续实现，后者仍然会让 AI 猜。

### 3. Clarify 不是只能运行一次

如果后续发现 spec 仍然有问题，可以再次运行 Clarify。

它不是一次性动作，而是一个需求补全工具。

只要 `spec.md` 还在被使用，Clarify 就可以继续帮助你把模糊点补清楚。

## 十五、总结

`/speckit-clarify` 的核心价值是：

把模糊变清晰，把猜测变确认，把口头决定写进 spec.md。

它通常做三件事：

```
扫描 spec.md
 ↓
提出关键问题
 ↓
把答案写回 spec.md
```

在我的忘记密码案例里，Clarify 最终确认了 3 个关键决策：

1. 当前验证码能力未接入时，暂不校验验证码也可以重置密码

2. 前端只调用 backend，由 backend 调用 auth-service

3. 本次任务不生成单元测试，以 lint/build/typecheck 和 quickstart 手工验收为主

这 3 个回答，直接影响了后续的 `plan.md`、`tasks.md` 和实现方式。

所以我觉得 Clarify 是 Spec-Kit 里非常关键的一步。

它不负责写代码，但它能减少很多“代码写完才发现需求理解错了”的返工。

下一篇我会继续讲 `/speckit-plan`：当需求已经明确之后，Spec-Kit 是如何把 `spec.md` 转成技术实现计划的。
