## 🏗️ 技术栈决策

### FADR-001: 采用 React 19 + Vite 技术栈

**状态**: ✅ 已采纳

**决策**:
- 核心框架: React 19.x
- 构建工具: Vite 7.x
- 类型系统: TypeScript 5.x
- UI 组件库: Ant Design Mobile 5.x
- 状态管理: MobX 6.x + mobx-react 9.x
- 路由: React Router Dom 6.x

**为什么**:
- React 19 支持 Server Components、React Compiler 等现代化特性
- Vite 极快的冷启动和 HMR，提升开发体验
- Ant Design Mobile 成熟的移动端组件生态，减少重复造轮子
- MobX 简单高效的响应式状态管理，学习成本低

**边界约束**:
- ❌ 不引入其他状态管理库（Redux、Zustand、Jotai）
- ❌ 不使用其他构建工具（Webpack、Rspack）
- ❌ 不使用其他 UI 库（Vant、NutUI）

---

### FADR-002: 启用 React Compiler 编译优化

**状态**: ✅ 已采纳

**决策**:
- 生产构建时启用 babel-plugin-react-compiler
- Vite 配置中集成 React Compiler 插件

**为什么**:
- 编译时自动优化重渲染，减少手动 memo 样板代码
- 框架级优化，业务代码无需侵入式修改
- 显著提升复杂组件的渲染性能

**边界约束**:
- 开发阶段可根据性能需求选择性开启/关闭
- 极端性能场景可配合手动 memo 优化

## 📦 状态管理架构决策

### FADR-003: MobX 双轨状态管理架构

**状态**: ✅ 已采纳

**决策**:
- **全局状态层**: RootStore 单例模式，跨页面共享数据
- **页面状态层**: useLocalObservable Hook，页面内私有状态

**为什么**:
- 全局状态和页面状态分层，避免状态污染
- 局部状态随页面生命周期自动销毁，无内存泄漏
- 全局状态单一入口，便于追踪和调试
- 符合 MobX 最佳实践，类型安全

**边界约束**:
- ❌ 页面状态原则上不允许跨页面访问，确有需要提升到全局
- ❌ 禁止使用 observer HOC，必须用 useObserver Hook

## 📄 页面架构决策

### FADR-004: 页面四文件标准拆分模式

**状态**: ✅ 已采纳

**决策**:
每个页面包含 4 个核心文件，职责严格分离：
- `index.tsx` - 页面主组件
- `useStore.ts` - 页面状态
- `constant.ts` - 常量定义
- `types.ts` - 类型定义

**为什么**:
- 强制关注点分离，单一职责原则
- 状态逻辑与 UI 解耦，便于单元测试
- 类型定义集中，便于维护和查找

**边界约束**:
- ❌ handle.ts 已废弃，不再使用
- ❌ index.tsx 中不直接调用 API，必须通过状态层或业务 Hook

---

### FADR-005: Hooks 业务分层架构

**状态**: ✅ 已采纳

**决策**:
- handle.ts 已废弃，复杂业务逻辑统一抽离到 `hooks/useXxx.ts`
- 分层原则：状态管理（useStore）+ 业务逻辑（hooks）+ 渲染（组件）
- 满足任一条件即拆分：代码 > 30 行 / 依赖 2+ 个 Hook / 完整业务流程 / 复杂异步逻辑

**为什么**:
- 符合 React 官方规范（Hook 只能在 Hook 或组件中调用）
- 降低认知负担，不用纠结"放 handle 还是 hooks"
- 职责清晰：状态修改放 store，业务逻辑放 hooks，组件只负责渲染
- Hooks 可以独立测试，复用性更高
- 代码更内聚，相关逻辑放在一起

**边界约束**:
- ❌ Hooks 中不允许直接修改 MobX 状态（必须通过 store 方法）
- ❌ 简单逻辑不要过度抽离，直接写在组件内即可
- ❌ 跨页面通用 Hook 必须放在 `apps/web/src/hooks/`，不能放在页面目录下

## 🎨 样式架构决策

### FADR-006: 设计令牌体系

**状态**: ✅ 已采纳

**决策**:
所有设计令牌统一在 `src/styles/variables.scss` 定义：
- 颜色系统（主色、状态色、文本色）
- 字体层级（大小、字重）
- 间距系统（8px 网格）
- 圆角系统
- 阴影系统

**为什么**:
- 设计系统统一，视觉一致性高
- 主题切换时只需修改变量文件
- 避免魔法值，代码可维护性高
- 便于与设计团队协作（Design Token 对齐）

**边界约束**:
- ❌ 禁止硬编码颜色值，必须使用 SCSS 变量
- ❌ 禁止硬编码间距，必须使用间距变量
- ❌ 组件级局部样式不允许定义新的全局变量

## 🛣️ 路由架构决策

### FADR-007: React Router v6 模块化路由架构

**状态**: ✅ 已采纳

**决策**:
- 按业务模块拆分路由文件
- RouteInterceptor + KeepAliveLayout 双层嵌套
- enhanceRoutes 自动生成 fullPath

**为什么**:
- 模块化路由便于大型项目团队协作
- 统一的路由守卫机制，安全校验不遗漏
- 自动 fullPath 生成，避免手动维护路径错误
- 类型安全的 RouteConfig 扩展

**边界约束**:
- ❌ 所有路由必须同时嵌套 RouteInterceptor + KeepAliveLayout
- ❌ 禁止直接修改 index.tsx 添加路由配置
- ❌ 不允许替换为其他路由库

---

### FADR-008: AppHistoryProvider 应用历史栈

**状态**: ✅ 已采纳

**决策**:
- 应用级历史栈管理，独立于浏览器 history
- 支持自定义跳过规则（登录页、注册页等不入栈）
- 统一的 useAppHistory、useAppGoBack Hooks

**为什么**:
- 解决移动端 SPA 返回键直接退出应用的用户体验问题
- 灵活控制哪些页面不进入历史栈
- 统一的返回行为管理，避免各页面自行处理

## 🔌 API 架构决策

### FADR-009: Axios 分层封装架构

**状态**: ✅ 已采纳

**决策**:
- 核心层（core/）: axios-instance、缓存、取消管理
- 业务层（[module]/）: 各业务模块 API 定义

**核心能力**:
- RequestCache - GET 请求内存缓存
- CancelManager - 页面卸载自动取消未完成请求
- 统一错误处理

**为什么**:
- 分层封装，职责清晰
- 缓存减少重复请求，提升性能
- 自动取消避免内存泄漏
- 类型安全的 API 调用，前后端契约明确

**边界约束**:
- ❌ 所有 API 必须走封装后的实例，不能直接用 axios

### FADR-010: HttpOnly Cookie 认证方案

**状态**: ✅ 已采纳

**决策**:
- 启用 withCredentials: true（axios 全局配置）
- 禁止 localStorage/sessionStorage 存储任何 Token
- 前端不手动设置 Authorization 请求头
- Cookie 由后端设置，浏览器自动携带

**为什么**:
- 从根本上防御 XSS 攻击窃取 Token
- 符合 OWASP 安全最佳实践
- 简化前端认证逻辑，减少安全漏洞

**边界约束**:
- ❌ 代码中绝对不能出现 localStorage.getItem('token')
- ❌ 请求拦截器中不允许设置 Authorization header
- ❌ 禁止在任何日志中输出 Token 相关信息

## ⚙️ 构建与优化决策

### FADR-011: 生产构建优化策略

**状态**: ✅ 已采纳

**决策**:
- 代码分割：vendor / antd / utils 三分包
- 生产移除 console
- sourcemap: 开发开启，生产关闭
- 生产压缩: esbuild

**为什么**:
- 合理的代码分割减少首屏加载时间
- 生产环境移除调试信息提升安全性
- 开发环境保留完整调试能力

**边界约束**:
- ❌ VConsole 绝对不能出现在生产构建中

### FADR-012: React 错误边界与降级策略

**状态**: ✅ 已采纳

**决策**:
- 全局错误边界（main.tsx 最外层）
- 页面级错误边界（路由层）
- 友好的错误降级 UI + 重试按钮

**为什么**:
- 避免单个组件崩溃导致整个应用白屏
- 提升用户体验，错误时给出明确引导
- 便于错误追踪和定位

**边界约束**:
- 每个新的顶层容器都必须包裹错误边界
- 生产环境绝对不能暴露堆栈信息

### FADR-013: Vitest + Testing Library 测试体系

**状态**: ✅ 已采纳

**决策**:
- 测试运行器: Vitest
- 测试库: @testing-library/react
- 用户事件: @testing-library/user-event
- 覆盖率: c8

**测试优先级（投入产出比从高到低）**:
1. 工具函数
2. 公共组件
3. 复杂业务逻辑
4. 路由守卫和拦截器
5. Store action 方法

**为什么**:
- Vitest 与 Vite 无缝集成，速度极快
- Testing Library 关注用户行为，不是实现细节
- 合理的测试优先级，投入产出比最大化

**边界约束**:
- ❌ 不使用其他测试框架（Jest、Cypress）
- 覆盖率作为参考指标，不做硬性 KPI 要求

### FADR-014: Monolithic 前端架构（近期不引入微前端）

**状态**: ✅ 已采纳（1年内不引入微前端）

**决策**:
- 当前阶段保持 Monolith 单应用架构
- 采用 Router 层级的代码分割实现懒加载
- 业务模块通过目录隔离，不拆分为独立仓库

**为什么**:
- 团队规模小（< 5人），微前端引入的复杂度大于收益
- 当前项目处于快速迭代期，架构复杂度会拖慢进度
- Monorepo 已经能满足代码复用需求

**边界约束**:
- ❌ 1年内不引入 Module Federation / qiankun 等微前端方案
- ✅ 业务模块严格目录隔离，为未来拆分预留可能性

---

### FADR-015: 前后端 API 类型手动同步策略

**状态**: ✅ 已采纳（当前阶段）

**决策**:
- 采用"契约优先"方式，后端定义 DTO，前端手动复制类型
- 前端 API 目录结构与后端 Controller 一一对应
- 命名约定：`XxxRequestDto` / `XxxResponseDto`

**为什么**:
- 简单直接，无需引入额外的代码生成工具
- 小团队沟通成本低，API 变更频率可控
- 类型不一致在编译期就能发现

**边界约束**:
- ❌ 禁止使用 swagger-typescript-api 等自动生成工具（避免依赖锁定）
- ✅ API 变更必须同步通知前端
- ✅ 大型 API 变更必须同步更新类型定义

### FADR-016: 轻量级前端监控方案

**状态**: ⏳ 待实现（预留架构位）

**决策预研**:
- **性能指标**: Web Vitals（LCP/FID/CLS）+ 自定义指标（首屏、路由切换）
- **错误监控**: Sentry 基础版 + sourcemap 上传
- **埋点方案**: 纯前端手动埋点（不引入无埋点 SDK）
- **上报策略**: 批量上报 + 失败重试 + 本地缓存

**核心指标采集预研**:
- 页面加载性能（LCP、FCP、TTFB）
- 运行时错误（JS 异常、资源加载失败）
- API 请求性能（成功率、耗时）
- 用户行为埋点（PV、点击、停留时长）

**预留决策点**:
- 当前项目暂不实现监控功能
- 为未来接入监控系统预留架构位
- 预研边界约束：
  - ❌ 不采集用户敏感信息（密码、手机号、身份证）
  - ❌ 不上报完整的请求/响应 body（避免数据泄露）
  - ✅ 采样率可配置，生产环境 10-30% 采样

### FADR-018: 多环境配置管理策略

**状态**: ✅ 已采纳

**决策**:
- Vite `import.meta.env` 驱动环境变量
- 4 个环境: local / dev / test / prod
- 敏感配置（API Key、加密密钥）不提交代码，通过 CI 注入

**环境变量分类**:
| 类型 | 存放位置 | 示例 |
|------|---------|------|
| 公开配置 | `.env.{env}` | API_BASE_URL、CDN_URL |
| 敏感配置 | CI 环境变量 / 服务器环境 | SECRET_KEY、DB_PASSWORD |

**边界约束**:
- ❌ `.env` 文件禁止提交到 Git
- ❌ 前端代码中不能硬编码任何密钥
- ✅ 所有环境变量必须有 TypeScript 类型定义

## 📌 架构决策添加流程

新增架构决策必须按以下流程：
1. **问题定义阶段**: 明确要解决的架构问题
2. **方案对比阶段**: 至少对比 2-3 个可行方案，分析优劣
3. **团队共识阶段**: 前端团队达成共识
4. **记录阶段**: 提交 PR 添加到本文件
5. **执行阶段**: 所有新代码必须遵守
