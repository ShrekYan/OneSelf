## 🏗️ 架构与系统边界决策

### ADR-001: 采用 Monorepo 多微服务架构

**状态**: ✅ 已采纳

**决策**:
- Monorepo 单仓库管理多个独立微服务
- `apps/web/`: 前端 H5 移动端应用
- `services/auth-service/`: 认证授权服务（端口 8889）
- `services/backend/`: 主业务服务（端口 8888）
- `services/log-service/`: 日志服务（端口 8890）
- `packages/shared-logging/`: 跨系统共享日志 SDK

**为什么**:
- 微服务独立部署、独立扩展
- 共享代码通过 packages 目录统一管理
- 明确的职责边界，符合单一职责原则

**边界约束**:
- ❌ 新增系统必须放入对应目录（apps/ 或 services/ 或 packages/）
- ❌ 服务间通过 HTTP API 调用，不直接共享数据库

---

### ADR-002: 认证服务与业务服务分离

**状态**: ✅ 已采纳

**决策**:
- Token 签发、刷新、验证完全由 auth-service 负责
- backend-service 不做 JWT 解析，仅通过 HTTP 调用 auth-service 的 `/introspect` 接口验证
- 认证相关代码从 backend 完全迁移到 auth-service

**为什么**:
- 认证领域独立，符合领域驱动设计
- 安全策略统一管理
- 未来支持多业务服务接入时无需重复实现认证逻辑

**边界约束**:
- ❌ backend 不引入 jsonwebtoken 依赖
- ❌ 所有 Token 验证必须通过 auth-service
- ❌ 后端服务间调用必须使用内网认证

## 🔐 安全与认证决策

### ADR-003: HttpOnly Cookie 为唯一 Token 存储方案

**状态**: ✅ 已采纳

**决策**:
- Access Token 和 Refresh Token 全部通过 HttpOnly Cookie 传输
- 禁止使用 localStorage/sessionStorage 存储任何 Token
- 前端禁止手动设置 Authorization 请求头
- Cookie 自动携带，前端无需干预

**为什么**:
- 从根本上防御 XSS 攻击窃取 Token
- 浏览器自动处理，减少前端代码复杂度
- 符合 OWASP 安全最佳实践

**边界约束**:
- ❌ 任何代码中不得出现 localStorage.getItem('token') 或类似代码
- ❌ 所有 API 调用依赖 Cookie 自动携带机制

---

### ADR-004: 密码加密使用 Argon2id 算法

**状态**: ✅ 已采纳

**决策**:
- 新用户注册默认使用 Argon2id 算法哈希密码
- 兼容历史 bcrypt 用户，支持静默迁移
- 数据库同时存储 `password_hash` 和 `password_algorithm` 两个字段
- 验证成功后自动将 bcrypt 哈希升级为 Argon2id

**为什么**:
- Argon2 是目前最安全的密码哈希算法，抗 GPU/ASIC 攻击
- 支持平滑迁移，用户无感知

**边界约束**:
- ❌ 新增代码禁止使用 bcrypt 哈希新密码
- ❌ 密码验证必须同时支持两种算法

---

### ADR-005: 密码哈希缓存机制

**状态**: ✅ 已采纳

**决策**:
- 密码验证成功后，将算法+哈希缓存到 Redis（TTL: 24h）
- 下次登录优先使用缓存验证，降低 CPU 消耗

**为什么**:
- Argon2 是 CPU 密集型操作，缓存可将登录 QPS 提升 5-10 倍
- 缓存命中率预期 > 95% 对于活跃用户

**边界约束**:
- ❌ 缓存仅做性能优化，数据库始终是唯一真实来源
- ❌ 密码修改后必须立即删除对应缓存

---

## 🗄️ 数据库与 ORM 决策

### ADR-006: Prisma 模型 PascalCase 命名规范

**状态**: ✅ 已采纳

**决策**:
- 所有 Prisma 模型名使用 PascalCase 大驼峰命名
- 数据库表名保持 snake_case 下划线命名（通过 @@map 映射）
- 禁止使用全小写模型名

**为什么**:
- Prisma 生成的 TypeScript 客户端类型正确
- 无需使用 `as any` 绕过类型检查
- 代码类型安全，减少潜在 bug

**边界约束**:
- ❌ `prisma/schema.prisma` 中所有模型名必须是 PascalCase
- ❌ 禁止代码中出现 `(this.prisma as any).articles` 这种写法

---

### ADR-007: 时间字段统一使用 BigInt 毫秒时间戳

**状态**: ✅ 已采纳

**决策**:
- 所有时间字段（created_at, updated_at, expires_at, published_at 等）
- 统一使用 `BigInt` 类型存储 Unix 毫秒时间戳
- 禁止使用 `DateTime` 或 `Date` 类型
- 禁止在数据库层面使用 NOW() 等时间函数

**为什么**:
- 完全避免时区问题（统一 UTC）
- 数据库层面不做时间计算，全部在应用层处理
- 跨系统兼容性最好

**边界约束**:
- ❌ 新增表的时间字段必须是 BigInt 类型
- ❌ 代码中不使用 Prisma 的 `@default(now())`

---

### ADR-008: Redis 刷新令牌存储

**状态**: ✅ 已采纳

**决策**:
- Refresh Token 不再持久化到 MySQL 数据库
- 全部存储在 Redis 中，使用 TTL 自动过期
- 用户维度同时维护索引，支持全设备登出

**为什么**:
- 消除数据库瓶颈，支持更高并发
- 原生 TTL 机制，无需定时清理过期数据
- Redis 更适合短生命周期的会话数据

---

### ADR-009: 数据库连接指数退避重试

**状态**: ✅ 已采纳

**决策**:
- Prisma 和 Redis 连接失败时采用指数退避重试
- 最多重试 5 次：1s → 2s → 4s → 8s → 16s
- 每次重试都记录警告日志
- 慢查询阈值设定为 1 秒，超过则记录警告日志

**为什么**:
- 应对数据库短暂不可用（如主从切换、网络抖动）
- 避免瞬间流量冲垮数据库
- 及时发现性能问题

---

## ⚡ 性能与缓存决策

### ADR-010: HTTP 响应 GZIP 压缩

**状态**: ✅ 已采纳

**决策**:
- 所有后端服务启用 compression 中间件
- 压缩阈值: 大于 1KB 才压缩
- 压缩级别: level 6（性能与压缩率平衡）
- 跳过图片等已压缩的二进制格式

**为什么**:
- JSON 响应压缩率通常可达 70-80%
- 显著减少网络传输体积，提升 API 响应速度
- CPU 开销可接受

**边界约束**:
- ❌ 所有 NestJS 服务必须在 main.ts 配置 compression 中间件

---

### ADR-011: 用户预加载缓存机制

**状态**: ✅ 已采纳

**决策**:
- 系统启动时或定时任务预加载活跃用户到 Redis
- 登录请求优先命中缓存，避免 DB 查询
- 缓存未命中时自动回源 DB 并回填

**为什么**:
- 用户缓存命中率 > 95%
- 登录响应时间 P95 < 50ms

---

## 📝 异常处理与日志决策

### ADR-012: 三层异常过滤器架构

**状态**: ✅ 已采纳

**决策**:
- `BusinessExceptionFilter`: 业务异常，返回友好错误码
- `PrismaExceptionFilter`: 数据库异常，脱敏处理，不泄露表名/字段
- `AllExceptionsFilter`: 兜底异常，捕获所有未处理异常，记录完整堆栈

**为什么**:
- 分层处理，职责清晰
- 防止敏感信息泄露到前端
- 统一错误码管理，便于前端处理

**边界约束**:
- ❌ Prisma 异常绝对不能直接返回到客户端
- ❌ 所有错误码统一在 `business-error-codes.ts` 管理

---

### ADR-013: 统一响应格式标准

**状态**: ✅ 已采纳

**决策**:
- 所有 API 响应统一格式（TransformInterceptor 自动包装）
- 结构: `{ code: number, message: string, data: T }`

**为什么**:
- 前端统一处理响应逻辑
- Swagger 文档自动生成类型
- 前后端交互协议标准化

---

### ADR-014: 定时清理过期数据（每日凌晨 2 点）

**状态**: ✅ 已采纳

**决策**:
- 每日凌晨 2 点执行过期数据清理任务
- Cron 表达式: `0 0 2 * * *`
- 清理内容包括：已过期且已撤销的 Refresh Token
- 可通过 `.env` 的 `CLEANUP_ENABLED=false` 开关禁用

**为什么**:
- 主动清理优于被动膨胀
- 凌晨 2 点是业务低峰，对在线用户影响最小
- 删除操作会锁表，避开高峰时段

## 🏗️ NestJS 架构规范

### ADR-015: 模块分层架构

**状态**: ✅ 已采纳

**决策**:
```
业务模块: Module → Controller → Service
   ↓
Common 模块（过滤器、拦截器、中间件、守卫、装饰器）
   ↓
Infrastructure 模块（PrismaModule、RedisModule）
```

**为什么**:
- 分层清晰，职责明确
- 依赖方向严格控制，避免循环依赖

**边界约束**:
- ❌ Controller 只能注入 Service，不能注入 Prisma 直接操作
- ❌ Common 模块不能依赖业务模块
- ❌ 基础设施模块（Prisma、Redis）必须是全局模块

---

### ADR-016: API 版本控制

**状态**: ✅ 已采纳

**决策**:
- 采用 URI 路径版本控制
- 当前版本: v1
- 所有接口前缀: `/api/v1/*`
- 通过 NestJS 的 `enableVersioning()` 配置实现

---

### ADR-018: 跨服务鉴权策略

**状态**: ✅ 已采纳

**决策**:
- 服务间调用采用 **JWT Token + 服务密钥** 双重认证
- 每个服务分配独立的 `SERVICE_ID` + `SERVICE_SECRET`
- 调用方在请求头中携带：`X-Service-Id` + `X-Service-Signature`（HMAC-SHA256 签名）
- 接收方在 Guard 层统一验证，不通过直接拒绝

**为什么**:
- 防止服务被未授权调用
- 可追溯调用来源，便于问题排查
- 支持细粒度权限控制（哪个服务能调哪个接口）

**边界约束**:
- ❌ 禁止服务间直接使用用户 Token 互相调用
- ✅ 服务密钥定期轮换（建议 90 天）
- ✅ 生产环境密钥必须通过环境变量注入，不硬编码

---

### ADR-019: 分布式事务最终一致性方案

**状态**: ✅ 已采纳

**决策**:
- **原则**: 避免分布式事务，优先通过业务设计保证最终一致性
- **方案 1（推荐）**: 本地消息表 + 定时重试 + 幂等接口
- **方案 2（备选）**: 事件驱动架构 + 补偿机制

**为什么**:
- 两阶段提交（2PC/XA）性能损耗大，不适合高并发场景
- 最终一致性在大多数业务场景下可接受
- 简单方案更容易维护和排查问题

**边界约束**:
- ❌ 禁止引入 Seata 等重量级分布式事务框架
- ✅ 所有写操作接口必须实现幂等
- ✅ 关键操作必须有操作日志，支持人工回滚

---

### ADR-020: 数据库读写分离策略（预留）

**状态**: ⏳ 待实现（预留架构位，QPS > 1000 时启用）

**决策预研**:
- **方案**: MySQL 主从复制 + 基于 TypeORM/Prisma 的读写分离
- **主库**: 处理所有写操作 + 强一致性读操作
- **从库**: 处理可容忍延迟的读操作（列表查询、统计报表、历史数据）
- **路由策略**: 基于注解/装饰器自动路由，支持强制走主库

**当前状态**:
- 数据量小，单库完全满足需求
- 暂不实施，预留架构位，先保证代码可扩展

**边界约束**:
- ❌ 当前阶段不实施读写分离
- ✅ DAO 层设计预留读写路由扩展点
- ✅ 做好监控，QPS 到达阈值时启动实施

## 🏗️ 技术栈决策

### FADR-001: 采用 React 19 + Vite 技术栈

**状态**: ✅ 已采纳

**决策**:
- 核心框架: React 19.x
- 构建工具: Vite 7.x
- 类型系统: TypeScript 5.x
- UI 组件库: Ant Design Mobile 5.x
- 状态管理: MobX 6.x + mobx-react 9.x
- 路由: React Router Dom 6.x

**为什么**:
- React 19 支持 Server Components、React Compiler 等现代化特性
- Vite 极快的冷启动和 HMR，提升开发体验
- Ant Design Mobile 成熟的移动端组件生态，减少重复造轮子
- MobX 简单高效的响应式状态管理，学习成本低

**边界约束**:
- ❌ 不引入其他状态管理库（Redux、Zustand、Jotai）
- ❌ 不使用其他构建工具（Webpack、Rspack）
- ❌ 不使用其他 UI 库（Vant、NutUI）

---

### FADR-002: 启用 React Compiler 编译优化

**状态**: ✅ 已采纳

**决策**:
- 生产构建时启用 babel-plugin-react-compiler
- Vite 配置中集成 React Compiler 插件

**为什么**:
- 编译时自动优化重渲染，减少手动 memo 样板代码
- 框架级优化，业务代码无需侵入式修改
- 显著提升复杂组件的渲染性能

**边界约束**:
- 开发阶段可根据性能需求选择性开启/关闭
- 极端性能场景可配合手动 memo 优化

---

## 📦 状态管理架构决策

### FADR-003: MobX 双轨状态管理架构

**状态**: ✅ 已采纳

**决策**:
- **全局状态层**: RootStore 单例模式，跨页面共享数据
- **页面状态层**: useLocalObservable Hook，页面内私有状态

**为什么**:
- 全局状态和页面状态分层，避免状态污染
- 局部状态随页面生命周期自动销毁，无内存泄漏
- 全局状态单一入口，便于追踪和调试
- 符合 MobX 最佳实践，类型安全

**边界约束**:
- ❌ 页面状态原则上不允许跨页面访问，确有需要提升到全局
- ❌ 禁止使用 observer HOC，必须用 useObserver Hook

---

## 📄 页面架构决策

### FADR-004: 页面四文件标准拆分模式

**状态**: ✅ 已采纳

**决策**:
每个页面包含 4 个核心文件，职责严格分离：
- `index.tsx` - 页面主组件
- `useStore.ts` - 页面状态
- `constant.ts` - 常量定义
- `types.ts` - 类型定义

**为什么**:
- 强制关注点分离，单一职责原则
- 状态逻辑与 UI 解耦，便于单元测试
- 类型定义集中，便于维护和查找

**边界约束**:
- ❌ handle.ts 已废弃，不再使用
- ❌ index.tsx 中不直接调用 API，必须通过状态层或业务 Hook

---

### FADR-005: Hooks 业务分层架构

**状态**: ✅ 已采纳

**决策**:
- handle.ts 已废弃，复杂业务逻辑统一抽离到 `hooks/useXxx.ts`
- 分层原则：状态管理（useStore）+ 业务逻辑（hooks）+ 渲染（组件）
- 满足任一条件即拆分：代码 > 30 行 / 依赖 2+ 个 Hook / 完整业务流程 / 复杂异步逻辑

**为什么**:
- 符合 React 官方规范（Hook 只能在 Hook 或组件中调用）
- 降低认知负担，不用纠结"放 handle 还是 hooks"
- 职责清晰：状态修改放 store，业务逻辑放 hooks，组件只负责渲染
- Hooks 可以独立测试，复用性更高
- 代码更内聚，相关逻辑放在一起

**边界约束**:
- ❌ Hooks 中不允许直接修改 MobX 状态（必须通过 store 方法）
- ❌ 简单逻辑不要过度抽离，直接写在组件内即可
- ❌ 跨页面通用 Hook 必须放在 `apps/web/src/hooks/`，不能放在页面目录下

- 类型安全的 API 调用，前后端契约明确

**边界约束**:

### FADR-010: HttpOnly Cookie 认证方案

**状态**: ✅ 已采纳

**决策**:
- 启用 withCredentials: true（axios 全局配置）
- 禁止 localStorage/sessionStorage 存储任何 Token
- 前端不手动设置 Authorization 请求头
- Cookie 由后端设置，浏览器自动携带

**为什么**:
- 从根本上防御 XSS 攻击窃取 Token
- 符合 OWASP 安全最佳实践
- 简化前端认证逻辑，减少安全漏洞

**边界约束**:
- ❌ 代码中绝对不能出现 localStorage.getItem('token')
- ❌ 请求拦截器中不允许设置 Authorization header
- ❌ 禁止在任何日志中输出 Token 相关信息
