## 📋 方案零：现状（不改造）

### 核心思路

什么都不改，保持现在的模式：

- 每个阶段单独解析成一个 `run-xx` 目录
- 手动记录阶段之间的依赖关系和产物
- 手动管理编号，避免重复

### 优点

- ✅ 开发成本：0
- ✅ 没有任何风险
- ✅ 灵活度最高，想怎么来怎么来

### 缺点

- ❌ 每个阶段都从 T001 开始编号，任务 ID 重复
- ❌ 跨阶段产物完全靠人脑记，容易漏
- ❌ 没有全局进度，做完一个项目要翻 4 个目录
- ❌ 重复加载项目规范，浪费 token
- ❌ 没法自动生成统一的交付报告

### 适用场景

- 只是偶尔做一次多阶段项目
- 项目规模 < 30 个任务
- 不想花时间改造，能凑合用就行

## 🏗️ 方案一：项目根目录模式

> **定位**: 超大项目的企业级完整解决方案

### 核心思路

创建统一的项目根目录，所有阶段都在这个根目录下管理：

```
.claude/runs/
└── 小贝3项目-发车业务-20260510/  # 项目根目录（只创建一次）
    ├── project-manifest.json      # 全局信息总清单
    ├── phase-1-后端API层/
    │   └── task-manifest.json
    ├── phase-2-基础组件库/
    │   └── task-manifest.json
    └── phase-3-业务页面开发/
        └── task-manifest.json
```

### 核心文件格式

```json
// project-manifest.json
{
  "projectId": "小贝3项目-发车业务-20260510",
  "totalPhases": 3,
  "currentPhase": 1,
  "phases": [{ "phaseId": "phase-1", "status": "completed", "taskCount": 15 }],
  "globalOutputs": [
    /* 所有阶段的产物自动汇总 */
  ],
  "globalNextTaskId": 16
}
```

### 具体改动点

1. **xmind-task-parser 改造**（约 3 小时）
   - 检测多阶段项目
   - 创建项目根目录
   - 分阶段生成独立 task-manifest
   - 全局连续编号
   - 支持 `--project-id`、`--phase` 参数

2. **task-executor 改造**（约 3 小时）
   - 识别 project-manifest
   - 自动读取前置阶段产物
   - 产物自动汇总到全局清单
   - 自动更新阶段状态
   - 断点续跑支持

3. **体验优化工具**（约 2 小时）
   - `/project-status` 查看全局进度
   - `/continue-phase` 继续下一个阶段
   - 自动生成项目交付报告

### 优点

- ✅ 目录统一，集中管理，归档方便
- ✅ 全局状态完美，什么都不用手动管
- ✅ 跨阶段依赖自动传递，完全不需要手动传参数
- ✅ 自动生成完整的项目交付报告
- ✅ 支持断点续跑，执行中断不影响
- ✅ 多人协作支持好

### 缺点

- ❌ 开发工作量大：8-12 小时
- ❌ 改的地方多，风险相对较高
- ❌ 学习成本相对高，需要理解整个项目生命周期概念
- ❌ 灵活度低，必须按固定流程走

### 适用场景

- 项目规模 ≥ 50 个任务
- 项目需要长期维护，后续还要回来改
- 需要正规的交付报告和项目归档
- 多人协作开发同一个大项目

## 🧩 方案二：全局编号池 + 产物清单模式

> **定位**: 用最小成本解决 80% 核心问题的务实方案

### 核心思路

**约定大于配置**，完全不改变现有目录结构，只在每个 run 目录里多加一个小文件：

```
.claude/runs/
├── run-20260510-100000-阶段一-后端API层/
│   ├── task-manifest.json
│   └── output-manifest.json  # ← 新增：本阶段产物清单
│
├── run-20260510-140000-阶段二-基础组件库/
│   ├── task-manifest.json
│   └── output-manifest.json  # ← 自动读取前面的产物
│
└── run-20260510-180000-阶段三-业务页面开发/
    ├── task-manifest.json
    └── output-manifest.json
```

### 核心文件格式

```json
// output-manifest.json
{
  "phaseId": "phase-1",
  "phaseName": "后端API层",
  "nextTaskId": 16, // 下一个阶段从这里开始编号
  "outputs": [{ "type": "api", "name": "用户登录接口", "path": "services/auth/src/login.ts" }],
  "hintsForNextPhase": ["发车接口路径是 /v1/normal/departDetail"]
}
```

### 具体改动点

1. **xmind-task-parser 改造**（约 1.5 小时）
   - 新增 `--depends-on` 参数，接受 1 个或多个前置 run 目录
   - 读取前置阶段的 output-manifest
   - 从 `nextTaskId` 开始全局连续编号
   - 把前置产物注入到本阶段上下文

2. **task-executor 改造**（约 2 小时）
   - 每个任务完成后自动识别并记录产物
   - 整个阶段完成后自动生成 output-manifest.json
   - 支持 XMind 里写「给下一阶段提示：xxx」

3. **可选小工具**（约 1 小时）
   - `phase-summary` 一键生成多阶段总览

### 优点

- ✅ 开发工作量极小：4-6 小时，只有方案一的一半
- ✅ 100% 向后兼容，旧项目完全不受影响
- ✅ 风险极低：所有新功能都是可选的，默认不走新逻辑
- ✅ 学习成本极低：只需要多学一个 `--depends-on` 参数
- ✅ 灵活度高：想怎么组合阶段就怎么组合，不想用就不用
- ✅ 渐进式启用：小项目不用，大项目才用

### 缺点

- ❌ 目录还是分散的，归档要找多个文件夹
- ❌ 没有统一的全局状态管理
- ❌ 跨阶段依赖需要手动传 `--depends-on` 参数
- ❌ 没有统一的项目交付报告（需手动调用工具生成）

### 适用场景

- 项目规模 30-80 个任务
- 偶尔做多阶段项目，不是天天做
- 不想冒大风险改造核心功能
- 想要快速上线，这周就能用
- 灵活度比完美统一更重要

## 📄 方案三：增量解析模式

### 核心思路

还是一个 XMind 文件，但是支持标记哪些阶段可以执行：

```
📦 小贝3项目
├── 📂 阶段一：后端API层 [已完成]
│   └── T001...
├── 📂 阶段二：基础组件库 [可执行]  # ← 只解析标记的部分
│   └── T016...
└── 📂 阶段三：业务页面开发 [待执行]
    └── T034...
```

### 具体改动点

1. 解析器支持「只解析标记为 [可执行] 的节点」
2. 执行完自动把标记改成 [已完成]
3. 手动把下一个阶段改成 [可执行]
4. 再次调用解析器增量解析

### 优点

- ✅ 始终一个文件，管理最简单
- ✅ 全局编号天然不会重复
- ✅ 全局视角最好，所有任务都在一个文件里看

### 缺点

- ❌ 一个文件太大，50+ 任务看起来费劲
- ❌ 需要修改解析器核心逻辑，开发量中等
- ❌ 多人协作时同时改一个文件容易冲突
- ❌ 跨阶段产物传递不如方案一、二清晰

### 适用场景

- 项目规模 30-50 个任务
- 单人开发，不需要协作
- 喜欢所有东西都在一个文件里的简洁感

## 🎯 决策指南

### 第一步：先回答这 3 个问题

1. **你做的项目一般多大？**
   - < 30 任务：方案零，不用改
   - 30-80 任务：方案二
   - > 80 任务：方案一

2. **你能接受的开发时间？**
   - 不想花时间：方案零
   - 这周就要用上：方案二（4-6 小时）
   - 不急，想要完美：方案一（8-12 小时）

3. **目录分散对你来说有多痛？**
   - 无所谓，能找到就行：方案二
   - 非常痛，必须统一管理：方案一

---

| -------------------------------- | ------------------ |

| 做大项目，需要正规归档和交付报告 | 方案一，一步到位   |

## 💡 推荐的演进路径

**不要一开始就做方案一！** 建议的演进顺序：

```
阶段零（现在）：方案零，凑合用
    ↓ 觉得编号重复、记不住产物，确实有痛点了
阶段一（下周）：先做方案二，4-6 小时做完，马上能用
    ↓ 用方案二跑 2-3 个项目，确实觉得目录分散很痛
阶段二（1-2 个月后）：再做方案一的补充功能，演进到统一项目根目录
```

**为什么不一步到位？**

1. 方案二已经能解决 80% 的核心问题（编号重复、跨阶段依赖）
2. 剩下 20% 的问题（目录分散、没有全局报告）是不是真的痛，用了才知道
3. 很多时候你会发现，方案二已经完全够用了，根本不需要做方案一
4. 就算最后要做方案一，方案二开发的功能 90% 都可以复用，不会白做
