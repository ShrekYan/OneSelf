## 第 5 章：核心知识点沉淀

### 知识点 1：ID 生成方案对比（面试高频考点）

| 方案                    | 优点                                                                                         | 缺点                                                                      | 适用场景                   |
| ----------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------- |
| **自增 ID**（author-N） | ✅ 可读性好，短小<br>✅ 数据库索引性能好                                                     | ❌ 有竞态条件，高并发必炸<br>❌ 极易预测，暴露业务数据<br>❌ 分布式不友好 | 单实例、低并发、内部系统   |
| **UUID v4**（本次采用） | ✅ 全局唯一，无需中心化<br>✅ Node.js 内置，零依赖<br>✅ 不可预测，安全性高<br>✅ 分布式友好 | ❌ 较长（36 字符）<br>❌ 可读性差<br>❌ InnoDB 聚簇索引有一定性能影响     | 绝大多数业务场景，推荐默认 |
| **NanoID**              | ✅ 比 UUID 短（21 字符）<br>✅ URL 友好<br>✅ 同样安全随机                                   | ❌ 需要安装依赖<br>❌ 生态不如 UUID 成熟                                  | 前端、URL 暴露的 ID，推荐  |

**💡 面试答题技巧**：被问到"系统用什么 ID 比较好"时，从以上 3 个方案 + 7 个维度展开分析，面试官当场刮目相看！

### 知识点 2：竞态条件（Race Condition）

**什么是竞态条件？**

> 多个并发执行的流程，它们的执行结果依赖于特定的执行顺序，但这个顺序无法保证。

**本次案例中的竞态条件**：

```
时序：
1. 请求 A：查询 lastUser → author-100 → 计算 newId = author-101
2. 请求 B：查询 lastUser → author-100（A 还没插入）→ 计算 newId = author-101
3. 请求 A：插入 author-101 ✅ 成功
4. 请求 B：插入 author-101 ❌ 主键冲突！
```

**为什么会发生？**

- 查询和插入不是原子操作
- 中间有时间窗口，其他请求可以插入
- 并发量越高，概率越大

**解决方法**：

1. ✅ **最佳方案**：改用 UUID（无状态，无需查询）
2. ⚠️ 方案 2：数据库自增主键（但 MySQL 自增不支持前缀）
3. ⚠️ 方案 3：加分布式锁（复杂度高，性能差）

**💡 架构师金句**：

> 能不用状态解决的问题，就不要引入状态。
> 竞态条件这种 Bug，**代码 Review 看不出来，测试环境测不出来，一到线上高并发必炸**。
> 提前预防的成本 = 事后救火成本的 1%。

### 知识点 4：工具类封装的设计原则

**本次 IdGenerator 的设计体现了以下原则**：

| 原则         | 说明                       | 本次案例体现                                      |
| ------------ | -------------------------- | ------------------------------------------------- |
| **单一职责** | 一个类只做一件事           | 只负责生成 ID，不做其他事情                       |
| **开闭原则** | 对扩展开放，对修改关闭     | 新增表只需加新方法，不改现有方法                  |
| **依赖倒置** | 高层不依赖低层，都依赖抽象 | 业务代码依赖 `IdGenerator`，不直接依赖 `crypto`   |
| **易于切换** | 底层实现可灵活替换         | 想换成 NanoID，只需修改 `generateUUID()` 一个方法 |

**💡 代码设计金句**：

> 好的代码设计，就是把"未来一定会变"的地方，封装成只需要改一个地方。

## 第 6 章：踩坑教训与避坑指南

### 🕳️ 踩坑记录 1：自增 ID 的竞态条件 Bug

**踩坑场景**：

- 为了"ID 好看、可读"，用了 author-1、author-2 格式
- 实现方式：查最后一条记录 → 解析数字 → +1 → 插入
- 结果：并发注册时必现主键冲突，报错 500

**踩坑原因**：

- 只考虑了"可读性"，忽略了"并发安全性"
- 抱有侥幸心理："我们并发量小，不会有问题"

**正确做法**：

- 业务 ID 就用 UUID 或 NanoID，不要自增
- 真要自增，用数据库自增主键（不要应用层自增）
- 对外暴露的 ID，绝对不要用可预测的自增序列

---

### 🕳️ 踩坑记录 2：只看眼前问题，忽略整体统一

**踩坑场景**：

- 发现 Users 表 ID 有问题，只改 Users 表
- 下次开发文章发布，又写出 article-1 格式
- 再下次开发分类管理，又写出 category-1 格式
- 结果：3 种格式并存，数据库里一团糟

**踩坑原因**：

- 解决问题只看眼前，没有系统思维
- 没有想过"这是不是一个系统性的问题？"

**正确做法**：

- 发现一个问题时，先全局搜索一下类似的问题
- 如果是系统性问题，统一解决，不要一个个补
- 花 10 分钟做个工具类，一劳永逸

---

### 🕳️ 踩坑记录 3：代码不封装，到处复制粘贴

**踩坑场景**：

- 每个 .create() 地方都写 crypto.randomUUID()
- 有一天想换成 NanoID，要搜整个项目改 10 个地方
- 还很容易改漏，留下两种格式并存

**踩坑原因**：

- 嫌麻烦，不想多写一个工具类
- 觉得"就一行代码，没必要封装"

**正确做法**：

- 只要是可能会变的逻辑，哪怕只有一行，也要封装
- 工具类的成本很低，但收益是永久的
- 封装不是为了现在，是为了未来的那个你

## 第 7 章：架构师思维养成

### 思维 1：从"解决一个问题"到"解决一类问题"

| 普通开发者                            | 架构师                                                          |
| ------------------------------------- | --------------------------------------------------------------- |
| Users 表 ID 有问题？那就只改 Users 表 | 发现 Users 表 ID 有问题 → 所有表是不是都有这个问题？ → 统一解决 |
| 思路：补窟窿，哪里漏了补哪里          | 思路：系统性修复，从根上解决                                    |

**💡 养成方法**：发现问题后，先问自己 3 个问题：

1. 这是不是第一次出现？
2. 其他地方会不会有同样的问题？
3. 未来再出现类似问题怎么办？

---

### 思维 2：预防成本 ≪ 救火成本

| 阶段           | 成本 |
| -------------- | ---- |
| 设计阶段预防   | 1x   |
| 开发阶段修复   | 5x   |
| 测试阶段发现   | 20x  |
| 线上出问题救火 | 100x |

**💡 架构师金句**：

> 竞态条件这种 Bug：
>
> - 设计阶段发现：10 分钟换个方案
> - 开发阶段发现：半天加锁、改逻辑
> - 测试阶段发现：很难复现，可能一周都定位不了
> - 线上炸了：全公司熬夜救火，还要赔用户损失

---

### 思维 3：代码是写给人看的，顺便给机器执行

```typescript
// ❌ 写给机器看的
id: crypto.randomUUID(),

// ✅ 写给人看的
id: IdGenerator.generateArticleId(),
```

- 第一行：机器知道是什么，但人要想一下"这是在生成文章 ID 吗？"
- 第二行：不用想，一眼就懂，而且还隐含了"文章 ID 就是这么生成的"的规范

**💡 养成方法**：写完代码，读一遍，问自己：

> 如果一个新来的实习生看到这段代码，他能立刻看懂这是在做什么吗？
