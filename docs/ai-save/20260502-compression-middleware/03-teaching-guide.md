## 第 5 章：知识点沉淀

### 🎯 核心知识点 1：NestJS 中间件配置的两种方式对比

| 方式                                   | 适用场景                                                  | 优点                                             | 缺点                                                             |
| -------------------------------------- | --------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| **main.ts + app.use()**                | Express 原生中间件（如 compression, cookie-parser, cors） | 代码简洁，一行搞定，执行时机早                   | 不支持 Nest 依赖注入，无法使用 MiddlewareConsumer 的精细路由控制 |
| **app.module.ts + MiddlewareConsumer** | 自定义 NestJS 中间件类                                    | 支持依赖注入，可精细控制路由，符合 Nest 架构风格 | 需要创建类，代码量多，执行时机稍晚                               |

**记忆口诀**：原生中间件走 main.ts，自定义业务中间件走 module.ts

---

### 🎯 核心知识点 2：compression 配置三要素

| 参数          | 推荐值        | 设计思路                                                                                             |
| ------------- | ------------- | ---------------------------------------------------------------------------------------------------- |
| **threshold** | 1024          | 小文件压缩收益低，CPU 开销相对占比高，跳过更划算                                                     |
| **level**     | 6             | level 1-9，6 是官方默认值，压缩率和速度的最佳平衡点。level 9 压缩率只提升 2-5%，但 CPU 消耗增加 30%+ |
| **filter**    | 跳过 image/\* | 图片等二进制格式已经经过压缩，再用 gzip 压缩收益极低，甚至可能变大                                   |

**记忆口诀**：1K 阈值，级别 6，图片跳过

---

### 🎯 核心知识点 3：Express getHeader() 类型安全处理

**问题**：

```typescript
// ❌ TypeScript 报错：类型是 string | number | string[]
res.getHeader('Content-Type')?.includes('image/');
```

**原因**：Express 设计上，Header 可以是多值（Set-Cookie），也可能是数字（Content-Length），所以返回类型是联合类型。

**正确写法**：

```typescript
// ✅ 安全写法
String(res.getHeader('Content-Type') || '').includes('image/');
```

**经验**：只要是调用 Express 的 getHeader，永远不要假设返回类型，必须做类型安全处理。

## 第 6 章：踩坑教训记录

### ⚠️ 踩坑记录 1：想当然的类型假设导致编译失败

**场景**：想当然认为 `getHeader()` 返回的一定是 `string`，直接调用 `.includes()`

**现象**：3 个服务全部编译失败，报错：

```
Property 'includes' does not exist on type 'string | number | string[]'
```

**根因**：没有查看 Express 的类型定义，主观假设返回类型

**正确做法**：

1. 不确定类型时，先查看类型定义或写简单代码测试
2. 处理 Header 时统一使用 `String()` 包装后再操作

**预防措施**：写代码前先想"这个返回值一定是 string 吗？"

---

### ⚠️ 踩坑记录 2：中间件配置顺序的重要性

**场景**：配置 compression 时需要考虑位置

**知识点**：中间件顺序 = 执行顺序

- compression 必须在**发送响应的中间件之前**配置
- 越早配置，越能确保所有响应都被压缩

**正确顺序**：

```
1. compression（最先）
2. cookieParser
3. 其他中间件
4. 路由处理器
```

**经验**：中间件的顺序不是随便写的，每一个位置都有其道理。

## 第 7 章：最佳实践总结

### ✅ Monorepo 多服务配置最佳实践

1. **保持一致性**：所有服务的基础设施配置（压缩、CORS、日志等）必须完全相同
2. **同步验证**：修改后必须同步验证所有服务，不能只测一个就认为没问题
3. **注释清晰**：每个配置项都要加注释说明理由，方便后来人理解为什么这么配
4. **集中管理**：长期来看，这类配置应该抽到 shared 包中统一管理，避免重复代码

---

### ✅ 后端性能优化通用方法论

1. **先测量后优化**：不要凭感觉优化，先拿到数据再动手
2. **权衡成本收益**：每一个优化都要考虑"带来的收益" vs "增加的复杂度/CPU开销"
3. **分层优化**：应用层压缩 vs Nginx 层压缩，各有适用场景，没有绝对的对错
   - 应用层：灵活、不需要依赖基础设施
   - Nginx 层：性能更好、支持缓存压缩结果
