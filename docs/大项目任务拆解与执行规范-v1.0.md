# 大项目任务拆解与执行规范

> **版本**: v1.0 | **适用场景**: 任务数量 ≥ 30 个的中大型项目 | **更新日期**: 2026-05-10

---

## 📌 适用场景判断

| 项目规模 | 任务数量       | 推荐方案             |
| -------- | -------------- | -------------------- |
| 小型项目 | < 15 个任务    | AI 全自动解析执行    |
| 中型项目 | 15 - 30 个任务 | AI 预解析 + 人工复核 |
| 大型项目 | ≥ 30 个任务    | 本文档规范           |

---

## 🎯 核心原则

### 三大黄金法则

1. **拆小原则**：任何超过 25 个任务的包，必须继续拆分
2. **串行原则**：一个阶段 100% 完成并验收，才能开始下一个阶段
3. **复核原则**：AI 解析的结果，人工必须花 3 分钟复核

---

## 📋 六步拆解法（核心流程）

---

### 第一步：顶层架构拆分 ✨ 最重要的一步

#### ❌ 错误拆分方式（按业务功能）

```
📦 电商项目
├── 购物车模块
├── 订单模块
├── 支付模块
└── 个人中心模块
```

#### ✅ 正确拆分方式（按技术边界）

```
📦 电商项目总览（仅概览，不解析）
├── 📂 阶段一：后端 API 层开发（≤ 20 个任务）
├── 📂 阶段二：前端基础组件库（≤ 20 个任务）
├── 📂 阶段三：业务页面开发（≤ 25 个任务）
├── 📂 阶段四：联调 + 测试（≤ 10 个任务）
└── 📂 阶段五：上线部署（≤ 5 个任务）
```

#### 拆分标准

- 每个阶段的任务数量控制在 **15-25 个**
- 阶段总数控制在 **3-5 个**，最多不超过 6 个
- 阶段之间必须有清晰的技术边界

#### 本步 Checklist

- [ ] 已按技术边界拆分，不是按业务功能拆分
- [ ] 每个阶段任务数 ≤ 25 个
- [ ] 阶段总数 ≤ 6 个
- [ ] 阶段之间有清晰的依赖顺序

---

### 第二步：分阶段建立独立文件

#### 目录结构规范

```
docs/
├── {项目名}-总览.md              # 顶层架构图，仅查看不解析
├── 阶段一-{模块名}.tasks.md     # 独立解析文件
├── 阶段二-{模块名}.tasks.md     # 独立解析文件
├── 阶段三-{模块名}.tasks.md     # 独立解析文件
└── ...
```

#### 示例

```
docs/
├── 电商项目-总览.md
├── 阶段一-后端API层.tasks.md
├── 阶段二-基础组件库.tasks.md
├── 阶段三-业务页面开发.tasks.md
├── 阶段四-联调测试.tasks.md
└── 阶段五-部署上线.tasks.md
```

#### 每个 .tasks.md 文件内部规范

遵循 [XMind 任务解析层级规范 v3.0](./XMind任务解析层级规范-v3.0.md)，保持 3-4 层结构：

```
📦 阶段一：后端 API 层开发
└── 📂 用户模块
    ├── ✅ T001 新增用户登录接口
    │   ├── 🔹 路径: /v1/auth/login
    │   ├── 🔹 约束: 只新增不修改
    │   └── 🔹 依赖: 无
    ├── ✅ T002 新增用户注册接口
    └── ✅ T003 新增用户信息查询接口
```

#### 本步 Checklist

- [ ] 每个阶段有独立的 `.tasks.md` 文件
- [ ] 文件名统一格式：`阶段N-{描述}.tasks.md`
- [ ] 每个文件内部遵循 3-4 层规范
- [ ] 有一个总览文件展示全局架构

---

### 第三步：定义阶段间依赖关系

#### 在总览文件中明确阶段依赖

```markdown
## 阶段间依赖关系

阶段一（后端API层）
↓
阶段二（基础组件库） 【依赖：阶段一完成】
↓
阶段三（业务页面开发） 【依赖：阶段二完成】
↓
阶段四（联调测试） 【依赖：阶段三完成】
↓
阶段五（部署上线） 【依赖：阶段四完成】
```

#### 硬规则

- ❌ 前一个阶段没有 100% 完成并验收，绝对不能开始下一个阶段
- ❌ 禁止跨阶段并行开发（90% 的项目失控都是因为这个）

#### 本步 Checklist

- [ ] 总览文件中明确定义了阶段间依赖
- [ ] 所有团队成员都清楚串行执行规则
- [ ] 没有跨阶段并行的计划

---

### 第四步：AI 预解析 + 人工复核

#### 每个阶段单独执行此流程

| 步骤 | 操作                                  | 负责人 | 耗时     |
| ---- | ------------------------------------- | ------ | -------- |
| 1    | 调用 xmind-task-parser 解析本阶段任务 | AI     | 1 分钟   |
| 2    | 检查生成的 `task-manifest.json`       | 人工   | 3 分钟   |
| 3    | 发现问题直接修改 JSON 文件            | 人工   | 1-5 分钟 |
| 4    | 确认无误后标记为"可执行"              | 人工   | 10 秒    |

#### 复核重点检查项

1. ✅ 任务编号是否连续、正确
2. ✅ 依赖关系 `explicit_dependencies` 是否符合预期
3. ✅ 有没有遗漏的任务
4. ✅ 每个任务的约束条件是否正确提取

#### 本步 Checklist

- [ ] 已调用 AI 完成本阶段解析
- [ ] 人工花了 ≥ 3 分钟复核 JSON
- [ ] 编号、依赖、约束都确认无误
- [ ] 已标记为"可执行"状态

---

### 第五步：串行执行 + 阶段验收

#### 执行流程

```
1. 只执行当前阶段的任务
   ↓
2. 本阶段所有任务执行完成
   ↓
3. 人工 Code Review 所有代码
   ↓
4. 运行 lint、type-check、测试
   ↓
5. ✅ 验收通过，代码提交
   ↓
6. 开始下一个阶段的解析 → 复核 → 执行
```

#### 阶段验收标准

- [ ] 本阶段所有任务都标记为 completed
- [ ] 代码通过 lint 检查
- [ ] TypeScript 类型检查无错误
- [ ] 所有新增功能都经过基本测试
- [ ] 代码 Review 完成，没有严重问题
- [ ] 代码已提交到 Git

#### 为什么必须阶段验收？

- ✅ 前面的坑不会带到后面去
- ✅ 每个阶段上下文很小，AI 不会跑偏
- ✅ 做一半发现方向错了，最多只浪费一个阶段的工作量

#### 本步 Checklist

- [ ] 本阶段所有任务都已完成
- [ ] lint、type-check 全部通过
- [ ] 代码 Review 完成
- [ ] 代码已提交到 Git
- [ ] 确认可以开始下一个阶段

## 📊 不同规模项目决策矩阵

| 任务数量       | 推荐方案     | 核心操作                                 |
| -------------- | ------------ | ---------------------------------------- |
| **< 15 个**    | 纯 AI 全自动 | 画 XMind → AI 解析 → 直接执行            |
| **15 - 30 个** | 混合模式     | 画 XMind → AI 解析 → 3分钟复核 → 执行    |
| **30 - 50 个** | 本规范轻量版 | 拆成 2-3 个阶段 → 每个阶段按混合模式执行 |
| **> 50 个**    | 本规范完整版 | 严格执行六步拆解法                       |

## ❌ 避坑指南（常见错误）

### 坑 1：把 50 个任务放一个文件里解析

**后果**：AI 解析时间长、容易漏任务、执行时容易跑偏忘记约束
**解决**：拆成多个阶段文件

### 坑 2：阶段还没验收就开始下一个阶段

**后果**：前面的坑带到后面，最后全乱了，返工成本极高
**解决**：严格执行串行规则，没验收绝不往下走

### 坑 3：相信 AI 100% 准确，不复核

**后果**：依赖关系搞反、约束条件遗漏，执行到一半发现全错了
**解决**：花 3 分钟复核一下 JSON，成本极低，收益极高

### 坑 4：拆分粒度太细，一个任务只做 10 分钟的事

**后果**：任务太多，管理成本上升
**解决**：每个任务的粒度控制在"1-2 天能做完"

## ✅ 项目启动快速检查清单

拿到一个 ≥ 30 个任务的大项目时，按顺序过一遍：

- [ ] 第一步：已按技术边界拆成 3-5 个阶段，每个阶段 ≤25 个任务
- [ ] 第二步：每个阶段建立了独立的 `.tasks.md` 文件
- [ ] 第三步：明确定义了阶段间的依赖关系
- [ ] 第四步：从第一个阶段开始，AI 预解析 + 人工复核
- [ ] 第五步：串行执行，每个阶段完成后做验收
- [ ] 第六步：建立了全局进度跟踪表格

---

## 💡 核心心法总结

1. **大任务必须拆小**，拆到每个小包 ≤25 个任务
2. **串行执行，不要并行**，一个包做完再做下一个
3. **AI 先干活，人来拍板**，AI 解析完花 3 分钟复核，成本最低
4. **阶段验收是底线**，没验收的代码绝对不能流到下一个阶段
