# 【学习归档】XMind-AI 审核模式工作流完整方案

> **文档版本**：v1.0
> **创建时间**：2026-05-09
> **适用场景**：前端/后端 代码开发、需求拆分与执行、组件开发
> **核心设计**：人做决策，AI 做执行；每个任务先审后做，风险可控

---

## 📋 方案概述

### 什么是 XMind-AI 审核模式？

XMind-AI 审核模式是一套人机协作的开发流程，核心思想是：

> **人负责架构决策、任务拆分、方案审核；AI 负责代码生成、质量检查、结果汇总。**

每个任务都遵循：**生成方案 → 人工审核 → 执行代码** 的三步流程，确保代码质量和业务准确性。

---

## 🎯 人机分工边界

### 🧑‍💻 人做什么（决策层）

| 环节               | 说明                           | 为什么人做                      |
| ------------------ | ------------------------------ | ------------------------------- |
| **需求分析**       | 理解业务，定义需求边界         | AI 经常漏业务场景               |
| **XMind 任务拆分** | 按模块/功能/层级拆分任务       | 依赖关系、执行顺序只有人最清楚  |
| **方案审核**       | 确认 AI 生成的执行方案是否正确 | AI 的方案可能不符合项目实际情况 |
| **异常处理**       | 修改方案、跳过任务、终止流程   | 只有人能判断业务价值            |

### 🤖 AI 做什么（执行层）

| 环节             | 说明                             | 为什么 AI 做        |
| ---------------- | -------------------------------- | ------------------- |
| **XMind 解析**   | Markdown → 结构化任务清单 JSON   | 机械劳动，AI 更准确 |
| **依赖拓扑排序** | 计算任务执行顺序                 | 算法问题，AI 擅长   |
| **生成执行方案** | 每个任务的具体实现步骤、文件清单 | 重复模式，AI 很快   |
| **代码生成**     | 按方案生成具体代码               | AI 强项             |
| **质量检查**     | ESLint + TypeScript 检查         | 机械劳动，自动执行  |
| **结果汇总**     | 生成最终交付报告                 | 模板化工作，AI 擅长 |

## 🔄 完整执行流程

```
阶段 1：人做决策
├── 1. 📝 需求分析（人）
│   └── 理解业务，定义需求边界
│
└── 2. 🧠 XMind 任务拆分（人）
    └── 按模块/层级/依赖拆分原子任务

阶段 2：AI 预处理
├── 3. 📤 导出 Markdown（人）
│   └── XMind → 导出为 Markdown 文件
│
└── 4. 🔍 XMind 解析（AI）
    ├── 读取 Markdown 文件
    ├── 生成 task-manifest.json（任务清单）
    └── 生成 execution-plan.md（执行计划）

阶段 3：审核 + 执行（循环每个任务）
├── 5. ✅ 确认整体执行计划（人）
│
└── 对每个任务按依赖顺序执行：
    ├── 6. 📋 生成任务方案（AI）
    │   └── scheme.md（含实现步骤、修改文件、注意事项）
    │
    ├── 7. 👀 人工审核方案（人）
    │   ├── [1] 确认执行
    │   ├── [2] 修改方案
    │   ├── [3] 跳过此任务
    │   └── [4] 终止整个流程
    │
    └── 8. 🚀 执行任务（AI）
        ├── 生成代码文件
        ├── 自动质量检查
        └── 保存执行结果 execution-result.md

阶段 4：交付
└── 9. 📦 生成最终交付报告（AI）
    ├── 任务执行概览
    ├── 修改文件清单
    ├── 功能特性说明
    ├── 验证步骤
    └── Git Commit 建议
```

## 📝 XMind 编写规范

### 极简模式（推荐，你只需要写业务）

```markdown
# 项目名称 - 功能描述

## 模块名称 1

### 任务 1 名称

- 功能点描述 1
- 功能点描述 2
- 特殊要求（如果有）

### 任务 2 名称

- 功能点描述
- 显式依赖：T001（如果跨模块依赖就写，同模块可以不写）

## 模块名称 2

### 任务 3 名称

- ...
```

### 同模块内自动依赖

同一模块下的任务，默认按顺序依赖，不需要手动写：

```markdown
## 组件实现

### T001: 定义类型（自动成为前置任务）

### T002: 实现核心组件（自动依赖 T001）

### T003: 导出注册（自动依赖 T002）
```

✅ **记住：XMind 里只写业务，技术规范全部由 AI 自动注入！**

- 位置：右上角定位

### 导出与注册

- 统一导出 Badge 组件

## ✅ 审核时四选一操作

每个任务审核时，你有四个选择：

| 选项  | 操作        | 说明                             |
| ----- | ----------- | -------------------------------- |
| **1** | ✅ 确认执行 | 方案正确，直接执行               |
| **2** | 📝 修改方案 | 方案不对，输入你的修改要求       |
| **3** | ⏭️ 跳过     | 这个任务不需要做，直接进入下一个 |
| **4** | ❌ 终止     | 整个流程到此为止                 |

> 💡 **最佳实践**：如果发现方案大方向不对，先终止流程（选 4），回去修改 XMind 重新来，比逐个修改任务效率更高。

## 💡 最佳实践

### 1. 任务拆分原则

| 原则         | 说明                                    | 示例                                      |
| ------------ | --------------------------------------- | ----------------------------------------- |
| **原子性**   | 一个任务只做一件事                      | ❌ 「开发整个页面」→ ✅ 拆成 5-8 个小任务 |
| **合适粒度** | 每个任务 AI 执行时间 1-10 分钟          | 太细：「定义一个变量」→ 合并              |
| **依赖清晰** | 同模块按顺序，跨模块写显式依赖          | 「类型定义」→「组件实现」→「导出注册」    |
| **模块分离** | 按业务模块、技术分层划分 XMind 二级节点 | 类型层 / 组件层 / API 层 / 页面层         |

### 2. 描述技巧

- ✅ **用业务语言**：「支持三种颜色主题」
- ❌ **不要写技术细节**：「使用 SCSS 变量定义颜色，用 classNames 切换」
- 💡 **AI 会自动填充技术规范**，你不需要写

### 3. 风险控制

- ✅ **第一个任务执行完检查一下**：确认整体方向正确
- ✅ **复杂任务先审方案再执行**：方案不对立刻改
- ✅ **发现不对就终止**：不要硬着头皮往下走，重新拆 XMind 更快

## 📊 适用场景分析

### ✅ 非常适合用这套流程

1. **新组件开发**：需求明确，步骤清晰
2. **按文档实现功能**：有明确的 PRD / 设计稿
3. **重构任务**：拆分后逐个替换
4. **批量相似任务**：如多个相似组件、多个相似接口

### ⚠️ 不太适合

1. **技术预研类任务**：不确定要做什么，边做边探索
2. **超复杂核心业务**：建议人工写，或者拆成超级细的任务
3. **一次性的小需求**：直接让 AI 做可能更快

---

## ⚖️ 优缺点分析

### 优点 ✨

1. **风险可控**：每个任务先审后做，不会出现「跑了半小时结果全错」的情况
2. **质量有保障**：方案你审核过，代码质量你把关
3. **过程可追溯**：所有方案、结果都持久化保存，随时可以回看
4. **渐进式交付**：做一个成一个，不会全部做完才发现全错
5. **学习曲线平滑**：你可以逐步理解 AI 的实现思路，建立信任

### 缺点 ⚠️

1. **有人工等待成本**：每个任务都需要你点一下确认
2. **速度比全自动慢**：多了审核环节，整体时间长一些
3. **XMind 拆分需要经验**：拆得不好会影响执行效率

## 🎓 学习建议

### 阶段 1：入门（第一个项目）

- 找一个简单的独立组件（如 Badge、Button）
- 完整跑一遍全流程
- 重点体会：XMind 怎么拆、方案怎么审
- 目标：跑通流程，不求快

### 阶段 2：熟练（3-5 个项目）

- 尝试不同类型的任务：组件、页面、工具函数
- 总结 XMind 拆分的最佳粒度
- 优化你的审核标准
- 目标：形成自己的 XMind 拆分模式

### 阶段 3：优化（实际项目）

- 在真实业务项目中使用
- 总结哪些场景适合，哪些不适合
- 考虑是否需要批量模式（简单任务一键全执行）
- 目标：融入日常开发流程

## 🎯 核心价值总结

### 这套方案解决了什么痛点？

| 痛点                          | 解决方式                       |
| ----------------------------- | ------------------------------ |
| ❌ AI 批量执行，经常全错      | 每个任务先审后做，早发现早止损 |
| ❌ 依赖关系混乱，执行顺序错了 | 自动拓扑排序，保证先做前置任务 |
| ❌ 中间结果丢失，无法回滚     | 每个任务都持久化保存，随时回看 |
| ❌ 技术规范不一致             | 全局配置自动注入，统一所有代码 |
| ❌ 人要写很多重复的实现说明   | AI 自动生成方案，人只需要审核  |

### 一句话总结

> **用 XMind 把「做什么」说清楚，让 AI 把「怎么做」说明白，你来点头确认，AI 负责动手实现。**

这是一套「慢就是快」的开发流程——前期多花 5 分钟审核，后期少花 5 小时返工。
