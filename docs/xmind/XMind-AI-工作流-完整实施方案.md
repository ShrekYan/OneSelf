## 2. 核心组件详细设计

### 2.1 XMind Markdown 解析器

#### 输入格式约定（你需要你在 XMind 中遵循）

```
中心主题：项目名称（如：策略详情页开发
├── 模块A（一级节点：业务模块）
│   ├── 任务1（二级节点：可执行任务）
│   │   ├── 业务目标：xxx（三级节点：任务描述）
│   │   ├── 输入约束：xxx（三级节点：前置要求）
│   │   ├── 输出规范：xxx（三级节点：交付要求）
│   │   └── 显式依赖：T001, T002（三级节点：可选）
│   └── 任务2（同一模块内任务隐含依赖：任务2 依赖 任务1（同模块内节点先后顺序隐含依赖）
└── 模块B
    └── 任务3
```

#### 解析规则

| XMind 结构 → 结构化字段映射

| XMind 位置           | 输出字段              | 说明                 |
| -------------------- | --------------------- | -------------------- |
| 中心主题             | project_name          | 项目名称             |
| 一级节点             | module                | 任务所属模块         |
| 二级节点             | business_goal         | 任务的业务目标       |
| 三级节点「业务目标」 | business_goal         | 任务详细描述         |
| 三级节点「输入约束」 | input_constraints     | 前置条件和约束       |
| 三级节点「输出规范」 | output_specification  | 交付要求             |
| 三级节点「显式依赖」 | explicit_dependencies | 任务依赖             |
| \*\*同模块节点顺序   | 自动推断依赖          | 后序任务依赖前序任务 |

### 2.2 任务结构化引擎（升级 xmind-task-parser Agent

#### 核心功能

1. **ID 生成**：T001, T002, T003... 按顺序递增
2. **依赖推断**：
   - 同模块内，第 N 个任务默认依赖第 N-1 个任务
   - 显式标注的依赖优先级最高
3. **Agent 自动匹配**：
   - 包含「组件」「页面」「样式」→ frontend-developer
   - 包含「接口」「Service」「Controller」→ backend-architect
   - 包含「修复」「优化」→ 自动推断对应 Agent
4. **风险评估**：
   - 任务描述长度 + 关键词 → low/medium/high
5. **规范自动注入**：每个任务自动补充项目规范约束
   - 前端任务：自动注入 React + MobX + SCSS Modules 规范
   - 后端任务：自动注入 NestJS + Prisma 规范

#### 输出格式

```json
{
  "project_name": "策略详情页开发",
  "source_xmind": "strategy-detail.md",
  "generated_at": "2026-05-09",
  "tasks": [
    {
      "task_id": "T001",
      "module": "公共组件",
      "business_goal": "实现普通发车弹窗组件",
      "input_constraints": "遵循 React 19 + MobX 规范，使用 SCSS Modules",
      "output_specification": "组件可复用，支持 className 扩展",
      "explicit_dependencies": [],
      "agent_type": "frontend-developer",
      "estimated_size_risk": "low",
      "quality_gates": ["lint", "ts-check"]
    }
  ],
  "execution_plan": {
    "total_tasks": 10,
    "parallel_groups": [
      ["T001", "T003"],
      ["T002", "T004"]
    ],
    "estimated_duration": "25分钟",
    "quality_gates": ["lint", "ts-check"]
  }
}
```

### 2.3 任务编排执行器（新增 task-orchestrator Agent

#### DAG 并行执行算法

```
输入：任务清单（含依赖关系）
输出：并行执行组

算法步骤：
1. 构建邻接表 → 入度为 0 的任务 → 第一轮并行组
2. 移除已完成任务 → 更新剩余任务入度 → 下一轮并行组
3. 重复直到所有任务执行完成
```

#### 并行执行示例

你的 XMind：

```
策略详情页开发
├── 公共组件
│   ├── T001: 弹窗组件
│   └── T002: 进度条组件
├── API 层
│   └── T003: 接口定义
└── 页面层
    └── T004: 页面布局
```

执行编排：

```
第 1 轮并行：T001, T003（无依赖，不同模块）
第 2 轮并行：T002, T004（依赖前序任务）
```

#### 上下文共享机制

```
.claude/runs/
└── <run-id>/
    ├── task-manifest.json      # 任务清单
    ├── T001-result.md          # T001 执行结果
    ├── T002-result.md          # T002 执行结果
    └── execution-report.md          # 最终交付报告
```

每个任务执行前自动读取前置任务的输出作为上下文。

### 2.4 自动质量门禁

#### 检查项（每个任务完成后自动执行

| 检查项          | 执行命令           | 自动修复                     |
| --------------- | ------------------ | ---------------------------- |
| ESLint          | `npm run lint`     | ✅ 支持 `npm run lint --fix` |
| TypeScript 类型 | `npx tsc --noEmit` | ❌ 需要人工                  |
| 导入排序        | 自动检查           | ✅ 自动修复                  |

#### 不通过处理流程

```
任务执行完成
    ↓
质量检查
    ├─ ✅ 通过 → 进入下一任务
    └─ ❌ 不通过
        ├─ 尝试自动修复（lint  ├─ 修复成功 → 继续
        └─ 修复失败 → 暂停并提示人工介入
```

### 5.2 XMind 编写最佳实践

✅ **推荐做法：**

- 一级节点 = 业务模块（如：公共组件、API 层、页面层）
- 二级节点 = 可执行任务（原子性，一个任务只做一件事）
- 任务描述清晰具体，避免模糊
- 同模块内任务按依赖顺序排列

❌ **避免：**

- 任务粒度太大（一个任务做多个不相关功能
- 依赖关系不清晰
- 描述太模糊（如："做页面"）
