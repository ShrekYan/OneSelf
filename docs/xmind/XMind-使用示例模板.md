# XMind 思维导图编写模板与最佳实践

> 本文档定义本项目中 XMind 思维导图的标准编写规范，确保 AI 能准确解析并执行。
>
> ✅ **核心原则：你只需要写业务需求，技术栈规范全部由 Claude 自动遵循**

---

## 🎯 四层约束体系自动保证规范

| 层级      | 约束来源                        | 内容                                      | 是否需要在 XMind 写 |
| --------- | ------------------------------- | ----------------------------------------- | ------------------- |
| 🔴 第一层 | `CLAUDE.md`                     | Monorepo 架构、技术栈固化决策             | ❌ 不需要           |
| 🟠 第二层 | `.claude/FRONTEND-DECISIONS.md` | React 19 + MobX + SCSS Modules + 设计令牌 | ❌ 不需要           |
| 🟡 第三层 | Agent 自身规范                  | 各 Agent 的详细编码规范                   | ❌ 不需要           |
| 🟢 第四层 | 你写的 XMind                    | **只有业务需求**                          | ✅ 只写这个         |

> **重要**：所有技术栈规范、架构约束、代码规范已在项目全局配置中固化，Claude 每次启动自动加载，**绝对不需要在 XMind 中重复描述**。

## 📋 XMind 标准结构

### ✅ 推荐：极简模式（强烈推荐）

你只需要写 3 层，其他全部交给 AI：

```
中心主题：项目名称（一句话）
├── 模块名称 A（一级节点：业务模块分类）
│   ├── 任务 1（二级节点：可执行的原子任务）
│   │   └── 业务需求描述...（三级节点：直接写需求）
│   └── 任务 2（二级节点：同模块内任务，默认依赖任务 1）
└── 模块名称 B（一级节点）
    └── 任务 3（二级节点）
```

## ✅ 完整极简示例

### 推荐写法（你只需要关心业务）

```markdown
# 策略详情页 - 普通发车功能开发

## 公共组件

### 弹窗组件

- 支持 primary / default / danger 三种类型
- 包含标题、内容、确认/取消按钮
- 点击按钮触发回调事件

### 进度条组件

- 支持 0-100% 进度展示
- 支持自定义颜色和高度
- 带动画效果

## API 层

### 发车详情接口

- GET /v1/normal/departDetail
- 包含发车基本信息、跟投状态

### 跟投接口

- POST /v1/normal/follow
- 提交跟投金额和支付方式

## 页面层

### 策略详情页布局

- 顶部：策略信息展示区
- 中间：发车进度和跟投按钮
- 底部：历史记录列表

### 普通发车业务逻辑

- 未开始：展示倒计时
- 进行中：展示进度条 + 跟投按钮
- 已结束：展示最终结果
```

### ⚠️ 避免写法（冗余，完全不需要）

```diff
- ❌ 不要写：使用 React 19 + TypeScript
- ❌ 不要写：遵循 SCSS Modules 规范
- ❌ 不要写：使用 MobX 状态管理
- ❌ 不要写：导入使用 @/ 别名
```

> 这些 Claude 都知道，而且会自动严格遵循！

## 🔧 高级选项（只有需要时才写）

以下内容只有在有特殊要求时才需要写：

| 选项         | 示例                              | 必要性            |
| ------------ | --------------------------------- | ----------------- |
| 显式依赖     | `- 显式依赖：T001, T003`          | ⚠️ 跨模块时需要   |
| 指定文件位置 | `- 输出到：src/components/Button` | ⚠️ 特殊位置时需要 |
| 特殊业务约束 | `- 只有 VIP 用户可见`             | ✅ 业务需要时写   |

> **记住**：技术类约束永远不需要写，只有业务类的特殊要求需要写。

## 📐 编写规范

### 1. 中心主题

```markdown
# 项目名称 - 核心功能描述
```

✅ 好的示例：

- `策略详情页 - 普通发车功能开发`
- `用户中心 - 登录注册流程重构`

❌ 不好的示例：

- `新功能`（太模糊）
- `页面开发`（信息不足）

---

### 2. 一级节点（模块划分）

**原则：按业务领域或技术分层划分**

推荐的模块命名：

- `公共组件` - 可复用的 UI 组件
- `API 层` - 接口定义和封装
- `页面层` - 页面级开发
- `状态管理` - MobX Store 相关
- `工具函数` - 通用工具方法
- `后端 API` - 后端接口开发

✅ 好的示例：

```
## 公共组件模块
## API 层模块
## 页面层模块
```

---

### 3. 二级节点（原子任务）

**原则：一个任务只做一件事，原子性**

✅ 好的示例（原子性）：

```markdown
### 实现普通发车弹窗组件

### 定义普通发车详情接口类型

### 实现进度条组件样式
```

❌ 不好的示例（任务过大）：

```markdown
### 实现整个页面（包含多个功能）

### 开发所有组件（范围太广）
```

---

### 4. 三级节点（任务属性）

| 属性名   | 是否必填 | 说明                         |
| -------- | -------- | ---------------------------- |
| 业务目标 | ✅ 推荐  | 任务要实现的目标，越详细越好 |
| 输入约束 | ✅ 推荐  | 前置条件、技术约束、特殊要求 |
| 输出规范 | ✅ 推荐  | 交付产物的具体要求           |
| 显式依赖 | ⚠️ 可选  | 跨模块依赖时必须标注         |

---

## 🔗 依赖关系规则

### 规则 1：同模块内自动推断依赖

```
## 公共组件模块
### 任务 A（第一个任务，无依赖）
### 任务 B（第二个任务，自动依赖任务 A）
### 任务 C（第三个任务，自动依赖任务 B）
```

**同模块内任务按顺序自动建立依赖关系：任务 C → 任务 B → 任务 A**

### 规则 2：跨模块依赖必须显式标注

```
## 页面层模块
### 任务 D
- 显式依赖：T001, T003
```

### 规则 3：显式依赖优先级最高

如果标注了显式依赖，覆盖自动推断的依赖关系。

## 🎯 最佳实践

### ✅ 推荐做法

1. **任务粒度适中**
   - 每个任务预计 AI 执行时间：5-15 分钟
   - 太大拆细，太小合并

2. **描述具体明确**
   - 好："实现普通发车弹窗，包含标题、内容、确认/取消按钮"
   - 不好："做个弹窗"

3. **按依赖顺序排列**
   - 先做的任务放前面
   - 后做的任务放后面

4. **模块划分清晰**
   - 不同模块的任务不要混在一起
   - 无依赖的模块可以并行执行

### ❌ 避免做法

1. ❌ 不要一个任务包含多个不相关功能
2. ❌ 不要描述太模糊（如："优化一下"）
3. ❌ 不要任务粒度太大（一个任务超过 30 分钟工作量）
4. ❌ 不要任务粒度过小（琐碎任务太多）

## 🔍 导出注意事项

1. **从 XMind 导出时，选择 Markdown 格式**
2. **导出后检查文件编码**（必须是 UTF-8）
3. **文件名建议**：`xxx-需求-xmind.md`
4. **存放位置**：`docs/` 目录下

---

## 💡 小技巧

1. **先搭框架，再填细节**
   - 先创建所有一级模块
   - 再创建二级任务
   - 最后补充三级节点的详细描述

2. **利用 XMind 的拖拽调整顺序**
   - 拖拽调整任务顺序 = 调整依赖关系

3. **复杂依赖用备注标注**
   - 特殊依赖关系可以在 XMind 备注中说明
   - AI 会自动解析备注内容
