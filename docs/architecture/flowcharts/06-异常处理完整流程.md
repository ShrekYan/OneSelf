# 06 - 异常处理完整流程

---

## 📊 架构图

```mermaid
flowchart TB
    ERR[异常抛出] --> CATCH[AllExceptionsFilter 捕获]
    CATCH --> TYPE{异常类型?}

    TYPE -->|BusinessException| BIZ[业务异常处理]
    BIZ --> LOOKUP[查 ErrorCode → HTTP 状态码映射]
    LOOKUP --> FORMATBIZ[格式化为标准响应格式]

    TYPE -->|PrismaClientKnownRequestError| PRISMA[数据库异常处理]
    PRISMA --> MAPPING[P2002 唯一约束冲突<br/>P2025 记录不存在<br/>...]
    MAPPING --> FORMATDB[脱敏后返回友好提示]

    TYPE -->|其他| UNKNOWN[未知异常处理]
    UNKNOWN --> LOG[记录完整堆栈到日志]
    LOG --> HIDE[隐藏敏感信息，返回通用错误]

    FORMATBIZ --> RESP[返回统一响应]
    FORMATDB --> RESP
    HIDE --> RESP

    RESP --> STRUCTURE[{
        success: false,
        errorCode: string,
        errorMessage: string,
        timestamp: number,
        requestId: string
    }]

    note over PRISMA,MAPPING "安全关键：
不直接返回 Prisma 错误信息
避免泄露表名、字段名等数据库结构
返回用户能理解的业务语言"
```

## 🧠 复刻时的思考

### 1. 为什么要自定义 BusinessException？直接 throw Error 不行吗？

```
❌ 直接 throw Error 的问题：
- 没有错误码，前端没法做分支处理
- 没有 HTTP 状态码，返回的都是 500
- 没有业务语义，日志里不好排查
- 没法区分"用户输错了"和"系统真的挂了"

✅ BusinessException 的价值：

throw new BusinessException(
  ErrorCode.USER_NOT_FOUND,      // 错误码（前端判断分支）
  '用户不存在',                   // 给用户看的友好信息
  HttpStatus.NOT_FOUND           // HTTP 状态码
)

💡 类比前端：
new Error('登录失败')
  vs
new BusinessError(CODE.AUTH_FAILED, '密码错误', 401)

有错误码，前端可以做针对性处理：
- 401 → 清 Token 跳登录
- 403 → 提示无权限
- 429 → 提示稍后再试
```

### 2. 为什么 Prisma 异常要单独处理？而不是统一走 BusinessException？

```
✅ Prisma 异常的特点：
1. 是底层 ORM 抛出来的，不是业务代码主动抛的
2. 包含大量数据库敏感信息（表名、字段名、SQL 片段）
3. 错误信息是技术语言（P2002: Unique constraint failed）
4. 用户看不懂，还可能泄露安全信息

✅ 处理原则：
捕获 Prisma 异常 → 翻译成业务语言 → 脱敏后返回

例：
Prisma 报错：P2002: Unique constraint failed on the fields: (`username`)
↓
翻译成：该用户名已被注册，请使用其他用户名
↓
返回给前端（用户能理解，不暴露任何数据库信息）

💡 类比前端：
后端返回的 500 错误
前端不能直接把 response 弹给用户看
要翻译成：服务器开小差了，请稍后重试
```

### 3. 异常过滤器的链式处理顺序为什么是这样？

```
异常抛出
  ↓
BusinessExceptionFilter（优先）
  ↓ 不匹配
PrismaExceptionFilter（其次）
  ↓ 不匹配
AllExceptionsFilter（兜底）

✅ 为什么按这个顺序？
- 业务异常是我们主动抛的，信息最完整，优先级最高
- Prisma 异常是已知的第三方异常，可以做固定映射
- 其他所有异常走兜底，记录日志，返回通用错误

💡 类比前端：
try {
  await login()
} catch (e) {
  if (e.code === 'AUTH_FAILED') { ... }  // 已知业务错误
  else if (e.code === 'NETWORK_ERROR') { ... } // 已知网络错误
  else { ... }  // 兜底
}
```

### 4. 为什么未知异常一定要记录完整堆栈？但不返回给前端？

```
✅ 记录完整堆栈（给开发者）：
- 方便定位问题在哪一行
- 方便复现和调试
- 日志里完整保留

❌ 不返回给前端（给用户）：
- 用户看不懂堆栈信息
- 可能泄露源码路径、数据库信息
- 可能泄露 API Key、Token 等敏感信息

💡 经典错误：
res.status(500).json({ error: e })
→ 把整个 Error 对象返回给前端
→ 整个堆栈都泄露了
→ 攻击者可以拿到源码结构，发动更精准的攻击

✅ 正确做法：
开发环境：可以返回堆栈（方便调试）
生产环境：只返回"服务器开小差了"
```

### 5. requestId 有什么用？为什么每个错误响应都要带？

```
✅ requestId 的价值：

1. 问题定位
前端："我遇到了一个错误"
后端："把 requestId 给我"
→ 直接在日志里搜这个 ID
→ 不用问时间、不用问用户 ID、不用问操作路径
→ 一秒定位所有关联日志

2. 跨服务追踪
请求经过 N 个服务
每个服务的日志都带同一个 requestId
→ 可以串联起整个调用链

3. 用户体验
前端显示：操作失败（错误码：ABCD1234）
→ 用户可以把这个码报给客服
→ 客服不需要懂技术，搜这个码就能定位
```
