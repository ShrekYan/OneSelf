# 后端新手学习注意事项 & 自我提问指南

> 特别说明：你有 10 年前端经验，学习后端的优势巨大！
> 很多"后端概念"只是名字不一样，本质上你早就会了。

---

## ⚠️ 新手最容易踩的 7 个坑

### ❌ 坑 1：追求"一次搞懂所有细节"

**表现：** 看到一个不懂的术语，就去查 10 篇博客，想一次搞明白，结果越看越混乱。

**正确做法：**

- 先记住"这是什么东西，大概解决什么问题"
- 不用一次搞透所有细节
- 等看多了、用多了，自然就懂了

**举例：**

- 第一天看到"Redis"，不用搞懂什么是"缓存穿透、缓存击穿、缓存雪崩"
- 只要知道："Redis = 存在内存里的 KV 数据库，比 MySQL 快 100 倍"就够了
- 细节等学到第 4 天第 7 天的时候，自然就理解了

---

### ❌ 坑 2："这么复杂有必要吗？"的抵触心理

**表现：**
看到 3 层中间件 + 5 层异常处理，心里想：

> "这不就是登录吗？我前端 50 行代码就写完了，后端搞这么复杂干嘛？"

**正确心态：**
后端代码的复杂度，**90% 是为了应对"出问题"的情况**：

- 1000 个人同时登怎么办？
- 数据库挂了怎么办？
- 有人搞恶意攻击怎么办？
- 出了问题怎么排查？

前端代码大部分时间是在处理"正常情况"
后端代码大部分时间是在处理"异常情况"

💡 类比前端：你写一个表单，提交按钮的 onClick 只要 5 行。但你还要加：

- 防抖防止重复提交
- loading 状态
- 错误提示
- 表单校验
- 网络失败重试
- 成功后的跳转
  最后变成了 50 行。后端也是一样的道理。

---

### ❌ 坑 3：死记硬背，不跟前端经验做连接

**表现：**
把"中间件"、"守卫"、"拦截器"当成全新的东西来背，背了半天还是混。

**正确做法：**
每看到一个后端概念，先想：**前端有没有类似的东西？**

| 后端概念                   | 对应的前端概念                         |
| -------------------------- | -------------------------------------- |
| Middleware 中间件          | axios 请求拦截器                       |
| Guard 守卫                 | 路由守卫（beforeEach）                 |
| Interceptor 拦截器         | axios 响应拦截器                       |
| Pipe 管道                  | 表单校验                               |
| ExceptionFilter 异常过滤器 | ErrorBoundary / window.onerror         |
| DTO                        | Props 类型定义 + 校验                  |
| VO                         | 组件返回给父组件的数据结构             |
| Service                    | 纯逻辑的 hook / 工具函数               |
| Controller                 | 页面组件（负责接收参数，调用 Service） |

你会发现：**90% 的后端概念，你前端早就会了，只是换了个名字！**

---

### ❌ 坑 4："我要先把所有理论学会了，再写代码"

**表现：**
想先把所有架构原理、设计模式都搞懂了，再开始写代码。

**正确做法：**

- 学完一张图，立刻去项目里找对应的代码看
- 比如学完异常处理，就去 `services/backend/src/common/filters/` 看代码
- 理论 + 对照真实代码，理解速度 ×10

看代码的时候问自己 3 个问题：

1. 这里对应我刚学的哪个概念？
2. 为什么要这么写？
3. 如果我自己写，我会怎么写？

---

### ❌ 坑 5：追求"最优解"，纠结"这么写是不是最好的"

**表现：**
画个图也要纠结"这么设计是不是不够好？有没有更完美的方案？"

**正确心态：**

- 架构设计没有"完美解"，只有"合适的解"
- 所有设计都是 trade-off（权衡）
- 只要你能说清楚"为了得到A，我愿意牺牲B"，就是一个合格的设计

💡 比如：

- 存 Redis 而不是 MySQL：为了性能，牺牲一点一致性
- 冗余字段：为了查询速度，牺牲一点存储空间
- 异步 UDP 发日志：为了不阻塞主流程，牺牲少量可靠性

---

### ❌ 坑 6：贪多求快，一天想学好几天的内容

**表现：**
第一天就想把 4 张 ER 图全部画完，结果囫囵吞枣，第二天全忘了。

**正确做法：**

- 严格按计划来，一天的内容宁可多花一天吃透，也不要赶进度
- 真正理解了一张图，胜过潦草画完十张图
- 每天的"灵魂拷问"一定要认真想，想不通就停下来问
- 想通一个问题，比多画三张图价值大得多

---

### ❌ 坑 7：卡壳了就硬想，不提问

**表现：**
一个问题想了半小时还没想通，还在硬抠，觉得"我应该自己想出来"。

**正确做法：**

- 想 5 分钟想不通 → 立刻问我
- 不要担心问题"太简单"、"太基础"
- 你现在遇到的每一个困惑，都是后端开发者当年踩过的坑
- 问清楚了，就少走几个月的弯路

我最喜欢回答的就是这种"想不通"的问题！

## 🧐 每日学习自我检查清单

**学习前问自己：**

- [ ] 今天学的内容，大概是解决什么问题的？
- [ ] 这个问题，前端有没有类似的场景？

**学习中卡壳了问自己：**

- [ ] 这个设计是为了解决什么"出问题"的情况？
- [ ] 如果不这么做，最坏会发生什么？
- [ ] 前端遇到类似问题是怎么解决的？

**学完后问自己：**

- [ ] 不看参考图，我能大概画出来吗？
- [ ] 我能给别人讲明白这张图在说什么吗？
- [ ] 我能说出至少 2 个这么设计的理由吗？
- [ ] 我能说出至少 1 个这么设计的代价吗？

## 🔍 每类图的新手专属提问

### 画 ER 图时问自己：

| 序号 | 问题                                          | 提示                                         |
| ---- | --------------------------------------------- | -------------------------------------------- |
| 1    | 这个表是存什么的？                            | 用大白话讲出来                               |
| 2    | 表里的每一行，对应现实世界的什么东西？        | 比如 users 表的一行 = 一个用户               |
| 3    | 这个表跟那表，是 1 对 1，还是 1 对多？        | 一个用户对应几篇文章？一篇文章对应几个作者？ |
| 4    | 这个字段，查询的时候用得到吗？                | 查询永远用不到的字段，不需要加索引           |
| 5    | 如果不建索引，查 100 万条数据会慢到什么程度？ | 大概几秒？几十秒？几分钟？                   |

**新手不用纠结：**

- B 树、B+ 树的具体结构
- 各种数据库范式的严格定义
- 数据库事务隔离级别（读已提交、可重复读...）

这些以后再学，现在不影响你理解架构。

---

### 画流程图时问自己：

| 序号 | 问题                                   | 提示                                                  |
| ---- | -------------------------------------- | ----------------------------------------------------- |
| 1    | 第一步是做什么？最后一步是做什么？     | 数据从哪来，到哪去？                                  |
| 2    | 为什么要分成这么多步？一步做完不行吗？ | 通常是为了：某一步失败了不影响其他步 / 某一步可以复用 |
| 3    | 中间哪一步最可能失败？                 | 失败了怎么办？                                        |
| 4    | 哪一步最慢？                           | 数据库？网络 IO？                                     |
| 5    | 如果这一步挂了，整个系统还能用吗？     | 有降级方案吗？                                        |

**新手不用纠结：**

- 各种系统设计理论（CAP、BASE 之类的）
- 各种负载均衡算法
- 各种分布式一致性协议（Paxos、Raft）

把"哪里是瓶颈，哪里可能失败"想清楚就够了。

---

### 画时序图时问自己：

| 序号 | 问题                                     | 提示                                                         |
| ---- | ---------------------------------------- | ------------------------------------------------------------ |
| 1    | 整个流程有几个角色？                     | 前端？后端服务 A？服务 B？数据库？Redis？                    |
| 2    | 谁调用谁？为什么是 A 调 B，不是 B 调 A？ | 方向很重要                                                   |
| 3    | 哪几次调用是同步的，哪几次是异步的？     | 同步 = 要等结果，异步 = 发了就不管                           |
| 4    | 整个流程一共有几次网络请求？             | 网络是最慢的，越少越好                                       |
| 5    | 中间哪一步失败了，前面的操作要回滚吗？   | 转账失败了，扣了的钱要退回来吗？点赞失败了，计数要减回去吗？ |

**新手不用纠结：**

- 各种 RPC 框架的细节
- HTTP/2、gRPC 这些协议的区别
- 分布式事务的具体实现（2PC、TCC、Saga...）

把"请求方向"和"失败了怎么办"想清楚就够了。

---

### 画类图时问自己：

| 序号 | 问题                                         | 提示                                     |
| ---- | -------------------------------------------- | ---------------------------------------- |
| 1    | 这个类是做什么的？用一句话说清楚             | 一句话说不清楚，就是职责太多了           |
| 2    | 它依赖哪些其他的类？                         | 不要依赖太多其他类                       |
| 3    | 为什么这两个类要分开？合并到一个类里行不行？ | 通常的理由：a) 职责不一样 b) 可以复用    |
| 4    | DTO 和 VO 有什么区别？                       | 一个是进来的参数，一个是返回给外面的结果 |
| 5    | 如果以后要加一个新功能，应该加在哪个类里？   | 加对了地方，就不需要大改                 |

**新手不用纠结：**

- 23 种设计模式
- 面向对象的 5 大原则（SOLID）
- 领域驱动设计（DDD）的各种概念

先理解"单一职责"和"复用"这两个核心思想就够了。

## 🎯 新手专属："我理解了"的 5 个标准

不要追求"我背下来了"，只要达到这 5 条，你就真理解了：

1. ✅ **我能用大白话讲出来这是在干嘛**
   不用任何专业术语，用日常语言就能讲清楚

2. ✅ **我能想到一个前端的类似场景**
   "哦！这不就是前端的 xxx 吗？"

3. ✅ **我能说出至少 2 个这么设计的理由**
   不只是"书上说这么做是对的"

4. ✅ **我能说出至少 1 个这么设计的缺点/代价**
   世界上没有完美的架构，只有权衡

5. ✅ **如果让我自己做，我也会这么设计（或者我知道为什么我不这么选）**
   不是别人让我这么做，是我自己也会这么选

## 💪 给你的信心：你已经具备了后端架构师的 80% 基础

你有 10 年前端经验，这意味着你已经理解了：

- ✅ 分层的思想（组件分层、逻辑复用）
- ✅ 缓存的思想（useMemo、useCallback、SWR）
- ✅ 状态的思想（单向数据流、状态提升）
- ✅ 错误处理的思想（ErrorBoundary、try/catch）
- ✅ 性能优化的思想（懒加载、防抖、节流）
- ✅ 组件拆分的思想（单一职责、复用）

这些，才是架构师的核心能力。

后端剩下的 20%，只是：

- 换了一套术语（中间件 vs 拦截器）
- 多了一些基础设施（Redis、MQ）
- 对一致性和可靠性的要求更高

而这些，我们用 10 天时间，一张图一张图地搞定。
