## 🧠 复刻时的思考

### 1. RefreshTokens 表为什么要有 client_ip 字段？

```
✅ 安全风控需要：

1. 异常登录检测
   → 同一个账号，IP 突然从北京变到美国
   → 时间差只有 1 小时，不可能飞过去
   → 触发告警，强制重新登录

2. 审计追踪
   → 账号被盗了，可以查登录 IP 溯源
   → 可以看到什么时间，从什么 IP 登录过
   → 配合其他日志，可以做完整的攻击链路分析

3. 地理围栏
   → 企业版功能，只允许公司 IP 范围内登录
   → 其他 IP 登录需要额外验证

✅ 记录但不依赖：
IP 可以伪造，可以用代理
可以作为风控参考，但不能作为唯一依据
配合 User Agent、设备指纹等其他信息一起用
```

### 2. RefreshTokens 为什么要有 revoked 字段？直接删除不行吗？

```
✅ 软撤销的好处：

1. 审计需求
   → 用户登出了，但是需要保留登录记录
   → 以后可以查这个用户什么时候登录过，什么时候登出
   → 合规要求，日志需要保留 6 个月

2. 防止复用
   → Token 已经泄露了，攻击者拿着旧 Token 来用
   → revoked = true 可以拒绝
   → 如果删了就无法判断这个 Token 曾经存在过

3. 支持"重新激活"
   → 用户登出了，10 分钟内又回来了
   → 可以选择恢复这个 Token，不用重新登录

✅ 权衡：
多占一点存储空间
但数据是宝贵的
存储现在很便宜，不要舍不得

💡 可以设置 TTL：
超过 30 天的 revoked Token 可以物理删除
既保留了短期审计能力，又不会无限增长
```

### 3. 为什么 password_algorithm 是一个单独的字段？存到哈希字符串里不行吗？

```
✅ 单独字段的好处：

1. 支持多种算法并存
   → 老用户 bcrypt，新用户 argon2
   → 以后出了更安全的算法，可以继续加
   → 不需要跑批量脚本一次性更新所有用户

2. 便于统计和监控
   → 现在有多少用户升级到 argon2 了？
   → 升级速度怎么样？
   → 一条 SQL 就能查出来

3. 回滚方便
   → 发现 argon2 有问题？
   → 新用户继续用 bcrypt
   → 已升级的用户不受影响

✅ 两种方式都可以：
bcrypt 通常把算法存在哈希字符串里：
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
↑ 算法标识

但是单独字段更灵活
更适合多算法平滑迁移的场景
```

### 4. 为什么 RefreshToken 表的索引是 expires_at 而不是 created_at？

```
✅ 查询模式决定索引：

最常见的查询：
1. 通过 refresh_token 查完整记录（唯一索引，O(1)）
2. 通过 user_id 查这个用户的所有 Token
3. 清理过期的 Token → WHERE expires_at < NOW()

created_at 的查询场景很少：
"查今天创建的所有 Token"
这种需求几乎没有

✅ 索引设计原则：
索引是给查询用的
不是为了有而有
有什么查询，加什么索引
不要在没人查的字段上浪费索引空间
```

### 5. 为什么 Users 表的 username 是唯一索引而不是主键？

```
✅ 主键 vs 唯一索引：

主键：
- 不可以修改
- 所有外键引用它
- 永不改变

username：
- 用户可能想改用户名
- 业务需求是可以变的
- 所以不能当主键

✅ 正确的设计：
id = UUID 主键，永远不变
username = 唯一索引，可以变

以后要加手机号登录、邮箱登录
也是一样的思路：
phone = 唯一索引
email = 唯一索引
都不能当主键

💡 数据库设计铁律：
任何有业务意义的字段都不适合当主键
因为业务需求永远在变
今天不变不代表明天不变
别给自己挖坑
```
