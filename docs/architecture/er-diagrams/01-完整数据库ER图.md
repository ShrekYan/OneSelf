## 🧠 复刻时的思考

### 1. 为什么主键用 UUID 而不是 INT AUTO_INCREMENT？

```
✅ UUID 的好处：

1. 分布式安全
   → 微服务架构下，不需要集中的 ID 生成器
   → 每个服务自己生成 ID，不会冲突
   → 方便数据合并、迁移

2. 不暴露业务数据量
   → 攻击者看不到 /article/1 到 /article/10000
   → 不知道你到底有多少篇文章
   → 防爬虫，防商业情报

3. 可以在应用层生成
   → 不需要等数据库返回自增 ID
   → 插入前就知道 ID 是什么
   → 方便做批量操作

❌ UUID 的缺点：
- 占空间更大（36 字符 vs 4 字节 INT）
- 索引性能略差（无序插入）

✅ 本项目的权衡：
安全性和分布式优势 > 一点点性能损失
用户量不大的情况下，差异可以忽略

💡 更好的方案：UUID v7
有序 UUID，兼顾有序性和唯一性
数据库索引性能和 INT 差不多
MySQL 8.0 原生支持
```

### 2. 为什么时间戳用 BigInt 毫秒而不是 DATETIME/字符串？全方位对比

```
📊 三种时间存储方案基础信息：

┌──────────────────┬──────────────┬────────────────────────┬──────────┐
│ 方案             │ MySQL 类型   │ 例子                   │ 占用空间 │
├──────────────────┼──────────────┼────────────────────────┼──────────┤
│ A. BigInt 毫秒   │ BIGINT       │ 1714977600000          │ 8 字节   │
│ B. DATETIME(3)   │ DATETIME(3)  │ '2024-05-06 14:40:00'  │ 8 字节   │
│ C. 字符串存储    │ VARCHAR(19)  │ '2024-05-06 14:40:00'  │ 19 字节  │
└──────────────────┴──────────────┴────────────────────────┴──────────┘

🔍 10 个维度全方位对比：

┌──────────────┬──────────────┬──────────────┬──────────────┐
│ 维度         │ BigInt 毫秒  │ DATETIME     │ 字符串       │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 存储空间     │ 8 字节       │ 5-8 字节     │ 19 字节 ❌   │
│ 计算性能     │ ✅ 极快      │ ⚠️ 中        │ ❌ 极慢      │
│ 时区问题     │ ✅ 全球统一  │ ⚠️ 受配置影响│ ⚠️ 无时区    │
│ 排序性能     │ ✅ 最快      │ ✅ 也快      │ ❌ 慢        │
│ 范围查询     │ ✅ 极快      │ ✅ 也快      │ ⚠️ 支持但慢  │
│ 可读性       │ ❌ 看不懂    │ ✅ 直接看懂  │ ✅ 直接看懂  │
│ 前端处理     │ ✅ 一行搞定  │ ⚠️ 要解析    │ ⚠️ 要解析    │
│ 加减运算     │ ✅ 小学数学  │ ⚠️ 查函数    │ ❌ 无法计算  │
│ 精度扩展     │ ✅ 毫秒/微秒  │ ⚠️ 要改类型  │ ❌ 加长度    │
│ 跨库兼容     │ ✅ 全库统一  │ ⚠️ 各库不同  │ ⚠️ 格式不统  │
└──────────────┴──────────────┴──────────────┴──────────────┘

🎯 核心痛点深入分析：

1. 时区问题（最坑！没有之一！）

❌ DATETIME 的坑：
你存了 '2024-05-06 14:40:00' 以为是北京时间
然后 DBA 把数据库时区改成了 UTC
读出来变成了 2024-05-06 06:40:00
差了 8 个小时！

真实踩坑案例：
某公司把数据库从上海迁移到 AWS 美西
所有时间全乱了，差了 15 个小时
几百张表，几千万条数据
花了一周才修复完

✅ BigInt 的优势：
1714977600000 这个数字
→ 在地球上任何一个地方，都代表同一个时刻
→ 不管你数据库时区怎么改
→ 不管你服务器部署在北京还是纽约
→ 这个数字永远不会变

前端展示时转成本地时间就行：
new Date(1714977600000).toLocaleString('zh-CN')

2. 计算性能差 100 倍

BigInt：两个整型直接比，CPU 单指令完成
SELECT * FROM articles
WHERE created_at > 1714977600000

DATETIME：要解析日期格式，做转换
SELECT * FROM articles
WHERE created_at > '2024-05-06'

字符串：字典序比较，各种格式坑
'2024-5-6' 和 '2024-05-06' 比较结果完全不对！

100 万条数据范围查询性能：
→ BigInt：~10ms
→ DATETIME：~50ms
→ 字符串：~500ms
差 50 倍！

3. 加减运算方便程度

BigInt：小学数学就会
const oneHourLater = timestamp + 3600 * 1000;
const oneDayAgo = timestamp - 86400 * 1000;

DATETIME：还要查函数，而且每个库不一样
MySQL: DATE_ADD(created_at, INTERVAL 1 HOUR)
PostgreSQL: created_at + interval '1 hour'
Oracle: ADD_MONTHS(created_at, 1)

4. 前端处理对比

BigInt 方案：一行搞定
const timeStr = new Date(article.created_at).toLocaleString();

DATETIME/字符串方案：
const timeStr = new Date(
  article.created_at.replace(' ', 'T')
).toLocaleString();

小心！
'2024-05-06 14:40:00' 在 Safari 里解析失败
要改成 '2024-05-06T14:40:00' 才行
各种浏览器兼容性坑

⚖️ BigInt 的唯一缺点及解决方案：

唯一缺点：SQL 里直接查看看不懂
SELECT created_at FROM articles;
→ 1714977600000，这是什么鬼？

解决方案 1：SQL 里转换一下
SELECT FROM_UNIXTIME(created_at / 1000) as created_at
FROM articles;
→ 2024-05-06 14:40:00

解决方案 2：用数据库可视化工具
Navicat、DataGrip 都支持自定义显示格式
配置一下，自动把 BigInt 转成时间显示
你看到的还是友好的时间格式

🎯 针对本项目的结论：

强烈推荐 BigInt 存毫秒时间戳

┌──────────────────┬──────────────────────────────────┐
│ 理由             │ 说明                              │
├──────────────────┼──────────────────────────────────┤
│ 时区安全         │ 跨时区部署、迁移零风险             │
│ 计算最快         │ 整型运算比日期函数快几十倍         │
│ 前端友好         │ new Date(ts) 直接用，零兼容问题    │
│ 代码统一         │ 所有语言都是时间戳，不用转          │
│ 精度够           │ 毫秒级精度，99% 场景够用           │
└──────────────────┴──────────────────────────────────┘

📌 什么时候能用 DATETIME？

只有满足以下所有条件才考虑：
✅ 永远不会跨时区部署
✅ 永远不会迁移数据库
✅ DBA 不会随便改时区
✅ 时间查询不多，主要用于展示
✅ 团队所有人都知道时区坑

但，你真的能保证吗？

💡 设计哲学：
时区坑是数据库第一大坑，没有之一！

你今天觉得「我们公司永远不会出海」
三年后业务发展了，要去东南亚了
那时候改时间字段，成本是现在的 1000 倍

早踩坑不如晚踩坑？不，直接用 BigInt，永远不踩坑
```

### 3. 为什么 Articles 表要有 author_name 和 author_avatar 冗余字段？JOIN 不行吗？

```
🎯 先看场景：
H5 博客首页，每篇文章卡片都要显示：
→ 作者头像
→ 作者昵称
一屏 3-5 篇，下拉无限加载

❌ JOIN 的性能问题：

三种方案对比（查 10 篇文章）：
┌────────────┬────────────────────┬────────────┐
│ 方案       │ 查询次数           │ 耗时       │
├────────────┼────────────────────┼────────────┤
│ 1+N 查询   │ 1 篇文章 + 10 次用户 │ ~200ms+    │
│ JOIN 查询   │ 1 次两表关联        │ ~50ms      │
│ 冗余字段   │ 1 次单表查询        │ ~2ms       │
└────────────┴────────────────────┴────────────┘
→ 性能差距 25 倍！

✅ 冗余字段的核心好处：

1. 首页秒开
   → 移动端网络差的地方，0.5s vs 0.02s
   → 用户体验天壤之别
   → 打开速度直接影响留存率

2. 数据库压力降一个数量级
   → JOIN 需要读两张表，CPU/IO 都高
   → 单表查询可以充分利用缓存
   → 高并发下能扛住的 QPS 差 10 倍

3. 缓存更容易
   → 整个文章列表可以直接整个缓存到 Redis
   → JOIN 方案缓存一致性复杂

4. 前端渲染更简单
   → {article.author_name} 直接用
   → 不需要处理作者加载状态

❌ 冗余的代价到底有多大？

┌────────────┬──────────────────────────────────┐
│ 代价       │ 实际影响                          │
├────────────┼──────────────────────────────────┤
│ 多占空间   │ 每篇多 50 字节，10 万篇 = 5MB    │
│ 数据不一致 │ 用户很少改昵称，改了也没人注意    │
│ 更新复杂   │ 异步批量更新，用户无感            │
└────────────┴──────────────────────────────────┘

🎯 关键洞察：频率对比
→ 用户看文章：一天可能看 100 次
→ 用户改昵称：一年可能改 1 次

写 1 次，读 36500 次
你愿意为了 1 次更新方便，让 36500 次读取都变慢吗？

✅ 一致性方案（三级可选）：
1. 强一致：同步更新所有文章 → 用户少可用
2. 最终一致：异步 MQ 批量更新 → 推荐
3. 可接受不一致：只更新详情页，列表用缓存 → 最省事

💡 设计哲学：
不要教条遵守数据库范式！
范式是为了减少更新异常，前提是"更新多"
读多写少的场景，反范式才是正确设计

→ 银行系统：绝对不能冗余（差一块钱是大事）
→ 博客系统：必须冗余（作者名晚更新三天不是事）

行业标准：CSDN、知乎、掘金全都是这么做的
```

### 4. 为什么 ArticleLikes 要有独立的 id 主键？联合主键不行吗？

```
❌ 联合主键的问题：

PRIMARY KEY (article_id, user_id)

1. 其他表要引用这个点赞记录时，需要两个外键
2. ORM 操作不方便，很多框架需要单主键
3. 以后要加扩展字段（取消点赞时间等）不方便

✅ 独立主键 + 联合唯一索引：

id VARCHAR(36) PRIMARY KEY
UNIQUE KEY uk_article_user (article_id, user_id)

两全其美：
- 有独立主键，ORM 好操作
- 联合唯一索引保证不重复点赞
- 扩展方便

💡 数据库设计原则：
所有表都要有独立的单字段主键
不要用业务字段当主键
业务唯一性用唯一索引保证
```

### 5. 为什么所有表都有 is_active 软删字段？DELETE 不行吗？

```
✅ 软删除的好处：

1. 数据可恢复
   → 删错了可以恢复
   → 用户后悔了可以恢复
   → 审计需要保留历史数据

2. 关联数据完整
   → 删除用户，用户的文章还在
   → 文章还能显示"已注销用户"
   → 不会出现外键约束错误

3. 统计准确
   → 统计历史数据时不会少
   → 报表不会因为删除而失真

❌ 软删除的注意点：
- 所有查询都要加 WHERE is_active = TRUE
- 容易忘，导致查出已删除的数据
- 索引要包含 is_active 字段

✅ 本项目的权衡：
软删除的好处远大于成本
框架层面自动加过滤条件
业务代码不需要关心
```

### 6. 为什么 Categories 要存 article_count？COUNT 算出来不行吗？

```
❌ 实时 COUNT 的性能问题：

SELECT c.*, COUNT(a.id) as article_count
FROM categories c
LEFT JOIN articles a ON c.id = a.category_id
GROUP BY c.id

→ 分类列表页每次都要算
→ 10 个分类就要扫所有分类下的所有文章
→ 首页高并发下数据库直接崩

✅ 缓存字段 article_count 的好处：

1. 查询速度提升 100 倍
   → 直接读字段：< 1ms
   → COUNT 统计：几十 ~ 几百 ms
   → 对于首页这种高频场景，天差地别

2. 支持排序和索引
   → ORDER BY article_count DESC
   → 可以给 article_count 建索引
   → COUNT 结果无法建索引

3. 写入成本极低
   → 只在新增/删除文章时更新
   → Prisma 支持原子操作：increment / decrement
   → 一篇文章一天被看 10000 次，但只写 1 次

✅ 一致性保证：
1. 正常流程：文章增删时原子更新 +1/-1
2. 兜底：每天定时任务全量校准一次
3. 计数差 1-2 篇用户根本感知不到

💡 设计哲学：
读多写少的场景 → 一定要用空间换时间
写入 1 次，读取 10000 次 → 太值了

同理：
- Articles.likes → 不每次 COUNT ArticleLikes
- Articles.views → 浏览量缓存
- Articles.comments_count → 评论数缓存
```

### 7. 为什么 RefreshTokens 要存 client_ip？利弊分析

```
✅ 好处：

1. 安全审计（⭐⭐⭐⭐⭐）
   → 用户安全中心可以显示「最近登录设备列表」
   → 显示：北京海淀区 · 2026-05-06 14:30 · 当前设备
   → 用户可以手动下线可疑设备
   → 没有 client_ip 这个功能直接废掉

2. 异常检测（⭐⭐⭐⭐⭐）
   → 同一个 Refresh Token 从北京变成美国 IP → 高度可疑
   → 自动触发风控：强制重新登录、发邮件提醒用户
   → Token 被盗的第一道防线

3. 合规要求（⭐⭐⭐⭐）
   → 等保 2.0、网络安全法要求记录安全操作来源
   → 出了安全问题能溯源

4. 限流防护（⭐⭐⭐）
   → 同一个 IP 10 分钟创建 100 个 Refresh Token → 自动封禁
   → 防暴力破解、防批量注册

❌ 劣势：

1. 隐私合规风险（⭐⭐⭐⭐）
   → IP 属于个人信息
   → 需要在隐私政策中明确说明
   → 可以只存 IP 前两段（如 203.12.x.x），兼顾安全和隐私

2. IP 变动导致误报（⭐⭐⭐）
   → 手机 4G/5G/WiFi 切换，IP 会变
   → VPN 导致 IP 跨地区变化
   → 解决：只在 IP 变化巨大时才告警（如中国 → 美国）

3. 定位不准（⭐⭐）
   → 公司内网、NAT 看到的都是出口 IP
   → 但"地区变化"这个特征仍然有效

💡 针对本项目的结论：
强烈建议保留 client_ip！

→ 成本：每条多存 15 字节，100 万条才 15MB，几乎零成本
→ 收益：账号安全的基础能力，没有的话很多安全功能做不了
→ 隐私优化：可以只存 IP 前两段或只存地区名，不存完整 IP

实用建议：
不要教条说"IP 是隐私所以不能存"
用户看到自己账号从陌生地方登录了，第一反应是"为什么你不告诉我？"
存 IP 是对用户负责，不是侵犯隐私
```

### 8. 为什么 Articles.tags 用逗号分隔存储？这不是违反范式吗？

```
🎯 两种方案对比：
```

### 9. Articles.likes 高并发点赞怎么处理？如何避免竞态竞争？

```
🚨 竞态问题是怎么产生的？

❌ 90% 的新手都会写错的代码：

// 先查再更新
const article = await prisma.articles.findUnique({ where: { id } });
await prisma.articles.update({
  where: { id },
  data: { likes: article.likes + 1 },
});

高并发时间线：
T1: 线程 A 读取 likes = 100
T2: 线程 B 读取 likes = 100
T3: 线程 A 更新为 101
T4: 线程 B 更新为 101 ← 丢了一个赞！

结果：2 个人点赞，最后只加了 1
1000 并发下，可能只加了 50 个
这就是经典的「读-改-写」竞态问题

📊 五种解决方案对比：

┌──────────────────┬──────────┬──────────┬──────────┬──────────┐
│ 方案             │ 并发能力 │ 一致性   │ 复杂度   │ 推荐度   │
├──────────────────┼──────────┼──────────┼──────────┼──────────┤
│ A. 原子增量      │ 中       │ ✅ 强一致│ 极低     │ ⭐⭐⭐⭐⭐ │
│ B. 乐观锁        │ 中高     │ ✅ 强一致│ 低       │ ⭐⭐⭐⭐  │
│ C. 悲观锁        │ 低       │ ✅ 强一致│ 中       │ ⭐⭐     │
│ D. Redis 聚合    │ 极高     │ ⚠️ 最终  │ 高       │ ⭐⭐⭐⭐  │
│ E. 消息队列批量  │ 极高     │ ⚠️ 最终  │ 很高     │ ⭐⭐⭐    │
└──────────────────┴──────────┴──────────┴──────────┴──────────┘

✅ 方案 A：数据库原子增量（首推，最简单）

Prisma 原生支持 increment/decrement：

await prisma.articles.update({
  where: { id: articleId },
  data: {
    likes: {
      increment: 1,  // ✅ 原子操作，数据库层面保证不会竞态
    },
  },
});

翻译成 SQL：
UPDATE articles SET likes = likes + 1 WHERE id = ?

原理：
整个 UPDATE 语句是原子的
数据库执行期间会锁行
不需要先查，直接在数据库层面完成 +1

优点：
→ 代码最简单，一行搞定
→ 强一致性，不会丢赞
→ Prisma 原生支持，零额外成本

缺点：
→ 极高并发下（1000+ QPS）行锁会成为瓶颈
→ 但对于博客系统，完全够用了

✅ 完整实现（配合 ArticleLikes 唯一索引防重复点赞）：

async likeArticle(articleId: string, userId: string) {
  try {
    // 1. 插入点赞记录（联合唯一索引保证不重复）
    await prisma.articleLikes.create({
      data: { article_id: articleId, user_id: userId },
    });

    // 2. 原子增量更新点赞数
    await prisma.articles.update({
      where: { id: articleId },
      data: { likes: { increment: 1 } },
    });

    return { success: true };
  } catch (e) {
    // 唯一索引冲突 = 已经点赞过了
    if (e.code === 'P2002') {
      throw new Error('已经点赞过了');
    }
    throw e;
  }
}

🚀 方案 D：Redis 聚合 + 异步落库（百万级并发）

架构：
用户点赞 → Redis INCR → 立即返回成功
                  ↓
            定时任务（每秒）
                  ↓
            批量写入 MySQL

优点：
→ 并发能力拉满，Redis 扛 10万 QPS 没问题
→ 用户体验极致，毫秒级响应
→ 数据库压力极低，每秒写一次

缺点：
→ 最终一致性，可能有几秒延迟
→ 系统复杂度高，要处理 Redis 宕机等异常

🎯 针对本项目的结论：

强烈推荐「方案 A：原子增量 + 唯一索引防重复」

┌──────────────────┬──────────────────────────────────┐
│ 维度             │ 分析                              │
├──────────────────┼──────────────────────────────────┤
│ 并发量级         │ 博客一篇文章一秒 100 赞顶天        │
│ 代码复杂度       │ 一行代码，新手也能写对             │
│ 一致性保证       │ 强一致，绝对不会丢赞               │
│ 维护成本         │ 无额外组件                         │
└──────────────────┴──────────────────────────────────┘

📈 升级路线图：

┌──────────────────┬─────────────────────┐
│ 业务规模         │ 最佳方案            │
├──────────────────┼─────────────────────┤
```

### 10. 为什么每个表都要有 created_at 和 updated_at？用途是什么？

```
📊 两个字段的职责分工：

┌────────────┬──────────────┬──────────────────────────────┐
│ 字段       │ 语义         │ 更新时机                     │
├────────────┼──────────────┼──────────────────────────────┤
│ created_at │ 记录出生时间 │ 只写一次，插入时赋值，永不变  │
│ updated_at │ 最后心跳时间 │ 每次修改都更新               │
└────────────┴──────────────┴──────────────────────────────┘

✅ created_at 的 5 大核心用途：

1. 时间线排序（最常用）
   → 博客首页：最新文章在前
   → ORDER BY created_at DESC
   → 没有这个字段，你按什么排序？按主键？删了重发顺序就乱了

2. 数据溯源与审计
   → 出问题了：张三账号异常登录？
   → 看看 RefreshTokens.created_at = 凌晨 2 点
   → 哦，那天他正好在美国出差，没问题
   → 没有创建时间，你回答不了「什么时候发生的」

3. 统计分析
   → 今年新增了多少用户？WHERE created_at >= '2026-01-01'
   → 5 月份发了多少篇文章？
   → 业务报表、增长分析，全靠这个字段

4. 数据治理与清理
   → 清理 1 年前已撤销的 Refresh Token
   → 没有时间，你怎么判断哪些是垃圾数据？

5. 用户体验细节
   → 文章卡片显示：张三 · 2小时前
   → 用户一看就知道文章新不新
   → 没有 created_at，你怎么算「2小时前」？

✅ updated_at 的 5 大核心用途：

1. 增量同步（分布式系统必备）
   → 第一次：全量拉取 10 万条
   → 后续：只拉取 updated_at > 上次同步时间 的数据
   → 从 10 万条变成 100 条，性能提升 1000 倍
   → 没有 updated_at，每次都得全量同步，系统直接卡死

2. 缓存失效判断
   → 缓存的 updated_at < 数据库的 updated_at
   → 说明缓存过期了，重新查数据库
   → 缓存系统最基础的失效判断逻辑

3. 数据新鲜度展示
   → 文章底部显示：最后编辑于 2026-05-06 14:30
   → 技术文章，3 年前的可能已经不适用了
   → 用户一看就知道有没有过时

4. 多端同步冲突解决
   → 用户在手机上改文章标题
   → 同时在电脑上也改了同一篇
   → 哪个版本生效？看 updated_at，晚的覆盖早的
   → 没有 updated_at，多端同步根本做不了

5. 问题排查的救命稻草
   → 线上出 Bug：文章内容不对
   → 看看 updated_at = 15:20
   → 查日志，15:20 正好有个更新接口报错
   → 顺藤摸瓜找到问题
   → 没有 updated_at，你根本不知道数据什么时候被改坏的

🎯 你可能忽略的设计细节：

❌ 不要用业务时间代替

model Articles {
  published_at BigInt?  // 业务发布时间，可以改草稿
  created_at   BigInt   // 数据创建时间，永远不变
  updated_at   BigInt   // 最后更新时间
}
→ 文章可以存草稿 3 个月再发布，两个时间完全不是一回事

❌ 不要只存其中一个
新手说：updated_at 没用，只要 created_at 就行
三个月后产品经理：加个增量同步功能吧
你：... 做不了

→ 等你需要的时候再补，之前的数据已经永远丢失了

✅ Prisma 零成本自动更新

model Articles {
  id         String   @id @default(uuid())
  created_at BigInt   @default(now())  // 插入时自动赋值
  updated_at BigInt   @updatedAt       // ✅ Prisma 自动更新，不用你写！
}

💡 设计哲学：数据的四个基本问题

任何一条数据，你都应该能回答：
1. 它是什么？    → id + 业务字段
2. 什么时候来的？→ created_at
3. 什么时候改的？→ updated_at
4. 它还在不在？  → is_active

少了任何一个，某天你一定会遇到一个答不上来的线上问题

📝 总结：为什么「每个表都要有」？

┌──────────────────┬──────────────────────────────────┐
│ 理由             │ 说明                              │
├──────────────────┼──────────────────────────────────┤
│ 成本为零         │ 两个 BigInt = 16 字节，忽略不计   │
│ 不知道什么时候用 │ 等你需要时，历史数据已经补不回来了 │
│ 行业标准         │ 所有正规数据库设计都会有这两个字段 │
│ 救命用的         │ 线上排查问题时，你会感谢当初加了   │
└──────────────────┴──────────────────────────────────┘

最经典的打脸场景：
新手：这两个字段没用啊，删了吧
上线三个月后：我靠！当初为什么没加时间字段！

这不是过度设计，这是数据库设计的基本修养
```

### 11. `Users ||--o{ RefreshTokens` 1:N 关系深度分析

```
🔍 ER 符号含义：

Users ||--o{ RefreshTokens : "拥有 1:N"
  ↑    ↑   ↑ ↑
  |    |   | └─  0 个或多个
  |    |   └────  Crow's Foot 表示"多"
  |    └────────  1 个且必须有
  └─────────────  实体 1

含义：1 个 User 必须拥有 0 个或多个 RefreshToken

📋 Schema 核心设计：

model RefreshTokens {
  user_id String
  users   Users   @relation(
    fields: [user_id],
    references: [id],
    onDelete: Cascade,  // ✅ 关键：删除用户时自动删除所有 token
    onUpdate: Restrict
  )
  @@index([user_id])  // ✅ 查用户的 token 走索引
}

model Users {
  refresh_tokens RefreshTokens[]  // ✅ 反向关联
}

设计意图：
→ onDelete: Cascade：删除用户时，所有登录令牌自动失效，防安全隐患
→ @@index([user_id])：查询"用户所有登录设备" O(log n) 复杂度

🔄 业务生命周期全流程：

1. 创建：用户登录/注册
   → 每登录一个新设备 → 产生 1 条新 RefreshToken
   → Redis 存储：refresh:token:xxx + refresh:user:xxx 集合

2. 使用：Token 刷新
   → Access Token 2 小时过期，Refresh Token 7 天过期
   → 续期只换 Access Token，不换 Refresh Token

3. 销毁 1：单设备登出
   → logout(userId, refreshToken) → 只删当前设备的 token
   → 其他登录设备不受影响

4. 销毁 2：全设备踢出
   → logout(userId) → deleteAllUserRefreshTokens(userId)
   → 场景：账号异常强制下线、改密码踢出旧设备

5. 销毁 3：级联删除（用户被删）
   → MySQL 自动执行：DELETE FROM refresh_tokens WHERE user_id = 'xxx'
   → 不需要写代码，数据库层保证

🎯 核心能力矩阵：

┌──────────────────┬────────────────────────────────────┐
│ 能力             │ 实现方式                            │
├──────────────────┼────────────────────────────────────┤
│ 多设备同时登录   │ 每个设备一条独立 token              │
│ 单设备精准登出   │ token 唯一索引，按 token 删除       │
│ 全设备一键踢出   │ user_id 索引查所有 token 批量删     │
│ 级联安全清理     │ onDelete: Cascade，删除用户自动清理  │
│ 登录设备管理     │ client_ip + created_at 显示列表     │
│ 异常检测         │ token + client_ip 地域变化告警      │
└──────────────────┴────────────────────────────────────┘

⚠️ 代码架构现状说明：

当前架构：Redis 为主，数据库为预留
→ RefreshTokenRedisService 完全用 Redis 存储
→ 带 TTL 自动过期，性能极高
→ MySQL refresh_tokens 表 Schema 完整但代码未写入

风险分析：
→ ✅ Redis 优点：性能高、自动过期、天然缓存
→ ⚠️ 风险：Redis 宕机/数据丢失 → 所有用户强制掉线
→ 💡 建议：数据库做持久化兜底，Redis 做缓存层
           未命中时回源数据库，冷热分层

✅ 设计亮点总结：

┌──────────────────────┬──────────────────────────────────┐
│ 设计决策             │ 优点                              │
├──────────────────────┼──────────────────────────────────┤
│ 1:N 多 token 设计    │ 支持多设备独立登录                │
│ onDelete: Cascade    │ 删除用户无遗留僵尸 token          │
│ user_id 索引         │ 查询用户所有 token 性能优异        │
│ refresh_token 唯一索引│ 防止重复 token，快速查询单条       │
│ revoked 软删除字段   │ 支持 token 单独撤销（预留）        │
│ client_ip 字段       │ 登录设备溯源、风控检测            │
└──────────────────────┴──────────────────────────────────┘

📌 结论：

Users ||--o{ RefreshTokens 是典型的「用户-会话」多设备登录模型
→ 关系本质：一个用户多设备登录，每设备持有独立长期令牌
→ 核心价值：多设备在线能力 + 精细化登录管理 + 安全风控基础
→ 当前状态：Schema 完整，Redis 为主，数据库预留兜底
→ 架构建议：Redis 缓存 + 数据库持久化双写，防单点故障

这是企业级认证系统的标准设计，覆盖 99% 的多设备登录场景
```
