## 🧠 复刻时的思考

### 1. 为什么主键用 UUID 而不是 INT AUTO_INCREMENT？

```
✅ UUID 的好处：

1. 分布式安全
   → 微服务架构下，不需要集中的 ID 生成器
   → 每个服务自己生成 ID，不会冲突
   → 方便数据合并、迁移

2. 不暴露业务数据量
   → 攻击者看不到 /article/1 到 /article/10000
   → 不知道你到底有多少篇文章
   → 防爬虫，防商业情报

3. 可以在应用层生成
   → 不需要等数据库返回自增 ID
   → 插入前就知道 ID 是什么
   → 方便做批量操作

❌ UUID 的缺点：
- 占空间更大（36 字符 vs 4 字节 INT）
- 索引性能略差（无序插入）

✅ 本项目的权衡：
安全性和分布式优势 > 一点点性能损失
用户量不大的情况下，差异可以忽略

💡 更好的方案：UUID v7
有序 UUID，兼顾有序性和唯一性
数据库索引性能和 INT 差不多
MySQL 8.0 原生支持
```

### 2. 为什么时间戳用 BigInt 而不是 DATETIME/TIMESTAMP？

```
✅ BigInt 的好处：

1. 时区无关
   → 2024-05-01 12:00:00 在不同时区表示不同时间
   → 1714555200000 在全世界都是同一个时刻
   → 不需要服务器时区配置，不会踩坑

2. 计算方便
   → 加一小时：+ 3600 * 1000
   → 减一天：- 86400 * 1000
   → 不需要用 DATE_ADD() 之类的函数

3. 排序性能好
   → 整型比较远快于时间类型比较
   → 范围查询也更快

✅ 权衡：
可读性差一点（人眼看不懂毫秒数）
但代码里处理起来更方便
前端转成当地时间显示就行

💡 原则：
所有时间存储都用 UTC 毫秒时间戳
只在展示给用户看的时候才转成本地时间
```

### 3. 为什么 Articles 表要有 author_name 和 author_avatar 冗余字段？JOIN 不行吗？

```
❌ JOIN 的性能问题：

文章列表页查 10 篇文章
→ 1 次查 articles 表
→ 10 次查 users 表取作者信息
→ 1 + N 查询问题
→ 或者 JOIN，但 JOIN 在大表下性能差

✅ 冗余字段的好处：
查 10 篇文章 → 1 次查询搞定
作者名和头像都在 articles 表里
不需要 JOIN，不需要额外查

✅ 一致性保证：
用户改昵称
1. 更新 users 表
2. 异步更新所有 articles 表的 author_name
3. 或者接受最多 1 天的不一致（缓存过期）

✅ 权衡：
空间换时间
多存两个字符串（几十字节）
每次查询省几十毫秒
对于读多写少的场景（博客系统），太值了

💡 经典的反范式设计：
读多写少 → 适当冗余
写多读少 → 严格范式，避免不一致
根据业务场景选择，不要教条
```

### 4. 为什么 ArticleLikes 要有独立的 id 主键？联合主键不行吗？

```
❌ 联合主键的问题：

PRIMARY KEY (article_id, user_id)

1. 其他表要引用这个点赞记录时，需要两个外键
2. ORM 操作不方便，很多框架需要单主键
3. 以后要加扩展字段（取消点赞时间等）不方便

✅ 独立主键 + 联合唯一索引：

id VARCHAR(36) PRIMARY KEY
UNIQUE KEY uk_article_user (article_id, user_id)

两全其美：
- 有独立主键，ORM 好操作
- 联合唯一索引保证不重复点赞
- 扩展方便

💡 数据库设计原则：
所有表都要有独立的单字段主键
不要用业务字段当主键
业务唯一性用唯一索引保证
```

### 5. 为什么所有表都有 is_active 软删字段？DELETE 不行吗？

```
✅ 软删除的好处：

1. 数据可恢复
   → 删错了可以恢复
   → 用户后悔了可以恢复
   → 审计需要保留历史数据

2. 关联数据完整
   → 删除用户，用户的文章还在
   → 文章还能显示"已注销用户"
   → 不会出现外键约束错误

3. 统计准确
   → 统计历史数据时不会少
   → 报表不会因为删除而失真

❌ 软删除的注意点：
- 所有查询都要加 WHERE is_active = TRUE
- 容易忘，导致查出已删除的数据
- 索引要包含 is_active 字段

✅ 本项目的权衡：
软删除的好处远大于成本
框架层面自动加过滤条件
业务代码不需要关心
```
