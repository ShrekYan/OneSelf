## 📊 索引设计流程图

```mermaid
flowchart TD
    START[开始设计索引] --> ANALYZE[分析查询模式]
    ANALYZE --> Q1{查询的 WHERE 条件是什么？}
    Q1 --> Q2{查询的 ORDER BY 是什么？}
    Q2 --> Q3{查询的 JOIN 条件是什么？}
    Q3 --> Q4{查询频率高吗？}

    Q4 --> DESIGN[设计索引]

    DESIGN --> RULE1[最左前缀原则：等值查询在前，排序在后]
    DESIGN --> RULE2[区分度高的字段在前]
    DESIGN --> RULE3[索引字段数 <= 5 个]
    DESIGN --> RULE4[单表索引数 <= 5 个]

    RULE1 & RULE2 & RULE3 & RULE4 --> VERIFY{验证索引效果}
    VERIFY --> EXPLAIN[EXPLAIN 查看执行计划]
    EXPLAIN --> ANALYZE_CHECK[ANALYZE TABLE 统计信息更新]
    ANALYZE_CHECK --> SLOW[检查慢查询日志]

    SLOW --> OK{性能达标？}
    OK -->|是| DONE[完成，监控]
    OK -->|否| ADJUST[调整索引设计，重复流程]

    DONE --> MONITOR[持续监控索引使用率]
    MONITOR --> CLEAN[定期删除未使用的索引]

    note over DESIGN "关键：不是加越多索引越好
索引本身也占空间，也会拖慢写入
每加一个索引都要有充分的理由"
```

## 🧠 复刻时的思考

### 1. 为什么布尔字段 is_active 也要加索引？区分度不是很低吗？

```
✅ 要看查询频率：

如果查询是：
SELECT * FROM users WHERE username = ?
→ username 是唯一索引，这个就够了，不需要 is_active 索引

如果查询是：
SELECT * FROM users WHERE is_active = TRUE
→ 要列出所有启用的用户，可能很多
→ 这个索引就很有用

✅ 本项目的实际场景：
管理后台的用户列表页
默认只显示启用的用户
分页查询时需要这个索引

✅ 索引大小：
布尔字段的索引特别小
100 万行数据，索引才不到 1MB
占用空间可以忽略不计

💡 索引设计原则：
不要光看区分度
要看实际的查询模式
只要这个字段在 WHERE 里出现了
而且查询频率不低
就应该考虑加索引
```

### 2. 为什么 article_content_blocks 不用两个独立索引？要用复合索引？

```
❌ 两个独立索引：
INDEX idx_article_id (article_id)
INDEX idx_sort_order (sort_order)

查询：
WHERE article_id = ? ORDER BY sort_order

MySQL 只能用到 article_id 索引
拿到结果后还要 filesort 排序
如果文章有 100 个块，排序就很慢

✅ 复合索引（推荐）：
INDEX idx_article_sort (article_id, sort_order)

article_id 等值过滤后
sort_order 本身就是有序的
不需要额外排序！

💡 复合索引的 B-Tree 结构：
(article1, 1)
(article1, 2)
(article1, 3)
...
(article2, 1)
(article2, 2)

查询 article_id = 1 时
直接按顺序读出来就行，不需要排序
性能提升几倍到几十倍
```

### 3. 为什么不把所有字段都加上索引？

```
❌ 索引过多的坏处：

1. 占用存储空间
   每个索引都是一个 B-Tree
   100 万行数据，每个索引 1-10MB
   10 个索引就是几十上百 MB

2. 拖慢写入速度
   INSERT/UPDATE/DELETE 时
   每个索引都要更新
   5 个索引 = 写入慢 5 倍

3. 查询优化器选择困难
   索引太多，优化器可能选错
   反而导致性能下降

✅ 经验法则：
单表索引数控制在 5 个以内
复合索引不超过 5 个字段
不要为了还没出现的查询加索引
先有查询，再加索引
```

### 4. EXPLAIN 结果怎么看？哪些列最重要？

```
✅ 重点看这几列：

1. type：访问类型
   从好到坏排序：
   system > const > eq_ref > ref > range > index > ALL
   看到 ALL 就是全表扫描，必须优化

2. key：实际用的索引
   是不是你预期的那个索引？
   NULL 就是没用到索引

3. rows：预估扫描的行数
   越小越好
   1000 行以内一般没问题
   10000 行以上就要注意了

4. Extra：额外信息
   看到 'Using filesort' → 没用到索引排序，需要优化
   看到 'Using temporary' → 用了临时表，需要优化
   看到 'Using index' → 覆盖索引，很好

✅ 优化顺序：
消除全表扫描（ALL）
→ 消除 filesort
→ 消除 temporary
→ 减少 rows 数量
```

### 5. 怎么判断哪些索引没用？可以删了？

```
✅ MySQL 5.7+ 自带统计：

SELECT * FROM sys.schema_unused_indexes
WHERE object_schema = 'your_database'

这个视图会显示自从上次 MySQL 重启后
一次都没用过的索引

✅ 索引使用情况监控：

统计一个月：
- 使用率 < 1% 的索引 → 可以考虑删除
- 从来没用到的索引 → 直接删除
- 写入量大，查询很少的索引 → 权衡

✅ 删除索引的正确姿势：
1. 先在测试环境删，确认没有影响
2. 生产环境先观察一周，确认确实没人用
3. 删除前先备份索引定义
4. 留好回滚方案，随时可以加回来

💡 索引不是加了就一劳永逸
业务在变，查询在变
索引也要跟着迭代
半年回顾一次索引使用情况
该加的加，该删的删
```
