## 🧠 复刻时的思考

### 1. Categories 表的 article_count 缓存字段怎么更新？

```
✅ 最终一致性更新策略：

场景 1：发布新文章
1. INSERT INTO articles
2. UPDATE categories SET article_count = article_count + 1 WHERE id = ?

场景 2：删除文章
1. UPDATE articles SET is_active = FALSE
2. UPDATE categories SET article_count = article_count - 1 WHERE id = ?

场景 3：迁移文章分类
1. UPDATE articles SET category_id = NEW_ID
2. 旧分类 -1，新分类 +1

✅ 异步延迟更新：
点赞、浏览量这类高频操作
不需要实时更新计数器
可以每 100 次浏览批量更新一次数据库
或者用 Redis 计数，定期同步

💡 权衡：
允许计数器有短暂的不一致
换取极高的写入性能
读多写少的场景非常适合
```

### 2. ArticleContentBlocks 的 content 字段为什么用 TEXT 而不是 VARCHAR？

```
✅ TEXT vs VARCHAR：

VARCHAR(65535)：
- 最大 65535 字节
- 整行最大 65535 字节（所有字段加起来）
- 存放在内存里

TEXT：
- 最大 65535 字节（还有 MEDIUMTEXT, LONGTEXT）
- 单独存放，不占行的大小限制
- 不会影响其他字段的查询性能

✅ 为什么用 TEXT：
文章内容可能很长
一篇长文可能几万字
还可能有图片的 base64
用 VARCHAR 很容易超限

✅ 性能优化：
列表页只查 articles 表
不查 content_blocks 表
详情页才查内容块
所以 TEXT 的性能影响很小
只有详情页会用到
```

### 3. ArticleLikes 表为什么没有 is_liked 字段？取消点赞直接删除？

```
✅ 为什么直接删除：

1. 业务语义简单
   → 点赞了就有记录
   → 取消点赞就删记录
   → 存在 = 已点赞，不存在 = 未点赞
   → 不需要额外字段表示状态

2. 性能更好
   - COUNT(*) 更快（行数少）
   - 索引更小
   - 查询 WHERE user_id = ? AND article_id = ?
   - 有就是点赞了，没有就是没点

3. 节省空间
   - 布尔字段也要占 1 字节
   - 100 万点赞就是 1MB
   - 积少成多

❌ 什么时候需要 is_liked 字段：
- 需要统计"取消点赞率"
- 需要完整的点赞历史
- 数据分析需要
- 这时候应该叫 ArticleLikeHistory 表

💡 本项目的权衡：
不需要统计取消点赞
所以直接删除，保持简单
```

### 4. 复合索引 (article_id, sort_order) 为什么顺序是这样的？反过来不行吗？

```
✅ 最左前缀原则：

INDEX (a, b, c)
可以用 a 查询
可以用 a + b 查询
可以用 a + b + c 查询
不能用 b 查询
不能用 c 查询

✅ 为什么是 (article_id, sort_order)：
查询语句是：
SELECT * FROM article_content_blocks
WHERE article_id = ?
ORDER BY sort_order

先过滤 article_id = ?
然后在结果里按 sort_order 排序
article_id 在前，sort_order 在后

✅ 如果反过来：
INDEX (sort_order, article_id)
WHERE article_id = ? → 用不到索引！
因为最左前缀是 sort_order，查询没有用到

💡 索引设计的铁律：
等值查询字段放前面
范围/排序字段放后面
千万不要搞反顺序
搞反了索引就废了
```

### 5. Articles 表为什么有 is_top 和 is_published 两个布尔字段？合并成一个 status 字段不行吗？

```
✅ 两个独立布尔的好处：

1. 组合灵活
   is_top AND is_published → 置顶已发布
   is_top AND NOT is_published → 准备置顶，还没发布
   NOT is_top AND is_published → 普通已发布
   NOT is_top AND NOT is_published → 草稿

2. 查询方便
   查所有置顶：WHERE is_top = TRUE
   查所有已发布：WHERE is_published = TRUE
   不需要想 status 的枚举值

3. 扩展方便
   以后加 is_recommend（是否推荐）
   再加一个布尔字段就行
   不需要改枚举

❌ 缺点：
字段有点多
但布尔字段只占 1 字节
10 个布尔字段才 10 字节
完全可以接受

💡 设计原则：
独立的状态用独立的字段
互斥的状态用枚举字段
置顶和发布不是互斥的
所以应该分开
```
