# 全栈转型客观评估与学习调整

> 记录日期：2026-05-25
> 适用阶段：前端工程师向全栈 + AI 工程师转型过程中期
> 评估原则：客观、不美化、用于后续学习路线调整

---

## 一、总体评估结论

如果目标是：

> 能独立完成一个中小型全栈业务系统，并能结合 AI 工具高效开发、维护、迭代。

当前全栈转型进度大约处于：

> **45% - 55%**

更准确的定位是：

> **前端专家 + AI 工程化学习者 + 后端建模补课期。**

这说明当前已经明显越过“只会前端、刚接触后端”的阶段，但还没有进入“稳定独立全栈交付”的阶段。

## 三、已经完成得比较好的部分

### 1. 前端能力

前端不是当前转型瓶颈。

已经具备：

- React + TypeScript 开发经验
- 前端工程化意识
- 组件拆分能力
- API 封装意识
- 状态管理经验
- 性能、安全、规范意识

后续需要注意的是：

> 不要用纯前端思维理解后端。

后端更关注数据一致性、权限边界、事务、查询性能、异常处理和系统稳定性。

---

### 2. AI 工程化能力

当前最突出的能力之一是 AI 协同开发意识。

项目中已经沉淀：

- `.claude/` 规则体系
- Agent 配置
- Spec Kit 文档
- 小贝练习项目
- 工作流拆解
- 教学文档
- 架构决策文档

这说明当前已经不是简单“使用 AI 写代码”，而是在搭建自己的 AI 协同开发体系。

但距离非常成熟还需要继续验证：

- 多个真实业务功能从需求到上线完整闭环
- AI 生成结果的质量评估机制
- 失败案例库
- 自动化测试兜底
- 生产问题复盘

### 3. 工程化规范意识

## 四、当前主要短板

### 1. 数据库建模

当前数据库建模大约处于：

> **25% - 35%**

这是当前最核心的短板，也是转全栈必须补的基本功。

需要重点训练：

- 业务拆表
- 字段定义
- 主键 / 外键设计
- 一对多 / 多对多关系
- 中间表设计
- 状态字段设计
- 软删除字段设计
- 基础索引设计
- 根据页面和接口反推表结构

当前可能能看懂已有表结构，但从业务需求独立反推完整表结构还不够稳。

典型需要反复练习的问题：

- 标签应该用字符串存储，还是单独建表？
- 评论回复用 `parent_id`，还是单独回复表？
- 点赞和收藏是否应该共用行为表？
- 审核状态如何设计？
- 哪些表需要软删除？
- 哪些字段必须加索引？
- 统计字段是实时查询，还是冗余存储？
- 大字段是否需要拆表？

---

### 2. 后端业务开发能力

当前后端业务能力大约处于：

> **30% - 40%**

后端业务能力的核心不是 Controller 和 Service 语法，而是：

- DTO 怎么定义
- 参数怎么校验
- 权限怎么控制
- Service 责任怎么拆
- Prisma 查询怎么写
- 事务怎么处理
- 异常怎么统一
- 日志怎么打
- 缓存什么时候用
- 接口返回结构怎么保持稳定
- 数据一致性怎么保证

当前更接近：

> 能跟着已有模式写，但从 0 独立设计复杂后端模块还不够稳。

---

### 3. 数据库查询和性能意识

当前 SQL / ORM 查询与性能意识大约处于：

> **25% - 35%**

后端常见问题包括：

- N+1 查询
- 分页性能
- 模糊查询性能
- `count` 慢
- 排序字段缺少索引
- 大字段影响查询
- 统计字段实时计算过慢
- Redis 缓存一致性
- 事务锁冲突

现阶段不需要深入数据库内核，但至少要能识别常见业务性能坑。

---

### 4. 部署运维能力

当前部署运维能力大约处于：

> **20% - 30%**

全栈不一定要成为专业运维，但至少需要掌握：

- 本地环境
- 测试环境
- 生产环境配置
- Docker 基础
- 数据库连接
- 环境变量
- 日志查看
- 服务启动
- 接口联调
- 简单部署
- 回滚意识

这部分当前不是主线，但后续需要补基础能力。

---

## 五、当前不建议深入的内容

现阶段不要过早深入以下内容：

- Kubernetes
- 消息队列深度原理
- 高并发架构
- 分布式事务
- 数据库内核
- B+ Tree 底层细节
- redo log / undo log 深层机制
- Buffer Pool 细节
- 大模型训练
- 微服务治理
- 复杂 DevOps

这些不是不重要，而是当前优先级不高。

当前最重要的是：

> 先具备能把业务完整落库、完整写接口、完整联调前端的能力。

## 六、下一阶段最关键突破点

### 1. 死磕数据库建模

目标不是成为数据库专家，而是：

> 给一个业务需求，能拆出合理的表结构。

建议重点复刻和练习这些业务：

- 用户系统
- 文章系统
- 评论系统
- 点赞收藏
- 分类标签
- 关注系统
- 通知系统
- 后台审核
- AI 对话历史
- AI 知识库文档

每个业务都按以下顺序训练：

```text
业务需求
  ↓
页面展示
  ↓
接口设计
  ↓
表设计
  ↓
字段定义
  ↓
关系设计
  ↓
基础索引
```

---

### 2. 打通 NestJS CRUD 闭环

每个模块都按固定流程练习：

```text
表设计
  ↓
Prisma Model
  ↓
DTO
  ↓
Controller
  ↓
Service
  ↓
权限校验
  ↓
分页查询
  ↓
创建 / 更新 / 删除
  ↓
异常处理
  ↓
接口联调
```

先不要追求高级架构，先把这个闭环练到肌肉记忆。

---

### 3. 用完整业务功能突破

建议优先选择“评论系统”作为完整闭环训练对象。

评论系统可以覆盖：

- 评论表设计
- 回复关系设计
- 评论列表接口
- 发布评论接口
- 删除评论接口
- 点赞评论接口
- 前端页面展示
- 登录权限控制
- 分页
- 排序
- 基础索引
- 测试

如果能独立打穿 3 个类似模块，全栈能力会明显跃迁。

## 七、阶段定位

如果把“全栈 + AI 工程师”分成 4 个阶段：

| 阶段       | 状态                                       |
| ---------- | ------------------------------------------ |
| 0% - 25%   | 只会前端，刚接触后端                       |
| 25% - 50%  | 能看懂后端项目，开始写简单接口             |
| 50% - 75%  | 能独立完成中等复杂度全栈业务               |
| 75% - 100% | 能设计架构、处理生产问题、稳定交付复杂系统 |

当前处于：

> **45% - 55%：正在从第二阶段跨向第三阶段。**

这意味着：

- 已经不是纯前端
- 已经具备 AI 协同开发意识
- 已经建立工程化学习体系
- 但后端基本功还没有完全稳定
- 数据库建模仍是当前最关键短板

## 八、学习调整原则

后续学习应遵循以下原则：

### 原则 1：少横向扩展，多纵向打穿

不要同时学习太多后端概念。

优先选择一个业务模块，从数据库到前端完整打穿。

---

### 原则 2：先会做业务，再补底层原理

当前最重要的不是深入数据库内核，而是：

- 能拆表
- 能定义字段
- 能设计关系
- 能加基础索引
- 能写查询
- 能写接口
- 能联调页面

底层原理以后遇到性能瓶颈再补。

---

### 原则 3：继续大量手写复刻

数据库设计和字段定义属于基本功，短期没有捷径。

手写复刻的价值是：

- 建立字段命名直觉
- 熟悉表关系模式
- 形成索引判断习惯
- 熟悉业务落库方式
- 把“看懂”变成“会写”

建议继续坚持多轮复刻，但每一轮要有不同目标：

| 轮次    | 目标                       |
| ------- | -------------------------- |
| 第 1 轮 | 照着抄，熟悉语法和字段     |
| 第 2 轮 | 闭卷默写，对照找遗漏       |
| 第 3 轮 | 修改字段，理解字段约束     |
| 第 4 轮 | 新增表，练习关系设计       |
| 第 5 轮 | 重构设计，比较不同建模方案 |

---

### 原则 4：每个模块都沉淀一份复盘

每完成一个业务模块，至少记录：

- 业务需求是什么
- 拆了哪些表
- 每张表为什么存在
- 每个核心字段为什么这样定义
- 哪些字段加了索引
- 接口如何查询这些表
- 遇到了什么问题
- 下次如何改进

## 十、最终结论

当前最真实的位置是：

> **前端很强，AI 工程化意识很强，后端和数据库正在补基本功。**

当前最关键的突破口是：

> **数据库建模 + NestJS 业务闭环。**

一旦能够独立完成 3 个中等复杂度业务模块，例如评论系统、收藏系统、通知系统，整体全栈进度会从当前的 45% - 55% 明显提升到 65% - 70%。

现阶段不要追求“什么都懂”，而是要追求：

> **看到业务，能建表；看到页面，能反推接口；看到接口，能写后端；看到数据，能设计关系。**
