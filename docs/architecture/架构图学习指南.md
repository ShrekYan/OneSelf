# 架构图学习指南：手写复刻法

> 适用人群：有经验的开发者（10年前端经验）转后端，有概念但理解不深入，想建立架构直觉

---

## 🎯 你的阶段定位：「知其然，不知其所以然」

| 阶段          | 特征                                                                                | 你现在的位置      |
| ------------- | ----------------------------------------------------------------------------------- | ----------------- |
| L1 新手       | "这是什么？完全不懂"                                                                | ❌ 不是你         |
| **L2 实践者** | **"代码我能写出来，也能跑通，但是...**<br>**为什么要这么设计？有没有更好的方案？"** | ✅ **这就是你！** |
| L3 架构师     | "这个问题有3种方案，各有什么trade-off，在这个场景下选A最好"                         | 🎯 你的目标       |

---

## 💡 为什么手写复刻对你的价值 ×3

你已经有了上下文——你知道这些代码是怎么写的，你知道每个文件在哪，你甚至可能在写的时候就疑惑过：

> "为什么要多写这一层？直接写不行吗？"
>
> "为什么要搞这么复杂？简单点不好吗？"

以前这些疑惑你可能跳过去了，现在画图就是**把这些疑惑一个个捡起来，想明白**的过程。

### 你的独特优势

```
普通人画图：
"哦，这里有个箭头... 嗯，从A指到B... 记下了"
（不知道A和B到底是什么，只是死记硬背）

你画图：
"哦，这个 AuthController 我写过！
  当时还加了个 RefreshTokenRedisService...
  原来它们的关系是这样的！
  当时为什么要独立成 Service 来着？
  哦对！因为要在好几个地方用到，抽出来复用！"
```

你画的不是抽象的方框和箭头——你画的是**你写过的代码**在大脑里重新组织、连接、建立关系的过程。

## 🏗️ 三层学习价值

### 第一层：从"看懂"到"真懂"

| 状态                           | 理解深度 | 特征                                           |
| ------------------------------ | -------- | ---------------------------------------------- |
| 看AI生成的图                   | ~20%     | "嗯，有道理，我看懂了"，关上就忘               |
| 照着画一遍                     | ~40%     | "哦，原来这两个表是这样连的"，但还是停留在表面 |
| 关掉原图默写                   | ~60%     | 画到一半卡壳了 → 这就是你没真正理解的地方      |
| 卡壳了自己想明白为什么这么设计 | ~85%     | 这才是真正的学习，这个设计以后你也会用         |

**关键：卡壳的地方才是最有价值的**

- 画ER图时，犹豫"这个字段为什么要冗余？" → 你开始理解"空间换时间"的后端思维
- 画时序图时，纠结"为什么这一步要异步？" → 你开始理解高并发系统的设计思路
- 画类图时，想不通"这两个类为什么是依赖而不是继承？" → 你开始掌握面向对象的设计原则

---

### 第二层：建立后端的"架构直觉"

你有10年前端经验，你的大脑里已经有一套完整的前端思维框架了。画图的过程，就是在你的大脑里把"后端概念"映射到你已有的"前端知识体系"上。

| 前端思维              | 对应的后端思维                        |
| --------------------- | ------------------------------------- |
| 组件复用、颗粒度拆分  | 微服务边界、领域划分                  |
| useState / useReducer | 数据库设计、事务                      |
| React 生命周期        | NestJS 中间件、守卫、拦截器的执行顺序 |
| useEffect 依赖管理    | 缓存层级、缓存失效策略                |
| 浏览器事件循环        | Node.js 事件循环、异步编程模型        |

这个映射一旦建立完成：

- 你就不是从零学后端了
- 你是用10年前端经验去"类比"和"吸收"后端知识
- 学习速度是纯后端新人的 5-10 倍

### 第三层：培养架构师的"上帝视角"

普通开发者的视角：

```
Controller 写了吗？ → Service 写了吗？ → SQL 写对了吗？ → 跑起来了，搞定
```

架构师的视角（画完21张图后你就有了）：

```
这个请求要经过多少层？ → 每一层的开销是多少？ → 瓶颈在哪？
数据写入后，要更新哪几张表的缓存？ → 一致性怎么保证？
Redis 挂了降级到 MySQL，这个链路顺吗？
日志是同步写文件还是异步发 Graylog？ → 会不会阻塞主流程？
```

画图就是在练习"上帝视角"看整个系统：

- 画完整 ER 图，你会第一次真正理解"数据是怎么流动的"
- 画完整时序图，你会第一次真正理解"一个请求经历了什么"
- 画完整类图，你会第一次真正理解"代码是怎么组织的，为什么这么分层"

## 📝 3遍深度复刻法

每张图画 3 遍，不要只画 1 遍。

---

### 第 1 遍：照抄

**目标：熟悉 mermaid 语法，对结构有个印象**

- 看着参考图，原封不动画下来
- 不用太纠结为什么这么设计
- 先把结构和关系记下来
- 速度可以快一点

---

### 第 2 遍：默写 ⭐ 最关键

**目标：找出你的知识盲区**

这是最有价值的一步！

1. 把参考图完全关掉
2. 凭记忆和理解重新画一遍
3. **肯定会卡壳**
4. 卡壳了不要急着看答案
5. 先自己想 5 分钟：**如果是我，我会怎么设计？**
6. 想不出来，再看一眼答案，继续画

> 💡 这 5 分钟的思考，价值超过看 10 遍图！

你卡壳的地方，就是你的知识盲区。把这些盲区一个个填上，你的理解深度就会指数级增长。

---

### 第 3 遍：批判

**目标：建立架构思维**

再画一遍，这一次带着质疑的眼光：

- "这里这么设计真的好吗？有没有更好的方案？"
- "如果并发量 x10，这个设计会挂在哪？"
- "如果让我重新设计，我会怎么改？"
- "这个设计的 trade-off 是什么？（为了得到什么，牺牲了什么？）"

能提出问题，说明你真懂了！

## ❓ 每类图的 3 个灵魂拷问

画图时，每画一个元素，停下来问自己这 3 个问题。

---

### 画 ER 图时问：

1. **这个字段我当时为什么这么设计？**
   （我记得好像是因为查询要用到？）

2. **如果我把这个字段放到另一张表，会怎么样？**
   （性能会变差？JOIN 会变多？）

3. **我当时有没有想过其他方案？**
   （好像想过用数组存，后来为什么没选？）

---

### 画时序图时问：

1. **这一步我当时为什么要做成异步？**
   （记得当时同步写接口超时了...）

2. **如果这一步失败了，会发生什么？**
   （有降级吗？有重试吗？）

3. **把这两步顺序换一下行不行？**
   （为什么不行？会导致什么问题？）

---

### 画流程图时问：

1. **为什么要分成这几步？不能合并吗？**
   （职责分离？性能考虑？）

2. **这里为什么要加一层缓存？直接查库不行吗？**
   （查库的瓶颈是什么？）

3. **降级/回退路径是什么？**
   （中间某一步挂了怎么办？）

---

### 画类图时问：

1. **这个类我当时为什么要独立出来？**
   （记得当时是两个地方都要用...）

2. **如果把这个类合并到另一个类里行不行？**
   （代码会不会更乱？复用性会不会变差？）

3. **有没有我当时没想到的更好的设计？**

## ⏱️ 学习时间规划

| 学习内容     | 纯新人需要   | 你需要      |
| ------------ | ------------ | ----------- |
| ER 图 4 张   | 2-3 天       | 1 天        |
| 流程图 7 张  | 3-4 天       | 1.5 天      |
| 时序图 5 张  | 2-3 天       | 1 天        |
| 类图 5 张    | 3-4 天       | 1.5 天      |
| **全部完成** | **2 周左右** | **5 天** ⚡ |

**原因：**

- 你不需要理解"这是什么"——你已经知道了
- 你只需要建立"为什么这么设计"的因果关系
- 你有前端10年的架构直觉可以类比迁移

画完 21 张图之后，你会突然发现：

> "哦！原来后端的这些套路，我前端早就都在用了！只是名字不一样而已！"

到那时候，后端对你来说就没有"新知识"了，只是**同一个思想在不同领域的应用**而已。

## 🎯 完成标准

当你能做到以下几点，说明你出师了：

1. ✅ 关掉参考图，能凭理解默画出完整的 21 张图
2. ✅ 每张图的每个设计决策，你都能说出 3 个以上的理由
3. ✅ 能说出每个设计的 trade-off（为了得到什么，牺牲了什么）
4. ✅ 能指出 3-5 个可以优化的地方，并说明理由

## 💡 一句话总结

**AI 生成的图，是 AI 的理解，不是你的。**

你手写复刻的每一笔，都是在把 AI 的理解，**内化**成你自己的架构直觉。

画完这 21 张图，你对后端的理解深度，会超过很多**工作 2-3 年**的后端开发。因为大部分后端开发，每天也只是在写 CRUD，从来没有从上帝视角，完整地梳理过整个系统的架构。

> 纸上得来终觉浅，绝知此事要躬行。
