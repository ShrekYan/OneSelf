## 🧠 复刻图表时的思考模板

\*\*画任何一张图时，按这个顺序拷问自己：

### 📊 画 ER 图时问自己：

```
1. 这张表解决什么业务问题？没有这张表会怎样？

2. 字段类型选择的理由？
   BigInt vs DATETIME？ VARCHAR(36) vs INT？

3. 索引为什么建在这些列上？查询模式是什么？

4. 为什么需要/不需要冗余字段？
   Articles.author_name 为什么不 JOIN？

5. 如果并发量 x10，这张表会怎样？
```

---

### 🔄 画流程图/时序图时问自己：

```
1. 每一步的输入和输出是什么？

2. 如果这一步失败了会怎样？有降级方案吗？

3. 为什么是 A 调用 B，而不是 B 调用 A？

4. 这个流程的性能瓶颈可能在哪里？

5. 有没有可以并行处理的部分？
```

---

### 🏗️ 画类图时问自己：

```
1. 这个类的单一职责是什么？

2. 它依赖谁？谁依赖它？

3. 为什么用组合而不是继承？或者反过来？

4. 这个类的公开接口设计合理吗？是不是太大了？

5. 可测试性如何？
```

## 💡 设计决策速查表

| 决策              | 方案                 | 理由                               |
| ----------------- | -------------------- | ---------------------------------- |
| **时间戳类型**    | BigInt 毫秒          | 时区无关、计算方便、排序性能好     |
| **主键类型**      | UUID VARCHAR(36)     | 分布式安全、不暴露数据量           |
| **Token 存储**    | HttpOnly Cookie      | 防 XSS、自动携带                   |
| **密码算法**      | Argon2id             | 抗 GPU 攻击，比 bcrypt 更安全      |
| **登录性能**      | Redis 全量预加载     | 单实例支撑 600-1000 QPS            |
| **预加载切换**    | 原子双版本           | 同步失败不影响现有服务             |
| **Refresh Token** | Redis 全存储         | 登录流程零 MySQL                   |
| **日志传输**      | UDP GELF v1.1        | 无连接、高性能、允许少量丢失       |
| **日志存储**      | 本地文件 + Graylog   | 本地同步写保证不丢，异步发分析平台 |
| **异常处理**      | 多级 Filter 链式处理 | 业务异常 → 数据库异常 → 兜底异常   |

## 📖 使用说明

### 如何高效学习

1. \*\*第一天：每天学 1-2 张图，不要贪多
2. \*\*理解为主：先看 3 遍，理解了再动手画
3. **手写复刻**：关掉原图自己默写，卡壳才看一眼
4. **回答思考模板**：每张图画完后，必须回答 5 个问题
5. **对照代码**：去 `services/` 目录找对应代码印证

### 进阶玩法

- 每张图画 3 遍：
  - 第 1 遍：抄原图，熟悉语法
  - 第 2 遍：默写，看自己记住多少
  - 第 3 遍：改进，按自己的理解优化画法

- 画完后去看代码，对比理解
