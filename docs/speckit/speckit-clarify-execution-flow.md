# Speckit Clarify 执行机制详解

> **目标读者**: 想了解 `/speckit-clarify` 命令内部执行机制的新手
> **文档性质**: 需求澄清阶段技术手册
> **核心问题**: 如何系统性地检测并消除规格说明书中的模糊点？
> **权威来源**: 项目内置 Skill 定义（`.claude/skills/speckit-clarify`）

---

## 一、Clarify 阶段定位

```
Specify → [Clarify] → Plan → Tasks → Implement
             ↑
           你在这里
```

**核心职责**: `Clarify` 是 Speckit 工作流中的**需求质检与补全环节**。它通过系统化的模糊性扫描，识别 `spec.md` 中未被充分定义的区域，以交互式问答的方式与用户确认，并将结果永久写入规格说明书。

**类比**:

- `spec.md` = 业主需求书（"我要一栋三室两厅的房子"）
- `clarify` = 设计师与业主确认细节（"厨房要开放式还是封闭式？""卫生间要不要干湿分离？"）

**关键原则**:

- Clarify **不是一次性活动**，可以执行 0~N 次，直到不确定性降到可接受水平
- 每次澄清的问答必须**永久记录**在 `spec.md` 中，避免后期遗忘或扯皮
- 最多问 **5 个问题**，强制聚焦最关键的不确定性
- Clarify 必须在 `/speckit-plan` **之前**完成，否则下游返工风险剧增

## 二、执行前准备（Pre-Execution Checks）

### 2.1 Extension Hooks 检查

```text
检查 .specify/extensions.yml 是否存在
    │
    ├── 不存在 → 静默跳过，继续执行
    │
    └── 存在 → 读取 hooks.before_clarify 配置
          │
          ├── 筛选：跳过 enabled: false 的钩子
          ├── 筛选：跳过有非空 condition 的钩子（由 HookExecutor 处理）
          └── 对每个可执行钩子：
                ├─ optional: true → 显示可选钩子，等用户决定是否执行
                └─ optional: false → 自动执行，等待结果后再继续
```

**钩子命令转换规则**: `speckit.git.commit` → `/speckit-git-commit`

### 2.2 用户输入获取

Clarify 的输入来源有两种：

| 来源           | 示例                                  | 处理方式                               |
| -------------- | ------------------------------------- | -------------------------------------- |
| **命令行参数** | `/speckit-clarify "增加空值安全处理"` | 作为澄清主题的上下文提示               |
| **无参数调用** | `/speckit-clarify`                    | AI 自动扫描 spec，找出最值得澄清的问题 |

**关键规则**: 即使不提供参数，AI 也会执行完整的模糊性扫描。提供参数可以帮助 AI 聚焦特定领域。

### 2.3 环境检查

**命令**: `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`

**输出字段**:

| 字段           | 含义                     | 示例                              |
| -------------- | ------------------------ | --------------------------------- |
| `FEATURE_DIR`  | 当前特性目录             | `specs/001-string-utils`          |
| `FEATURE_SPEC` | 当前特性的 spec.md 路径  | `specs/001-string-utils/spec.md`  |
| `IMPL_PLAN`    | 实现计划路径（可选捕获） | `specs/001-string-utils/plan.md`  |
| `TASKS`        | 任务清单路径（可选捕获） | `specs/001-string-utils/tasks.md` |

**失败处理**: 如果 JSON 解析失败，中止执行并提示用户重新运行 `/speckit-specify`。

## 三、核心执行流程（Execution Flow）

Clarify 的执行分为三大阶段：**扫描（Scan）→ 问答（Question）→ 集成（Integrate）**。

```text
Phase 1: 扫描 (Scan)
    │
    ├── 加载当前 spec.md
    ├── 执行结构化模糊性扫描（10 大分类体系）
    ├── 对每个分类标记状态: Clear / Partial / Missing
    └── 产出: 内部覆盖图（不直接输出）
    │
    ▼
Phase 2: 问答 (Question)
    │
    ├── 生成最多 5 个候选问题（按 Impact × Uncertainty 排序）
    ├── 逐个向用户提问（每次只问 1 个）
    ├── 用户提供答案或接受推荐
    └── 记录到工作内存（暂不写盘）
    │
    ▼
Phase 3: 集成 (Integrate)
    │
    ├── 每个答案接受后立即更新 spec.md
    ├── 将问答写入 Clarifications 章节
    ├── 根据答案类型更新相关章节（Edge Cases / Requirements / Assumptions 等）
    ├── 每次写入后立即保存（原子覆盖）
    └── 执行验证检查
```

## 四、模糊性扫描分类体系（Taxonomy）

这是 Clarify 的核心算法。AI 从以下 10 个维度对 spec.md 进行结构化扫描：

### 4.1 功能范围与行为（Functional Scope & Behavior）

| 检查项                         | 示例                                 |
| ------------------------------ | ------------------------------------ |
| 核心用户目标与成功标准是否明确 | "快速处理" → 多快算快？              |
| 明确的范围外声明               | 是否明确说了"不做实时协作"？         |
| 用户角色/角色差异化            | 管理员和普通用户的功能差异是否定义？ |

### 4.2 领域与数据模型（Domain & Data Model）

| 检查项            | 示例                                          |
| ----------------- | --------------------------------------------- |
| 实体、属性、关系  | "文章"实体有哪些字段？标签是多对多吗？        |
| 身份与唯一性规则  | 用户 ID 是 UUID 还是自增？                    |
| 生命周期/状态转换 | 订单状态机：待支付 → 已支付 → 已发货 → 已完成 |
| 数据量/规模假设   | 预期多少用户？日活多少？                      |

### 4.3 交互与用户体验流程（Interaction & UX Flow）

| 检查项             | 示例                                             |
| ------------------ | ------------------------------------------------ |
| 关键用户旅程/序列  | 登录流程：输入 → 验证 → 跳转，每一步的交互细节？ |
| 错误/空值/加载状态 | 列表为空时显示什么？加载失败时显示什么？         |
| 可访问性与本地化   | 是否需要支持屏幕阅读器？是否需要多语言？         |

### 4.4 非功能质量属性（Non-Functional Quality Attributes）

| 检查项               | 示例                                 |
| -------------------- | ------------------------------------ |
| 性能（延迟、吞吐量） | API 响应时间要求？并发用户数？       |
| 可扩展性             | 水平扩展还是垂直扩展？               |
| 可靠性与可用性       | 允许多久的宕机时间？数据丢失容忍度？ |
| 可观测性             | 需要哪些日志、指标、链路追踪？       |
| 安全与隐私           | 认证方式？数据加密？威胁假设？       |
| 合规/监管约束        | GDPR？数据本地化要求？               |

### 4.5 集成与外部依赖（Integration & External Dependencies）

| 检查项                  | 示例                           |
| ----------------------- | ------------------------------ |
| 外部服务/API 及故障模式 | 依赖第三方支付，它挂了怎么办？ |
| 数据导入/导出格式       | 支持 CSV 还是 Excel？          |
| 协议/版本假设           | REST API 版本策略？            |

### 4.6 边界情况与失败处理（Edge Cases & Failure Handling）

| 检查项    | 示例                             |
| --------- | -------------------------------- |
| 负面场景  | 用户输入恶意脚本怎么办？         |
| 限流/节流 | API 调用频率限制？               |
| 冲突解决  | 两个人同时编辑同一篇文章怎么办？ |

### 4.7 约束与权衡（Constraints & Tradeoffs）

| 检查项                       | 示例                     |
| ---------------------------- | ------------------------ |
| 技术约束                     | 必须使用某个特定技术栈？ |
| 明确的权衡或已拒绝的替代方案 | 为什么不用方案 B？       |

### 4.8 术语与一致性（Terminology & Consistency）

| 检查项              | 示例                           |
| ------------------- | ------------------------------ |
| 规范术语表          | "用户"和"会员"是同一个东西吗？ |
| 避免同义词/废弃术语 | 统一用"文章"还是"帖子"？       |

### 4.9 完成信号（Completion Signals）

| 检查项             | 示例                                 |
| ------------------ | ------------------------------------ |
| 验收标准的可测试性 | "好用"无法测试，"2 秒内响应"可以测试 |
| 可测量的完成定义   | 代码覆盖率要求？性能基准？           |

### 4.10 杂项/占位符（Misc / Placeholders）

| 检查项               | 示例                                            |
| -------------------- | ----------------------------------------------- |
| TODO 标记/未解决决策 | spec 中是否还有 `[NEEDS CLARIFICATION]`？       |
| 模糊的形容词         | "robust"、"intuitive"、"user-friendly" 缺少量化 |

## 五、交互式问答机制

### 5.1 问题生成策略

AI 从扫描结果中提取 **最多 5 个** 候选问题，按 `(Impact × Uncertainty)` 启发式排序：

```text
 Impact（影响）: 答案对架构、数据建模、任务拆解、测试设计的影响程度
Uncertainty（不确定性）: 当前 spec 中该区域的信息缺失程度

排序公式: 优先处理高影响 + 高不确定性的区域
```

**问题约束**:

- 每个问题必须能用以下方式之一回答：
  - **多选题**: 2~5 个互斥选项
  - **短答案**: 明确限制 "Answer in <=5 words"
- 排除低影响问题（如纯代码风格偏好）
- 排除已有答案的问题
- 排除更适合 Plan 阶段的技术细节问题（除非阻塞功能明确性）

### 5.2 多选题呈现格式

AI 会分析所有选项，基于最佳实践给出**推荐选项**:

```text
**Recommended:** Option A - 理由：与项目现有风格一致，零依赖，风险最低

| Option | Description |
|--------|-------------|
| A | 使用原生方法实现 |
| B | 使用 lodash 实现 |
| C | 使用自定义正则实现 |
| Short | 提供不同的短答案（<=5 词） |

You can reply with the option letter (e.g., "A"), accept the recommendation by saying "yes" or "recommended", or provide your own short answer.
```

### 5.3 短答案呈现格式

对于无法提供有意义离散选项的问题：

```text
**Suggested:** 返回空字符串 "" - 理由：避免调用方因空值导致运行时异常，与防御式编程原则一致

Format: Short answer (<=5 words). You can accept the suggestion by saying "yes" or "suggested", or provide your own answer.
```

### 5.4 用户回答处理

| 用户输入                            | AI 行为                                                      |
| ----------------------------------- | ------------------------------------------------------------ |
| `yes` / `recommended` / `suggested` | 使用 AI 预先给出的推荐/建议作为答案                          |
| 选项字母（如 `A`）                  | 映射到对应选项的描述                                         |
| 自定义短答案                        | 验证是否符合 `<=5 词` 约束；模糊时请求澄清（不增加问题计数） |
| `done` / `good` / `no more`         | 提前终止问答                                                 |

**重要规则**:

- 每次只问 **1 个问题**
- 如果用户答案模糊，请求澄清（**不**增加问题计数）
- **绝不**提前透露后续排队的问题
- 达到 5 个问题或用户信号停止时结束问答

## 六、增量更新与验证

### 6.1 增量更新策略

每个答案被接受后，AI **立即**执行以下更新：

```text
1. 检查并创建 Clarifications 章节（如缺失）
2. 在 Clarifications 下创建 Session YYYY-MM-DD 子标题（如该 Session 首个答案）
3. 追加问答记录: "- Q: <问题> → A: <最终答案>"
4. 将澄清内容应用到最相关的章节:

   功能模糊性        → Functional Requirements
   用户交互/角色区分  → User Stories / Actors
   数据形状/实体      → Data Model（添加字段、类型、关系）
   非功能约束         → Success Criteria > Measurable Outcomes
   边界情况/负面流程   → Edge Cases / Error Handling
   术语冲突           → 统一术语；保留原文时加 (formerly referred to as "X")
```

### 6.2 更新规则

- **替换优于追加**: 如果新澄清使之前的模糊声明失效，**替换**而非追加
- **保持最小化**: 每个插入的澄清保持精简且可测试，避免叙述漂移
- **保留格式**: 不重新排序无关章节，保持标题层级完整
- **原子写入**: 每次集成后立即保存 spec.md，最小化上下文丢失风险

### 6.3 验证检查（每次写入后执行）

| 检查项         | 验证内容                                                        |
| -------------- | --------------------------------------------------------------- |
| 问答记录完整性 | Clarifications Session 中每个接受的答案恰好一条记录（无重复）   |
| 问题数量       | 总提问数（已接受）≤ 5                                           |
| 占位符清理     | 更新后的章节中不存在新答案本应解决的模糊占位符                  |
| 矛盾消除       | 不存在与新答案矛盾的早期声明                                    |
| Markdown 结构  | 仅允许新增的标题：`## Clarifications`、`### Session YYYY-MM-DD` |
| 术语一致性     | 所有更新章节中使用相同的规范术语                                |

## 七、与上下游的衔接

### 7.1 上游输入：spec.md

```text
spec.md 提供:
    ├── User Scenarios → 识别用户目标和验收场景是否完整
    ├── Edge Cases → 检查边界情况是否充分
    ├── Requirements → 检查功能需求是否可测试
    ├── Success Criteria → 检查成功标准是否可测量
    ├── Assumptions → 检查假设是否合理且完整
    └── Clarifications → 检查历史澄清是否已被充分吸收
```

### 7.2 下游影响：Plan 阶段

```text
Clarify 更新 spec.md 后:
    │
    ├── Edge Cases 更新 → Plan 阶段 Technical Context 的 Constraints 更新
    ├── Requirements 更新 → Plan 阶段 Project Structure 可能变化
    ├── Assumptions 更新 → Plan 阶段研究问题变化
    └── 术语统一 → Plan 阶段 data-model.md 命名一致
    │
    └── 必须重新运行 /speckit-plan（因为 spec 是 plan 的输入源）
```

### 7.3 何时需要重新 Clarify

| 场景                 | 操作                                 |
| -------------------- | ------------------------------------ |
| 需求变更（增删功能） | `/speckit-clarify` → `/speckit-plan` |
| 修改验收标准         | `/speckit-clarify` → `/speckit-plan` |
| 调整边界情况         | `/speckit-clarify` → `/speckit-plan` |
| 发现 spec 遗漏       | `/speckit-clarify`                   |
| 开发过程中发现歧义   | `/speckit-clarify`                   |

### 7.4 何时不需要 Clarify

| 场景             | 操作                    |
| ---------------- | ----------------------- |
| 技术实现方式调整 | 直接编辑 plan.md        |
| 文件路径调整     | 直接编辑 plan.md        |
| 代码风格调整     | 直接编辑 plan.md 或代码 |
| 修复代码 bug     | 直接编辑代码            |

## 八、实战案例：string-utils 的 4 次 Clarify

### 8.1 完整时间线

```text
初始需求: "apps/web/src/utils 中实现 3 个简单的字符串工具函数"
    │
    ▼
/speckit-specify → 生成 spec.md（初版）
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Clarify 1: "去除单元测试"                                        │
│ Q: 本特性是否需要编写单元测试？                                   │
│ A: 否，本特性不包含单元测试代码编写。                             │
│ 影响: spec.md → Assumptions 新增 "不包含单元测试"                 │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
/speckit-plan（第 1 次生成）
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Clarify 2: "测试使用 npm run lint 验证就行"                       │
│ Q: 本特性的验收方式是什么？                                       │
│ A: 使用 npm run lint 进行代码质量验证。                           │
│ 影响: spec.md → Clarifications 新增问答记录                       │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
/speckit-plan（第 2 次重新生成）
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Clarify 3: "增加空值安全处理（允许传入 null/undefined）"           │
│ 隐含 Q: 函数参数是否允许传入 null/undefined？                     │
│ A: 是，函数需对 null/undefined 做安全处理，返回空字符串 ""         │
│ 影响:                                                            │
│   - Edge Cases: 新增 "传入 null 或 undefined 时返回空字符串"       │
│   - Assumptions: 更新 "函数需对 null/undefined 做安全处理"        │
│   - data-model.md（后续 Plan 阶段）: 参数类型从 string 变为      │
│     string | null | undefined                                    │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
/speckit-plan（第 3 次重新生成）
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ Clarify 4: "去除 npm run lint"                                   │
│ Q: 本特性的验收方式是什么？                                       │
│ A: 代码实现正确即可，无额外验收步骤。                             │
│ 影响: spec.md → Clarifications 更新，覆盖之前的 lint 验收方式      │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
/speckit-plan（第 4 次重新生成）
    │
    ▼
/speckit-tasks → /speckit-implement → 生成 string.ts
```

### 8.2 4 次 Clarify 对比表

| 次数 | 指令                             | 变更内容                | spec.md 影响位置         | plan.md 是否重新生成 |
| ---- | -------------------------------- | ----------------------- | ------------------------ | -------------------- |
| 1    | `去除单元测试`                   | 明确不编写测试          | Assumptions              | 是                   |
| 2    | `测试使用 npm run lint 验证就行` | 验收方式改为 lint       | Clarifications           | 是                   |
| 3    | `增加空值安全处理`               | 参数支持 null/undefined | Edge Cases + Assumptions | 是                   |
| 4    | `去除 npm run lint`              | 取消验收步骤            | Clarifications           | 是                   |

### 8.3 影响最大的 Clarify：第 3 次

```text
变更前:
  export function trim(str: string): string;

变更后:
  export function trim(str: string | null | undefined): string;

传导链:
  spec.md Edge Cases 更新
    → plan.md Technical Context Constraints 更新
    → research.md 新增 "空值安全处理策略" 章节（决策：使用 str ?? ''）
    → data-model.md 所有函数参数类型改变
    → quickstart.md 使用示例新增 null/undefined 示例
    → string.ts 实现代码改变（return str.trim() → return (str ?? '').trim()）
```

## 九、常见问题（FAQ）

### Q1: 为什么 Clarify 必须在 Plan 之前完成？

**A**: 因为 Plan 阶段的所有技术决策（文件结构、接口类型、技术选型）都基于 spec.md。如果 spec 中还有未澄清的模糊点，Plan 就会基于猜测做出决策，导致后续 Implement 阶段返工。越早澄清成本越低。

### Q2: 一个问题被澄清后，AI 为什么立即更新 spec.md 而不是等全部问完？

**A**: 增量更新策略可以最小化上下文丢失风险。如果 AI 在内存中累积所有答案，最后一次性写入，中途发生错误可能导致全部丢失。每次答案接受后立即原子写入，更安全可靠。

### Q3: 为什么最多只能问 5 个问题？

**A**: 5 个问题是一个经验值，目的是强制 AI 聚焦**最关键**的不确定性，而不是事无巨细地问。如果 5 个问题后仍有重要未解决项，可以再次运行 `/speckit-clarify`。

### Q4: 用户回答模糊时，为什么不算新问题？

**A**: 澄清同一问题的歧义属于"同一问题的追问"，不消耗问题配额。这鼓励 AI 在继续前确保当前问题被充分理解，而不是匆忙跳到下一个问题。

### Q5: 我可以直接编辑 spec.md 而不使用 Clarify 吗？

**A**: 可以，但不推荐。Clarify 的价值在于：

1. **系统化扫描**: AI 从 10 个维度全面检查，你可能遗漏某些边界情况
2. **交互式确认**: 多选题和推荐答案帮助你快速决策
3. **永久记录**: Clarifications 章节的问答历史是团队知识沉淀

如果只是改个错别字，直接编辑即可。如果涉及功能、边界、验收标准，建议使用 Clarify。

### Q6: Clarify 和 Specify 中的 `[NEEDS CLARIFICATION]` 有什么区别？

**A**:

- **Specify 中的 `[NEEDS CLARIFICATION]`**: AI 在生成初始 spec 时标记的模糊点，通常最多 3 个，需要用户立即回答
- **Clarify**: 更全面的系统化扫描，可以执行多次，每次最多 5 个问题，支持增量更新

### Q7: 如果 AI 说 "No critical ambiguities detected"，还需要 Clarify 吗？

**A**: 不需要。但如果后续开发中发现遗漏，随时可以再次运行 `/speckit-clarify`。

### Q8: 为什么每次 Clarify 后都要重新 Plan？

**A**: 因为 `plan.md` 是派生文件（derived document），它的所有内容都是从 `spec.md` 推导出来的。spec 变了，plan 必须跟着变，否则会出现文档不一致。本案例中 4 次 Clarify 触发了 4 次重新 Plan。

## 十、总结

### Clarify 阶段的核心特征

| 特征           | 说明                                        |
| -------------- | ------------------------------------------- |
| **系统化扫描** | 从 10 大维度全面检查 spec 的模糊性          |
| **聚焦关键**   | 最多 5 个问题，按 Impact × Uncertainty 排序 |
| **交互式确认** | 每次只问 1 个问题，支持推荐选项和短答案     |
| **增量集成**   | 每个答案接受后立即更新 spec.md 并验证       |
| **永久记录**   | 所有问答写入 Clarifications 章节，可追溯    |
| **上游驱动**   | spec 变更后必须重新 Plan，保持文档一致性    |

### Clarify 的执行哲学

> **"把模糊变清晰，把口头变书面，把猜测变事实"**

开发中最大的返工来源不是技术难度，而是**需求理解不一致**。Clarify 阶段通过以下方式预防这个问题：

1. **系统化扫描**: 不依赖个人经验，从 10 个维度全面检查
2. **强制聚焦**: 最多 5 个问题，避免陷入无限讨论
3. **交互确认**: 多选题和推荐答案降低用户的决策成本
4. **即时记录**: 问答永久写入 spec，避免"当时说过但后来忘了"
5. **增量更新**: 每个澄清立即生效，降低上下文丢失风险

### 与上下游的关系

```text
spec.md（当前状态）
    │
    ├── 输入给 /speckit-clarify
    │     ├── 模糊性扫描（10 大 Taxonomy）
    │     ├── 交互式问答（最多 5 个）
    │     └── 增量更新 spec.md
    │
    ▼
更新的 spec.md
    │
    ├── Clarifications 章节: 新增问答记录
    ├── Edge Cases 章节: 新增边界情况
    ├── Requirements 章节: 更新功能需求
    ├── Assumptions 章节: 更新假设条件
    └── Success Criteria 章节: 更新可测量指标
    │
    ▼
/speckit-plan（基于更新后的 spec 重新生成）
```
