# .claude 配置体系架构总结

**归档日期**: 2026-05-07
**项目**: claude - H5 移动端 + NestJS 后端博客项目

---

## 🎯 核心设计思想：国家治理体系

| 层级比喻     | 对应目录/文件                            | 核心职责                                 | 一句话说明                              |
| ------------ | ---------------------------------------- | ---------------------------------------- | --------------------------------------- |
| **宪法**     | `DECISIONS.md` / `FRONTEND-DECISIONS.md` | 规定"**为什么**这么做"和"**边界**在哪里" | 不可随意修改，最高权威                  |
| **法律条文** | `rules/` 目录                            | 规定"**具体怎么做**"的细节               | 前后端共用，一处修改全体系生效          |
| **行政机关** | `agents/` 目录                           | 规定"**谁**来执行"和"执行的**流程**"     | 每个 Agent 是独立领域专家，有独立权限   |
| **办事指南** | `skills/` 目录                           | 规定"**具体场景**下按什么步骤做"         | 技术栈专项能力，可被多 Agent 复用       |
| **便民热线** | `commands/` 目录                         | 快捷入口，一键触发专用 Agent             | 用户不用管内部流程，输入命令就行        |
| **流水线**   | `workflows/` 目录                        | 多步骤自动化流程编排                     | 按顺序执行多个 shell 命令，支持条件分支 |
| **历史经验** | `project-memory.md` / `memory/`          | 踩坑教训积累，避免重复犯错               | 人工维护 + 自动更新                     |
| **行政许可** | `settings.json`                          | 工具权限白名单/黑名单、Hooks 配置        | 安全底线，防止破坏性操作                |

## 🔄 完整调用链（以"开发前端页面"为例）

```
用户：帮我开发登录页面
    ↓
CLAUDE.md 启动自动加载
    ↓
触发规则匹配 → 识别为前端开发任务
    ↓
frontend-developer 专用 Agent 启动
    ↓
#include 物理嵌入 12+ 个规则文件：
    ├─ FRONTEND-DECISIONS.md（前端架构决策）
    ├─ typescript-common.md（TS 通用规范）
    ├─ security-common.md（安全通用规范）
    ├─ code-format-common.md（格式规范）
    ├─ frontend-typescript.md（前端 TS 规范）
    ├─ frontend-css-scss.md（样式规范）
    └─ frontend-api-design.md（API 规范）
    ↓
Agent 执行任务：Read / Write / Edit
    ↓
自动调用 frontend-code-reviewer 审查代码
    ↓
返回结果给用户
```

| **workflows/** | 用户触发               | shell 命令                 | 按需      | 🟣 500 |

## 🔍 四层核心架构深度解析

### 传导链精确关系

```
宪法（DECISIONS）
    ↓ 提炼具体化：把"为什么"转化为"做什么"
法律条文（rules/）
    ↓ 按角色组装：把"做什么"分配给"谁来做"
行政机关（agents/）
    ↓ 按场景标准化：把"通用流程"细化为"特定场景步骤"
办事指南（skills/）
```

### 每一层解决的独特问题

#### 1. 宪法（DECISIONS）：解决团队认知对齐问题

**核心内容**：不仅说"用什么"，还要说"为什么用" + 边界约束

```markdown
## 决策 3：状态管理方案 - MobX

### 为什么选 MobX 而不是 Redux/Zustand？

1. 移动端 H5 包体敏感：MobX 比 Redux 小 40%
2. 团队有 3 年使用经验，学习成本为 0
3. 试过 Redux，样板代码太多，效率低 30%

### 边界约束

❌ 禁止使用任何其他状态管理库
❌ 禁止 observer() HOC，必须用 useObserver() Hook
```

**如果没有这层**：新人会质疑架构选择、遇到新场景 AI 不知道判断方向、架构师走了团队就散了。

---

#### 2. 法律条文（rules/）：解决可执行性问题

**核心内容**：把"为什么"转化为 AI 能理解的"具体怎么做"，有正反例子

```markdown
## 空值处理规范

✅ 正确：const userName = user?.name ?? '匿名用户'
❌ 错误：const userName = user?.name || '匿名用户' // 会把空字符串、0、false 也替换掉
```

**如果没有这层**：宪法只说"要用 TypeScript 严格模式"，但 AI 不知道"具体怎么写才算严格"、每个 Agent 重复写同样的规则、代码风格不统一。

---

#### 3. 行政机关（agents/）：解决角色与流程问题

**核心内容**：定义"谁来做" + "做的流程" + "做这件事需要什么工具权限"

```yaml
name: frontend-developer
tools: [Read, Write, Edit, Glob, Grep, Skill]  # 这个 Agent 能用哪些工具
triggers: ["开发前端页面", "创建组件"]       # 什么情况下自动触发

工作流程：
1. 先加载 skill 完整规范
2. 阅读需求 → 对照现有代码分析
3. 先定义类型 → 再写逻辑
4. 优先复用已有组件
5. 写完自动调用 code-reviewer 审查
```

**如果没有这层**：所有任务都用通用 Claude、权限过大容易误操作、没有固定流程、不会自动触发后续流程。

---

#### 4. 办事指南（skills/）：解决场景标准化问题

**核心内容**：特定场景下的 Step-by-Step 标准化操作步骤

```markdown
## 新建页面的标准流程

步骤 1：目录结构
```

apps/web/src/pages/Login/
├── index.tsx # 页面组件
├── useStore.ts # 页面状态管理
├── constant.ts # 常量
├── types.ts # 类型定义
└── styles.module.scss # 样式

```

步骤 2：useStore.ts 写法
- 必须用 `useLocalObservable`
- 方法必须用方法语法，不能用箭头函数
- 必须导出 Store 类型
```

**如果没有这层**：Agent 知道"要遵守规范"，但不知道"具体先写哪个文件"、每个页面结构都不一样、新人自己发明一套。

---

### 分层设计的 8 大好处

| 好处           | 说明                                                                 |
| -------------- | -------------------------------------------------------------------- |
| **单一职责**   | 改架构去 DECISIONS，改规范去 rules，改流程去 agents，改步骤去 skills |
| **复用最大化** | 一条 TypeScript 规则被 8+ 个 Agent 引用，一处修改全体系生效          |
| **冲突有解**   | 优先级明确：宪法 > 法律 > 办事指南 > 行政机关，不会出现规则冲突      |
| **上下文可控** | 分级加载，核心规则必载，场景规则按需加载，节省 Token                 |
| **人 AI 共用** | 架构师看宪法，技术负责人看规则，AI 看 Agent + Skill，各取所需        |
| **新人零成本** | 新人第一天就能写出符合团队 3 年积累规范的代码                        |
| **零架构债务** | 代码生成时就已符合架构，从根上杜绝架构腐化                           |
| **演进可控**   | 每次架构变更都有记录，可追溯、可批量重构旧代码                       |

---

### 核心洞察：架构治理的本质跃迁

| 传统架构治理                             | Claude Code 架构治理               |
| ---------------------------------------- | ---------------------------------- |
| 规则写在文档里，人写代码时不一定记得     | 规则直接变成 AI 的一部分           |
| Code Review 事后检查，发现问题时已有债务 | 代码生成时就已符合架构，事前拦截   |
| 零和博弈：审查 vs 被审查                 | 正和博弈：AI 帮你写对              |
| 新司机要考驾照、熟悉路况                 | 新司机上车就能开，车自己会遵守交规 |

> **从"人治" → "法治" → "自动化治理"的跃迁**

## ⚡ 三大关键设计机制

### 1. `#include:` 物理嵌入机制

```
# 不是运行时引用，而是编译期物理复制！

Agent 启动时，所有 #include 的规则文件直接变成 Agent 的 system prompt 的一部分
→ 100% 确保不会"忘了规范"
→ 修改一个规则，所有引用它的 Agent 立即生效
```

### 2. 强制执行协议（Commands 层）

以 `frontend-code-review.md` 为例：

> **🚨 强制执行协议（优先级 999）**
>
> 这是你必须执行的唯一动作，没有其他选择：
>
> - ✅ 立即调用 Agent：`frontend-code-reviewer`
> - ❌ 绝对禁止：主 Claude 自行扫描代码、跳过 Agent 直接输出、先解释再调用

**效果**：用户输入 `/frontend-code-review` 时，主 Claude 除了调用指定 Agent，什么都不能做 —— 完全杜绝不专业的即兴发挥。

### 3. 三级权限隔离

| 能力               | `frontend-developer` | `git-helper` | 普通对话 |
| ------------------ | -------------------- | ------------ | -------- |
| Read/Write/Edit    | ✅                   | ✅           | ❌       |
| Bash (git push)    | ❌                   | ✅           | ❌       |
| Glob/Grep 全局搜索 | ✅                   | ✅           | ❌       |
| Skill 调用         | ✅                   | ❌           | ❌       |

**效果**：每个 Agent 只能做职责范围内的事，最小权限原则。

## 🎯 为什么要分成这么多层？

| 不这么做的问题                             | 分层后的好处                          |
| ------------------------------------------ | ------------------------------------- |
| 所有规则写在一个文件 → 几千行无法维护      | 模块化，按领域拆分，可独立更新        |
| 修改一个规则要改 N 个地方                  | 通用规则一处修改，所有 Agent 立即生效 |
| 所有任务都用通用 Claude → 不专业、正确率低 | 专用 Agent 专司其职，正确率高 15-20%  |
| 权限过大容易误操作                         | 每个 Agent 独立权限，最小化风险       |
| 没有快捷入口，用户每次要描述完整需求       | 一个命令触发，不用重复说上下文        |
| 重复踩同样的坑                             | 记忆层积累经验，避免二次犯错          |

## 💡 核心洞察

> **Claude Code 本身的能力是 "基础分"（约 7 分），而 `.claude` 架构决策体系是 "加分项"（+2 分），把一个 70 分的工具变成了 90 分的生产力放大器。**

> **架构决策是「灵魂」，Claude Code 配置是「肉体」。两者结合，就是让 AI 不仅会写代码，还会"有思想"地写代码。**
