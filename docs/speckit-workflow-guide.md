# Speckit SDD 工作流完整指南

> **目标读者**: 新手开发者
> **适用范围**: 全项目特性开发
> **核心思想**: Specify（定义）→ Design（设计）→ Develop（开发）

---

## 一、什么是 Speckit

Speckit 是一个**结构化需求驱动开发（SDD）**工作流。它将传统的"想到哪写到哪"的开发方式，转变为**先定义、再设计、后实现**的分阶段流程。

### 为什么需要 Speckit

| 问题                           | Speckit 的解决方案                 |
| ------------------------------ | ---------------------------------- |
| 需求模糊，开发时才发现遗漏     | 先写 spec，强制明确所有边界        |
| 代码写完后发现不符合预期       | 先定义验收标准，开发有明确目标     |
| 多人协作时理解不一致           | spec 作为 Single Source of Truth   |
| 需求变更后文档不同步           | 派生文件机制，上游变更下游必须更新 |
| 技术决策没有记录，后期重复讨论 | research.md 永久保存决策依据       |

---

## 二、工作流总览

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Specify    │ ──▶ │  Clarify    │ ──▶ │    Plan     │ ──▶ │   Tasks     │ ──▶ │  Implement  │
│  (定义需求)  │     │  (澄清需求)  │     │  (技术规划)  │     │  (任务拆解)  │     │  (执行实现)  │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
                                                                                         │
                                                                                         ▼
                                                                              ┌─────────────────┐
                                                                              │   实际代码文件    │
                                                                              └─────────────────┘
```

### 各阶段一句话说明

| 阶段          | 命令                 | 核心问题               | 类比                 |
| ------------- | -------------------- | ---------------------- | -------------------- |
| **Specify**   | `/speckit-specify`   | "用户想要什么？"       | 建筑业的业主需求书   |
| **Clarify**   | `/speckit-clarify`   | "有哪些地方没说清楚？" | 设计师和业主确认细节 |
| **Plan**      | `/speckit-plan`      | "技术上怎么实现？"     | 建筑结构设计图       |
| **Tasks**     | `/speckit-tasks`     | "具体要做哪些事？"     | 施工任务清单         |
| **Implement** | `/speckit-implement` | "动手写代码"           | 工人按图施工         |

## 三、各阶段详解

### 3.1 Specify（定义需求）

**目的**: 将用户的一句话描述转化为结构化的规格说明书。

**输入**: 用户的自然语言描述，例如：

```text
apps/web/src/utils 中实现 3 个简单的字符串工具函数
- trim() - 去除首尾空格
- uppercase() - 转为大写
- lowercase() - 转为小写
```

**输出文件**:

| 文件                | 路径                                                | 作用                                                                 |
| ------------------- | --------------------------------------------------- | -------------------------------------------------------------------- |
| **spec.md**         | `specs/XXX-feature-name/spec.md`                    | **核心真相源**。包含用户故事、功能需求、验收场景、边界情况、假设条件 |
| **requirements.md** | `specs/XXX-feature-name/checklists/requirements.md` | 规格质量检查清单，确保 spec 达到可进入 Plan 阶段的标准               |

**spec.md 的核心结构**:

```markdown
# Feature Specification: [特性名称]

## User Scenarios & Testing ← 用户故事（谁、想要什么、为什么）

## Edge Cases ← 边界情况（null、空字符串、异常输入）

## Requirements ← 功能需求编号（FR-001、FR-002...）

## Success Criteria ← 成功标准（可测量的验收指标）

## Clarifications ← 澄清记录（问答历史）

## Assumptions ← 假设条件（开发前提）
```

**关键原则**: spec.md 是 **Single Source of Truth（唯一真相源）**。所有后续文档都基于它生成，spec 变了，下游文档必须同步更新。

---

### 3.2 Clarify（澄清需求）

**目的**: 检测并减少规格中的模糊点，将问答结果写回 spec.md。

**使用时机**:

- 刚完成 Specify，觉得有些地方不够明确
- 开发过程中发现 spec 有遗漏或需要调整
- 需求变更（增加功能、修改验收标准等）

**命令格式**:

```text
/speckit-clarify "你的问题或调整描述"
```

**本案例中的 Clarify 示例**:

| 次数 | 指令                             | 变更内容                | 影响                          |
| ---- | -------------------------------- | ----------------------- | ----------------------------- |
| 1    | `去除单元测试`                   | 明确不编写测试          | spec.md Assumptions 更新      |
| 2    | `测试使用 npm run lint 验证就行` | 验收方式改为 lint       | spec.md Clarifications 新增   |
| 3    | `增加空值安全处理`               | 参数支持 null/undefined | Edge Cases + Assumptions 更新 |
| 4    | `去除 npm run lint`              | 取消验收步骤            | Clarifications 更新           |

**Clarify 的核心价值**:

- 最多问 5 个问题，强制聚焦最关键的不确定性
- 每次问答永久记录在 spec.md 中，避免后期扯皮
- 越早澄清成本越低（在写代码前发现遗漏，比在测试阶段发现成本低 10 倍）

---

### 3.3 Plan（技术规划）

**目的**: 基于 spec.md 生成技术实现方案。

**重要**: plan.md 是 **派生文件（Derived Document）**。spec 变了，plan 必须重新生成。

**输出文件**:

| 文件              | 路径                      | 作用                                     | 读者            |
| ----------------- | ------------------------- | ---------------------------------------- | --------------- |
| **plan.md**       | `specs/XXX/plan.md`       | 技术方案总览：技术栈、项目结构、约束条件 | 开发者          |
| **research.md**   | `specs/XXX/research.md`   | 技术调研记录：决策依据、替代方案对比     | 开发者/架构师   |
| **data-model.md** | `specs/XXX/data-model.md` | 接口类型契约：函数签名、实体定义         | 开发者/测试人员 |
| **quickstart.md** | `specs/XXX/quickstart.md` | 快速开始指南：导入方式、使用示例         | 使用者          |

**plan.md 的核心结构**:

```markdown
# Implementation Plan: [特性名称]

## Summary ← 一句话总结做什么、在哪里做

## Technical Context ← 技术上下文（语言、依赖、平台）

## Constitution Check ← 架构约束检查（是否符合项目治理）

## Project Structure ← 项目结构决策（新增哪些文件、放在哪里）
```

**research.md 的价值**: 它不仅告诉你"选了什么"，更重要的是"为什么这样选"和"拒绝了什么"。例如：

```markdown
决策: 使用 str ?? ''（空值合并运算符）做前置保护
理由:

- ?? 仅对 null 和 undefined 生效，不会误处理空字符串 ''
- 相比 || 更安全，避免 falsy 值被错误替换
  替代方案考虑:
- str || ''：会错误地将空字符串、0、false 也替换，拒绝
```

**data-model.md 的本质**: 代码和规格之间的"合同"。开发者看了就知道函数该怎么写，测试人员看了就知道该怎么测。

---

### 3.4 Tasks（任务拆解）

**目的**: 将技术方案拆解为可执行的具体任务。

**输出文件**:

| 文件         | 路径                 | 作用                                                        |
| ------------ | -------------------- | ----------------------------------------------------------- |
| **tasks.md** | `specs/XXX/tasks.md` | 任务清单，按用户故事分组，每个任务包含 ID、优先级、文件路径 |

**任务格式规范**:

```text
- [ ] T001 [US1] 实现 trim 函数于 apps/web/src/utils/string.ts
  │      │   │      └─ 具体做什么 + 在哪里做
  │      │   └─ 属于哪个用户故事
  │      └─ 任务 ID（执行顺序）
  └─ 复选框（完成后标记为 [x]）
```

**任务组织原则**:

```markdown
## Phase 1: User Story 1 - 去除字符串首尾空格 (Priority: P1)

- [ ] T001 [US1] 实现 trim 函数于 apps/web/src/utils/string.ts

## Phase 2: User Story 2 - 字符串转为大写 (Priority: P1)

- [ ] T002 [US2] 实现 uppercase 函数于 apps/web/src/utils/string.ts

## Phase 4: Polish & Cross-Cutting Concerns

- [ ] T004 确保所有函数包含完整 JSDoc 注释
```

**为什么按用户故事分组**:

- 每个故事可以**独立实现和测试**
- 便于并行开发（不同故事可由不同人做）
- **MVP 思维**：做完 US1 就能用，不必等全部完成

---

### 3.5 Implement（执行实现）

**目的**: 按照 tasks.md 的任务清单，逐条执行，生成实际代码。

**AI 执行时的文件优先级**:

```
Primary Input（首要输入）
  ├── tasks.md          ← 执行顺序（做什么、按什么顺序）
  └── plan.md           ← 技术方案（怎么做、用什么技术）

Secondary Reference（次要参考）
  ├── data-model.md     ← 接口定义（函数签名）
  ├── quickstart.md     ← 使用示例
  └── spec.md           ← 需求兜底（有歧义时回查）

Tertiary Reference（辅助参考）
  └── research.md       ← 技术决策（为什么这样实现）
```

**执行规则**:

- AI 像"按图施工的建筑工人"，严格按文档执行
- 不会擅自添加文档没要求的功能
- 每完成一个任务，将 `- [ ]` 标记为 `- [x]`
- 如果 tasks 和 plan 有冲突，以 tasks 为准，但会参考 spec 确保不偏离需求

## 四、文件体系与关系

### 4.1 文件关系图

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              Single Source of Truth                         │
│                                  spec.md                                    │
│                              （核心真相源）                                  │
└─────────────────────────────────────────────────────────────────────────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
    ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
    │   plan.md       │    │   checklists/   │    │  contracts/     │
    │  （技术方案）    │    │  （质量检查）    │    │ （接口契约）     │
    └────────┬────────┘    └─────────────────┘    └─────────────────┘
             │
    ┌────────┴────────┐
    ▼                 ▼
┌─────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│research.│    │ data-model. │    │ quickstart. │    │  tasks.md   │
│  md     │    │    md       │    │    md       │    │ （任务清单）  │
│(技术调研)│    │ (接口定义)   │    │ (使用指南)   │    └──────┬──────┘
└─────────┘    └─────────────┘    └─────────────┘           │
                                                            ▼
                                                   ┌─────────────────┐
                                                   │  实际代码文件     │
                                                   │ （如 string.ts）  │
                                                   └─────────────────┘
```

### 4.2 文件分类

| 分类         | 文件                                                         | 说明                                 |
| ------------ | ------------------------------------------------------------ | ------------------------------------ |
| **源头文件** | spec.md                                                      | 唯一真相源，用户需求的结构化表达     |
| **派生文件** | plan.md, research.md, data-model.md, quickstart.md, tasks.md | 由上游文件生成，上游变更必须重新生成 |
| **检查文件** | checklists/requirements.md                                   | 质量门禁，确保规格达到标准           |
| **交付文件** | 实际代码文件（如 string.ts）                                 | 最终产物                             |

### 4.3 核心原则：瀑布依赖

```text
        spec.md  ← 用户视角："我要什么"
           │
           ▼
        plan.md  ← 开发视角："我怎么实现"
           │
           ▼
      tasks.md   ← 执行视角："具体做哪些事"
           │
           ▼
      string.ts  ← 代码视角："实际写出来的代码"
```

- **上层动了，下层必须跟着动**（spec 变了 → plan 必须重新生成 → tasks 可能需要更新 → implement 结果也会变）
- **下层动了，不用通知上层**（plan 的技术细节调整 → 不用改 spec）

## 五、核心决策法则

### 5.1 口诀

> **功能变了 → 改 spec → 重新 plan**
> **技术细节调整 → 直接改 plan**

### 5.2 判断对照表

| 场景             | 改 spec？ | 改 plan？ | 操作建议                             |
| ---------------- | --------- | --------- | ------------------------------------ |
| 增加/删除功能    | ✅        | 重新生成  | `/speckit-clarify` → `/speckit-plan` |
| 修改验收标准     | ✅        | 重新生成  | `/speckit-clarify` → `/speckit-plan` |
| 调整边界情况     | ✅        | 重新生成  | `/speckit-clarify` → `/speckit-plan` |
| 修改技术实现方式 | ❌        | ✅ 直接改 | 直接编辑 plan.md / research.md       |
| 调整文件路径     | ❌        | ✅ 直接改 | 直接编辑 plan.md                     |
| 修改代码风格     | ❌        | ✅ 直接改 | 直接编辑 plan.md 或代码              |
| 发现 spec 有遗漏 | ✅        | 重新生成  | `/speckit-clarify`                   |
| 修复代码 bug     | ❌        | ❌        | 直接改代码，无需改任何文档           |

### 5.3 记忆技巧

想象一个瀑布：

- **改源头（spec）**: 必须用 Clarify，然后重新 Plan
- **改中游（plan/research/data-model）**: 直接编辑，无需 Clarify
- **改下游（代码）**: 直接编辑，除非 bug 反映了需求理解错误

## 六、命令速查表

| 阶段          | 命令                      | 输入                    | 输出                                                  | 使用频率         |
| ------------- | ------------------------- | ----------------------- | ----------------------------------------------------- | ---------------- |
| **Specify**   | `/speckit-specify`        | 用户的一句话需求        | spec.md + checklists/                                 | 每个特性 1 次    |
| **Clarify**   | `/speckit-clarify "描述"` | 对 spec 的疑问或调整    | 更新的 spec.md                                        | 按需，0~N 次     |
| **Plan**      | `/speckit-plan`           | spec.md                 | plan.md + research.md + data-model.md + quickstart.md | spec 变更后执行  |
| **Tasks**     | `/speckit-tasks`          | plan.md + spec.md       | tasks.md                                              | plan 变更后执行  |
| **Implement** | `/speckit-implement`      | tasks.md + 所有设计文档 | 实际代码文件                                          | tasks 变更后执行 |

### 完整执行流程（正常路径）

```text
1. /speckit-specify "你的需求描述"
   └─ 生成 specs/XXX/spec.md + checklists/

2. （可选）/speckit-clarify "有哪些需要确认的"
   └─ 更新 spec.md

3. /speckit-plan
   └─ 生成 plan.md + research.md + data-model.md + quickstart.md

4. /speckit-tasks
   └─ 生成 tasks.md

5. /speckit-implement
   └─ 生成实际代码，标记任务完成
```

### 需求变更后的执行流程

```text
需求变更（如：增加一个函数、修改参数类型）
    │
    ▼
/speckit-clarify "变更描述"
    └─ 更新 spec.md
    │
    ▼
/speckit-plan
    └─ 重新生成 plan.md + research.md + data-model.md + quickstart.md
    │
    ▼
/speckit-tasks
    └─ 重新生成 tasks.md
    │
    ▼
/speckit-implement
    └─ 按新 tasks 执行
```

## 七、最佳实践

### 7.1 Specify 阶段

- **描述要具体**: 不要说"做个登录功能"，要说"用户输入手机号和验证码后完成登录"
- **验收标准要可测量**: "很快"不好测量，"2 秒内返回结果"可以测量
- **边界情况要提前想**: null、空字符串、超长输入、网络断开等

### 7.2 Clarify 阶段

- **不要跳过 Clarify**: 即使需求看起来很简单，也建议至少 clarify 一次
- **聚焦关键不确定性**: 最多 5 个问题，优先问影响架构和验收的问题
- **所有答案写入 spec**: 不要只记在脑子里

### 7.3 Plan 阶段

- **关注 research.md**: 这是最有技术价值的文件，记录了决策依据
- **data-model 要准确**: 类型定义是代码的合同，错了后期返工成本高
- **保持技术无关性**: spec 不关心"怎么做"，plan 才关心

### 7.4 Tasks 阶段

- **按用户故事分组**: 便于独立测试和增量交付
- **MVP 优先**: 先把核心功能做出来，再完善边缘功能
- **任务描述要具体**: 包含文件路径和期望输出

### 7.5 Implement 阶段

- **信任文档**: AI 严格按文档执行，如果结果不满意，先检查文档是否写清楚了
- **不要跳过 tasks**: 即使只有 1 个任务，也建议生成 tasks.md，保持流程一致性
- **完成后自我验证**: 对照 spec.md 的验收场景检查代码是否符合预期

## 八、常见问题（FAQ）

### Q1: 我已经改好了 plan.md，但发现 spec.md 也需要改，怎么办？

**A**: 先改 spec.md（用 `/speckit-clarify`），然后重新运行 `/speckit-plan`。不要反向操作，因为 plan 是派生文件。

### Q2: 我不想重新生成 plan，可以直接改 plan.md 吗？

**A**: 如果只是技术细节调整（如文件路径、实现方式），可以直接改 plan.md。但如果涉及功能、验收标准、边界情况，必须改 spec 并重新 plan。

### Q3: tasks.md 里的任务都完成了，但发现代码有个小 bug，要改哪里？

**A**: 直接改代码，不需要重新跑任何 Speckit 命令。因为 bug 修复不影响需求规格。

### Q4: 我想在代码里再加一个函数，要走完整流程吗？

**A**: 如果是计划内的函数（spec 里已定义），直接实现即可。如果是新函数，建议先 `/speckit-clarify` 更新 spec，再重新 `/speckit-plan` 和 `/speckit-tasks`。

### Q5: 一个特性需要 clarify 多少次？

**A**: 没有固定次数。本案例 clarify 了 4 次，简单特性可能 0~1 次，复杂特性可能 5 次以上。目标是**把不确定性降到可以接受的水平**。

### Q6: 为什么 spec.md 是 "Single Source of Truth"？

**A**: 因为所有其他文档（plan、tasks、data-model）都是从 spec 派生出来的。如果 spec 和 plan 出现矛盾，以 spec 为准。这样可以确保：无论下游文档怎么变，需求的源头只有一个。

## 九、总结

Speckit 工作流的核心价值可以用三句话概括：

1. **先定义，后实现**: 不写代码前先明确"要什么"和"怎么验收"
2. **文档即代码**: 所有设计决策都写入版本控制的文档，可追溯、可复用
3. **上游驱动下游**: spec 是唯一的源头，spec 变了，下游必须同步更新

### 适合使用 Speckit 的场景

- ✅ 新特性开发
- ✅ 大规模重构
- ✅ 多人协作的需求对齐
- ✅ 需要长期维护的项目

### 可以简化或跳过 Speckit 的场景

- ⚠️ 紧急 bug 修复（直接改代码）
- ⚠️ 一行代码的改动（如改个常量值）
- ⚠️ 纯探索性实验（ exploratory spike）

---

_本文档总结了 Speckit SDD 工作流的完整流程，适用于所有特性开发场景。_
