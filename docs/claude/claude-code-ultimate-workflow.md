# Claude Code 终极工作流

> 大上下文时代的最高效 AI 协作方法论
>
> **核心哲学：你画框，AI 填内容；你拍板，AI 干脏活累活。**

**最后更新：2026-05-07**

---

## 🎯 核心理念

### 一句话总结

> **用一个大的、聪明的脑袋想清楚所有事情。**
> **然后用一堆小的、干净的脑袋把事情一件件做好。**

### 核心洞察

1. **上下文越大，信噪比越低** —— 1M Token 一直聊，实际有效信息不如 100k 干净上下文
2. **原子拆分 + /clear 是永恒真理** —— 无论 Token 做到多大，执行阶段永远是零污染最准
3. **人定方向，AI 补细节** —— AI 是高管，不是老板，方向必须人来定
4. **配置是法律，需求是订单** —— 不要把外卖订单贴进国家法典

## 🧠 前置：三层记忆体系（项目初始化时做一次）

```
第一层：核心规则层 · 永远自动加载
├─ 位置：.claude/rules/*.md
├─ 内容：TypeScript 规范、代码格式、安全规则、组件规范
├─ 特点：跨项目通用，永恒不变，必须 100% 严格遵守

第二层：项目决策层 · 本项目自动加载
├─ 位置：.claude/DECISIONS.md
├─ 内容：本项目特有的架构决策（认证方案、数据库命名、通信约定）
├─ 特点：项目级生命周期，每条都有决策日期 + 理由

第三层：业务需求层 · 永远不要自动加载
├─ 位置：你的脑子里 / XMind / 随便什么地方
├─ 内容：具体功能的需求描述和任务拆分
├─ 特点：一次性的，做完就可以扔
```

**黄金原则：配置只管规则，不管具体功能需求。**

## 🔀 第一步永远是：分流判断

拿到任何需求，先花 10 秒钟判断：

```
拿到需求
    ↓
问自己：做这个需求，我需要新增架构决策吗？
    ↓
    ├─ 需要新增决策 → 🟥 走【架构级完整流程】
    └─ 不需要新增决策 → 🟩 走【纯业务简化流程】
```

| 需求类型  | 判断标准                                      | 例子                                                   |
| --------- | --------------------------------------------- | ------------------------------------------------------ |
| 🟥 架构级 | 会改变项目的"游戏规则"，需要写入 DECISIONS.md | 做第三方登录、加支付功能、引入新技术栈、改造数据库结构 |
| 🟩 业务级 | 用现有技术栈就能做，不需要改规则              | 做文章收藏、加评论点赞、用户改昵称、加一个列表页面     |

## 📋 🟩 纯业务需求简化流程（日常开发 80% 的情况）

```
┌─────────────────────────────────────────────────────────────┐
│ 阶段 0：你的先手思考（不开 AI · 10 分钟）                   │
├─────────────────────────────────────────────────────────────┤
│  想清楚：这个功能要什么效果？边界情况有哪些？               │
│  脑子里 / XMind 粗略拆好 3-5 个原子任务                     │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ 阶段 1：快速确认（可选 · AI 辅助 · 5 分钟）                 │
├─────────────────────────────────────────────────────────────┤
│  简单需求直接跳过这步，复杂的可以跟 AI 聊 5 分钟补一下边界   │
│  【注意】不需要改 DECISIONS.md！                             │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ 阶段 2：微观执行（零污染 · 高精准）                          │
├─────────────────────────────────────────────────────────────┤
│  每个任务独立会话 → 做完就 /clear → 下一个                  │
└─────────────────────────────────────────────────────────────┘
```

**就是这么简单！日常开发大部分时候根本不需要搞那么复杂。**

## 🔑 必须坚守的核心原则（一条都不能破）

| 原则                 | 说明                                                                      |
| -------------------- | ------------------------------------------------------------------------- |
| **物理隔离原则**     | 设计会话和执行会话必须物理隔离。不要在同一个会话里又聊方案又写代码。      |
| **零污染原则**       | 执行会话只知道"我现在要做什么"，完全不知道"其他 9 个任务要做什么"         |
| **决策只进不出原则** | DECISIONS.md 只追加新决策，不删旧决策（除非真的推翻了），绝对不写业务功能 |
| **人定方向原则**     | 方向必须人来定，AI 只负责补细节、挑漏洞、做推演                           |
| **用完就扔原则**     | 执行会话用完就 /clear，不要留恋，不要舍不得                               |
| **形式不重要原则**   | 任务清单写在哪无所谓，你记得就行。核心原则守住了就好。                    |

## 💎 灵活运用指南（不要被教条绑架）

| 情况                                   | 可以怎么做                                      |
| -------------------------------------- | ----------------------------------------------- |
| **超简单需求（1 个小时就能做完）**     | 直接开干，拆都不用拆，一个会话做完就 clear      |
| **中等需求（3-5 个任务，当天做完）**   | 脑子里拆好，一个个做，不用写下来                |
| **复杂需求（>5 个任务，要做 2-3 天）** | 建议用 XMind 记一下任务清单，怕忘了进度         |
| **超大型架构改造（跨周/跨月）**        | 走完整流程，写 docs/tasks/xxx.md 归档，方便追踪 |
| **团队协作开发**                       | 任务清单必须写下来，所有人同步进度              |

**核心判断标准：你会不会忘。不会忘就不用写，会忘就写下来。**

## ❓ 常见问题解答

### Q1：已经有规则文件了，还需要 DECISIONS.md 吗？

**A：非常需要。** 规则是跨项目通用的"法律"，DECISIONS.md 是本项目的"宪法修正案"。每个项目都会有自己特有的架构约定，这些不应该写到通用规则里。

### Q2：任务清单需要存成文件让 AI 看到吗？

**A：完全不需要！** 任务清单是给你自己看的，不是给 AI 看的。你做哪个任务，口头告诉 AI 就行。把任务清单放进配置里反而会造成上下文污染。

### Q3：/compact 什么时候用？我现在的流程里好像不需要了？

**A：你现在的流程确实几乎不需要了。** /compact 只有一种情况能用：设计会话聊了 300 条消息，Token 快满了，手动 /compact 一次继续聊。执行会话用完就 /clear，永远不需要 /compact。

### Q4：为什么不能在一个会话里把所有任务都做完？

**A：因为污染。** 做任务 2 的时候，AI 脑子里还有任务 1 的细节，很容易把任务 1 的逻辑错误地带到任务 2 里。上下文越干净，犯错的概率越低。

### Q5：我用 XMind 管任务，不用写 Markdown 文件，可以吗？

**A：太可以了！** 用什么工具管任务完全无所谓，只要你自己清楚，核心原则守住了就行。不要被方法论的形式绑架。

## ✅ 快速检查清单（每次开发前扫一眼）

- [ ] **分流判断**：这个需求是架构级还是业务级？要不要走完整流程？
- [ ] **先手思考**：我自己想清楚方向了吗？有没有把方向扔给 AI 来定？
- [ ] **物理隔离**：设计会话和执行会话是分开的吗？
- [ ] **决策沉淀**：如果有新的架构决策，我加到 DECISIONS.md 里了吗？
- [ ] **零污染执行**：每个原子任务都是新开的干净会话吗？
- [ ] **用完就扔**：任务完成后 /clear 了吗？

## 📚 附录：架构级需求完整实战演示

### 🎯 需求背景

为博客系统新增文章评论功能，用户可以发表评论、删除评论、查看评论列表。

**分流判断**：需要新增评论表，改变数据架构 → 架构级流程。

---

#### 阶段 0：你的先手思考（不开 AI · 30 分钟）

你在 XMind 上画：

```
【文章评论功能 - 架构思考】
├─ 数据层面：评论独立分表，第一版先做一级评论
├─ 接口层面：查列表、发表、删除、作者可以删所有人的
└─ 粗拆任务：
   ├─ 任务 1: 数据库设计 - 新建评论表
   ├─ 任务 2: 后端 API - 评论增删改查 + 分页
   ├─ 任务 3: 后端 API - 评论权限校验
   ├─ 任务 4: 前端页面 - 评论列表渲染
   └─ 任务 5: 前端交互 - 发表 + 删除评论
```

---

#### 阶段 1：宏观设计（AI 辅助 · 15 分钟 · 只聊不写）

你跟 AI 说：

> "我要做文章评论功能，这是我初步想的架构，帮我评估一下有没有遗漏的边界情况，帮我优化一下任务拆分。"

你们讨论 15 分钟后，确认：

```
【最终确认的架构决策（2条）】
1. 评论表独立分表，不嵌入文章表
2. 第一版只做一级评论，字段预留 parent_id 方便未来扩展

【AI 帮你优化后的原子任务清单】
任务 1: 数据库设计 - 新建评论表
任务 2: 后端 API - 评论的增删改查 + 分页
任务 3: 后端 API - 评论权限校验（作者/本人）
任务 4: 前端页面 - 评论列表渲染
任务 5: 前端交互 - 发表评论 + 删除评论
```

---

#### 阶段 2：决策沉淀（3 分钟）

把 2 条新决策写入 `.claude/DECISIONS.md`，任务清单你 XMind 里记着就行。

---

#### 阶段 3：逐个执行任务

**做任务 1**：开新会话 → "帮我做评论表的数据库设计" → 做完 clear

**做任务 2**：开新会话 → "帮我做评论的后端 API 接口" → 做完 clear

**做任务 3**：开新会话 → "帮我做评论的权限校验逻辑" → 做完 clear

...以此类推。

每个会话都是干净的，零污染。

## 💎 终极智慧

> **最好的上下文管理，就是根本不需要管理上下文。**
>
> 让 AI 记住该记住的，忘记该忘记的。
> 能够区分什么是该记住的，什么是该忘记的。
>
> 守死核心原则，放开所有形式。
> 怎么高效怎么来，怎么顺手怎么用。
