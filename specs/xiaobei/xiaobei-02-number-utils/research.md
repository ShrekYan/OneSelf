# Research: 小贝数字工具函数

## Decision: 在前端工具目录新增数字工具入口

**Rationale**: 仓库中已有 `apps/web/src/utils/string.ts` 承载小贝字符串工具函数，数字工具同属前端通用工具能力，放在 `apps/web/src/utils/number.ts` 能保持目录职责一致，并避免影响页面、组件、状态管理、API 或后端服务。

**Alternatives considered**:

- 放入现有 `string.ts`：数字能力与字符串能力混杂，文件职责不清晰。
- 放入共享包：当前需求仅面向小贝前端工具函数，放入跨系统共享包会扩大影响范围。
- 放入页面目录：数字工具是通用能力，不应绑定具体页面。

## Decision: 使用原生数字运算实现 add 和 multiply

**Rationale**: 两数相加与相乘是轻量同步计算，语言原生运算即可满足需求。保持实现简单可读，不引入额外依赖或抽象。

**Alternatives considered**:

- 引入数学工具库：当前仅有两个基础计算函数，依赖过重。
- 包装为异步流程：计算不依赖网络或外部资源，异步化会增加不必要复杂度。

## Decision: formatNumber 使用千位分隔展示并保留有效小数信息

**Rationale**: 规格要求格式化数字显示、千位以上数字需要更易读，并且不应丢失有效小数信息。默认使用常见英文逗号千位分隔形式，例如 `12345` -> `12,345`，小数部分按输入数字的标准字符串结果保留。

**Alternatives considered**:

- 固定保留两位小数：会改变输入数字的小数信息，与规格中“不应无故截断或四舍五入”冲突。
- 不添加千位分隔符：无法满足大数字可读性要求。
- 支持多地区格式：会扩大范围，引入 locale 选择与展示差异；当前规格未要求。

## Decision: 输入范围限定为 number

**Rationale**: 规格假设 add、multiply、formatNumber 均仅面向数字输入。使用明确数字输入能保持类型简单、边界清晰，并避免字符串、空值或非数字值带来的隐式转换。

**Alternatives considered**:

- 接受字符串数字并自动转换：会引入隐式转换和错误处理范围，超出当前需求。
- 接受 `null` / `undefined` 并兜底为 0：会隐藏调用方错误，且不符合类型声明完整的目标。

## Decision: 不新增或运行单元测试

**Rationale**: 用户已明确补充“不需要单元测试”。计划阶段仅保留契约核对、TypeScript 类型检查和 lint 作为验证方式，避免创建与用户要求冲突的测试任务。

**Alternatives considered**:

- 为数字工具新增 Vitest 用例：与用户明确要求冲突。
- 运行现有测试套件：当前需求未要求，且可能被无关测试配置影响。
