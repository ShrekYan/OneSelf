# 测试与通信类 Skills 模板

## 适用技能

适用于测试验证、自动化操作和沟通内容生成类 skills：

- `webapp-testing`
- `internal-comms`

## 分类特征

测试与通信类 skill 虽然产物不同，但都依赖“场景识别 + 示例/流程加载 + 结构化输出”：

1. `webapp-testing` 偏执行型，目标是验证 Web 应用行为、调试 UI、截图和查看日志。
2. `internal-comms` 偏内容生成型，目标是根据沟通类型生成符合组织风格的文本。
3. 两者都依赖 `examples/` 提供可复用样例。
4. 两者都需要先判断任务类型，再选择对应流程。
5. 输出必须明确、可检查，并能支撑用户下一步行动。

## 典型目录结构

testing-or-comms-skill/

## 场景识别模板

```markdown
## Scenario Routing

1. 判断用户意图属于哪一类：
   - 测试验证
   - 调试定位
   - 截图或日志采集
   - 状态汇报
   - 领导更新
   - FAQ / 事故报告 / 项目更新
2. 根据场景选择示例或流程。
3. 若缺少关键输入，先询问最少必要信息。
4. 生成可执行步骤或结构化内容。
5. 验证结果是否满足场景目标。
```

## 示例加载规则

`examples/` 应根据任务类型按需加载：

| 场景 | 示例文件类型 | 使用方式 |
|------|--------------|----------|
| Web 自动化测试 | `.py`、`.md` | 参考操作顺序、定位元素、获取日志 |
| 静态 HTML 自动化 | `.py` | 参考浏览器启动、页面加载、截图 |
| 控制台日志检查 | `.py` | 参考如何捕获 console 和错误 |
| 内部状态汇报 | `.md` | 模仿结构、语气和信息密度 |
| FAQ | `.md` | 模仿问答结构和清晰度 |
| 事故报告 | `.md` | 模仿时间线、影响、处置、后续行动 |

加载原则：

1. 只加载与当前任务类型最接近的示例。
2. 不把所有示例一次性塞入上下文。
3. 示例用于模仿结构和风格，不应无脑复制内容。
4. 如果用户提供了组织规范，应优先遵守用户规范。

## 测试执行流程模板

```markdown
## Web App Testing Workflow

1. 确认应用地址、测试目标和用户路径。
2. 打开页面并等待关键内容加载。
3. 发现元素和交互入口。
4. 执行用户操作。
5. 捕获页面状态、截图、网络或 console 日志。
6. 判断实际结果是否符合预期。
7. 输出复现步骤、观察结果和问题定位建议。
```

测试类输出建议：

```markdown
# 测试结果

## 测试目标

## 执行环境

## 操作步骤

## 实际结果

## 预期结果

## 发现的问题

## 证据

## 建议下一步
```

## 沟通内容生成流程模板

```markdown
## Internal Communications Workflow

1. 判断沟通类型：状态更新、领导汇报、FAQ、事故报告、项目更新等。
2. 收集受众、目标、背景、关键事实、语气和长度要求。
3. 读取最接近的示例。
4. 生成结构化草稿。
5. 检查是否清晰、具体、面向行动。
6. 根据用户反馈迭代语气、长度和重点。
```

沟通类输出建议：

```markdown
# {{沟通标题}}

## TL;DR

## 背景

## 当前状态

## 关键影响

## 下一步行动

## 需要决策或支持
```

## 验证清单

### 测试类

- [ ] 是否明确测试目标。
- [ ] 是否记录应用地址或入口。
- [ ] 是否描述操作步骤。
- [ ] 是否区分实际结果和预期结果。
- [ ] 是否提供截图、日志或其他证据。
- [ ] 是否给出可复现信息。
- [ ] 是否避免执行破坏性或未授权操作。

### 通信类

- [ ] 是否明确受众。
- [ ] 是否说明沟通目标。
- [ ] 是否包含必要背景。
- [ ] 是否突出关键信息和下一步行动。
- [ ] 语气是否符合场景。
- [ ] 是否避免编造事实。
- [ ] 是否标出需要用户补充的信息。

## 适用示例

### 示例 1：Web 应用测试

```markdown
用户需求：帮我验证本地页面的登录流程是否正常。

流程：
1. 确认本地地址和账号条件。
2. 打开页面。
3. 输入登录信息并提交。
4. 检查跳转、提示、console 日志。
5. 输出测试结论和证据。
```

### 示例 2：内部项目更新

```markdown
用户需求：帮我写一份本周项目进展更新。

流程：
1. 确认受众和用途。
2. 收集进展、风险、阻塞和下一步。
3. 参考项目更新示例。
4. 输出结构清晰的沟通草稿。
```

### 示例 3：FAQ 草稿

```markdown
用户需求：把新功能上线说明整理成 FAQ。

流程：
1. 提取用户关心的问题。
2. 按主题分组。
3. 使用简洁回答。
4. 标记需要业务确认的问题。
```
